  PART 1 — ARCHITECTURAL DECISION: ONE SCHEMA OR TWO?
================================================================================

  This section documents the comparison required by the revised brief.
  The decision must be based on the ACTUAL code, not preference.

  ─────────────────────────────────────────────────────────────────────────
  1.1 WHAT LAYER 1 REQUIRES vs WHAT THE CURRENT SCHEMA PROVIDES
  ─────────────────────────────────────────────────────────────────────────

  Layer 1 requirements (from revised spec):
    Header:     voyageId, agentId, polId, podId
    Cargo rows: array of { containerTypeId, quantity, rate, dg, dgValue,
                           commodity, vgm }   ← one row per container type
    totalFreight = SUM(row.quantity × row.rate)
    NO: containerNumber, carrierName, consignee, shipper, containerStatus

  Current Booking schema (confirmed from booking.model.js):
    containerNumber   required:true, unique index   ← primary match key
    containerTypeId   required:true                 ← single container type
    quantity          required:true                 ← single number
    freightRate       required:true                 ← single rate
    totalFreight      required:true                 ← single computed value
    No cargoRows array exists

  ─────────────────────────────────────────────────────────────────────────
  1.2 APPROACH A — EXTEND THE EXISTING BOOKING SCHEMA
  ─────────────────────────────────────────────────────────────────────────

  Proposed changes to booking.model.js:
    - Add:  bookingType: enum ['manual','operational'], default:'operational'
    - Add:  cargoRows: [{ containerTypeId, quantity, rate, dg, dgValue,
                          commodity, vgm, rowTotal }]
    - Change: containerNumber → required:false, default:null  (breaks index)
    - Change: containerTypeId → required:false                 (conditional)
    - Change: quantity, freightRate → required:false           (conditional)
    - Change: totalFreight → required:false, compute from rows OR from qty×rate

  Impact analysis on EACH consumer if Approach A is used:

  a) bookingImport.service.js
     - previewImport() builds: existingMap[b.containerNumber] = b
       If containerNumber is null on Layer 1 docs, null maps to existingMap[null].
       All Layer 1 docs overwrite each other in the map.
       THE DEDUP CHECK SILENTLY BREAKS for all bookings with null containerNumber.
     - validateRow() currently errors if containerNumber is missing.
       Must be made conditional on importType or add a bookingType filter
       to the Booking.find() query.
     - Final Loading reconciliation:
         Booking.updateMany({ containerNumber:{$nin:[...]} })
       If Layer 1 docs (null containerNumber) exist on the same voyage,
       $nin:['MSCU123',...] MATCHES nulls and cancels Layer 1 docs.
       Final Loading reconciliation now incorrectly cancels manual bookings.

  b) capacity.service.js
     - Currently queries: Booking.find({voyageId, status, isDeleted}).
       Selecting: quantity, containerTypeId.size
     - Layer 1 docs have no quantity at the document level (it's in cargoRows).
       The capacity engine reads b.quantity → undefined → NaN → 0 TEU for
       all Layer 1 docs. Capacity is silently undercounted.
     - Must add conditional logic to check cargoRows or quantity.

  c) reports.service.js
     - getRoundPnL: $group: { totalRevenue: {$sum:'$totalFreight'} }
       Layer 1 totalFreight is computed from cargoRows, not from qty×rate.
       If the field name is the same ('totalFreight'), this works IF the
       server correctly computes and stores it. No change needed here.
     - getVoyagePerformance: $group: { totalQty: {$sum:'$quantity'} }
       Layer 1 has no top-level quantity. Sum returns 0 for all Layer 1 docs.
       Reports silently undercount.

  d) dashboard.service.js
     - Booking.countDocuments — Layer 1 docs counted as bookings. Correct.
     - Aggregate on $quantity → same problem as reports.

  e) invoice.service.js — reads booking by id. No functional issue.

  f) export.service.js — exports Booking fields. Layer 1 docs would export
     with many null fields (containerNumber, containerTypeId etc). Misleading
     but not breaking.

  CONCLUSION ON APPROACH A:
    The import service BREAKS (containerNumber dedup + Final Loading cancel).
    The capacity engine SILENTLY UNDERCOUNTS (reads b.quantity which is null).
    The reports SILENTLY UNDERCOUNT (totalQty from $quantity).
    Fixing each of these requires branching on bookingType in every consumer.
    That is a shotgun surgery: 6+ files each need if/else on bookingType.
    The "minimum change" goal is violated — more files change than with Approach B.
    Approach A is REJECTED on technical grounds, not preference.

  ─────────────────────────────────────────────────────────────────────────
  1.3 APPROACH B — SEPARATE ManualBooking SCHEMA, SAME MODULE
  ─────────────────────────────────────────────────────────────────────────

  A new manualBooking.model.js inside the SAME bookings/ module folder.
  Separate MongoDB collection. Uses cargoRows[].

  Impact analysis on EACH consumer if Approach B is used:

  a) bookingImport.service.js → ZERO CHANGES. It queries Booking only.
     The Final Loading reconciliation only touches Booking.
     ManualBooking is invisible to the import flow.

  b) capacity.service.js → TARGETED ADDITION: one extra query to sum
     manualBooking cargoRows per voyage. The Booking query is unchanged.

  c) reports.service.js → TARGETED ADDITION: one aggregate per report
     function to add L1 revenue/counts. Existing aggregates unchanged.

  d) dashboard.service.js → TARGETED ADDITION: one aggregate for L1 counts.
     Existing Booking aggregates unchanged.

  e) invoice, export, existing booking CRUD → ZERO CHANGES.

  Files changed with Approach B vs Approach A:
    Approach A: booking.model.js + booking.validation.js + booking.service.js
                + bookingImport.service.js + capacity.service.js
                + reports.service.js (3 functions) + dashboard.service.js
                + BookingForm.jsx + BookingDetailCard.jsx = 9+ files, each with
                conditional branching throughout.
    Approach B: 4 new files (all inside bookings/) + targeted additions to
                capacity, reports, dashboard = 7 files, no branching in existing code.

  CONCLUSION ON APPROACH B:
    Fewer files changed. Zero branching in existing consumers.
    Import and Final Loading flow are completely unaffected.
    Existing Booking schema stays exactly as Sprint 021 left it.
    This satisfies minimum change + backward compatibility + no shotgun refactoring.

  PART 3 — GOAL 2: VOYAGE-BASED CAPACITY ENGINE
================================================================================

  ─────────────────────────────────────────────────────────────────────────
  3.1 THE EXACT PROBLEM WITH THE CURRENT ALGORITHM
  ─────────────────────────────────────────────────────────────────────────

  Current algorithm in capacity.service.js computeRoundCapacity():

    Step A: loads Route + RouteLegs (ordered by sequence)
    Step B: builds portSeqByPortId from leg sequence numbers
    Step C: for each booking, emits load event at polSeq, discharge at podSeq
    Step D: running sum across port sequences → onboardAfterTEU per port
    Step E: derives "segments" from ADJACENT ROUTE LEG PAIRS
    Step F: for each synthetic segment, looks for a voyage with matching
            polId:podId → marks isManualJump:true if not found

  Example where this goes wrong:
    Route: Port1 → Port2 → Port3
    Actual voyages in round: [Port1→Port3] (one manual voyage, Port2 skipped)
    Booking: on voyageId = that Port1→Port3 voyage

    Current result:
      Synthetic segment 1: Port1→Port2 (isManualJump=true, no covering voyage)
      Synthetic segment 2: Port2→Port3 (isManualJump=true, no covering voyage)
      Booking's polSeq=1, podSeq=3 → events at seq 1 and seq 3
      Segment 1 onboard = booking TEU  ← shows capacity used on a leg that
                                           does not exist as an actual voyage
      Segment 2 onboard = 0           ← incorrect

    Correct result (voyage-based):
      Voyage 1: Port1→Port3, onboardTEU = booking TEU, utilisationPct = X%
      That is the only capacity row that should exist.

  ─────────────────────────────────────────────────────────────────────────
  3.2 REVISED ALGORITHM — VOYAGE-FIRST, MINIMUM CODE CHANGE
  ─────────────────────────────────────────────────────────────────────────

  The new algorithm replaces Steps A–F with a simpler voyage-first approach.

  NEW Steps A–D:

    Step A: Load round + voyages + bookings + manualBookings
      REMOVED from load: Route, RouteLeg  (no longer needed)

      const [voyages, bookings, manualBookings] = await Promise.all([
        Voyage.find({ _id:{ $in: round.voyageIds } })
              .populate('polId', 'name code')
              .populate('podId', 'name code')
              .sort({ sequence: 1 }).lean(),
        Booking.find({ voyageId:{$in:round.voyageIds}, isDeleted:false,
                       status:{$in:statuses} })
               .select('quantity voyageId containerTypeId containerNumber status')
               .populate('containerTypeId','code size isDeleted')
               .lean(),
        ManualBooking.find({ voyageId:{$in:round.voyageIds}, isDeleted:false,
                             status:{$in:statuses} })
                     .select('totalTEU totalFreight totalUnits voyageId status')
                     .lean(),
      ]);

    Step B: Group Layer 2 bookings by voyageId, compute TEU per voyage
      const l2ByVoyage = {};
      for (const b of bookings) {
        const vid = String(b.voyageId);
        if (!l2ByVoyage[vid]) l2ByVoyage[vid] = { bookingCount:0, teu:0, units:0, revenue:0 };
        const {teu, matched} = resolveTEU(b.containerTypeId?.size);
        if (!matched) push MISSING_TEU_MAPPING warning;
        l2ByVoyage[vid].teu          += b.quantity * teu;
        l2ByVoyage[vid].units        += b.quantity;
        l2ByVoyage[vid].bookingCount += 1;
      }

    Step C: Group Layer 1 manual bookings by voyageId
      const l1ByVoyage = {};
      for (const m of manualBookings) {
        const vid = String(m.voyageId);
        if (!l1ByVoyage[vid]) l1ByVoyage[vid] = { teu:0, units:0, revenue:0 };
        l1ByVoyage[vid].teu     += m.totalTEU     || 0;
        l1ByVoyage[vid].units   += m.totalUnits   || 0;
        l1ByVoyage[vid].revenue += m.totalFreight || 0;
      }

    Step D: Build voyages[] array (replaces segments[])
      const cap = vessel.capacity ?? null;
      const voyageRows = voyages.map(v => {
        const vid  = String(v._id);
        const l1   = l1ByVoyage[vid] || { teu:0, units:0, revenue:0 };
        const l2   = l2ByVoyage[vid] || { bookingCount:0, teu:0, units:0 };
        const onboardTEU    = l1.teu + l2.teu;
        const remainingTEU  = cap != null ? cap - onboardTEU : null;
        const utilisationPct = cap != null ? Math.round(onboardTEU/cap*100) : null;
        if (remainingTEU != null && remainingTEU < 0) push VOYAGE_OVERBOOKED warning;
        return {
          voyageId:      v._id,
          voyageNumber:  v.voyageNumber,
          sequence:      v.sequence,
          isManual:      v.isManual || false,
          fromPort:      { portId:String(v.polId?._id||v.polId), name:v.polId?.name, code:v.polId?.code },
          toPort:        { portId:String(v.podId?._id||v.podId), name:v.podId?.name, code:v.podId?.code },
          etd:           v.etd, eta: v.eta,
          voyageStatus:  v.status,
          layer1:        { unitCount:l1.units, teu:l1.teu, revenue:l1.revenue },
          layer2:        { bookingCount:l2.bookingCount, unitCount:l2.units, teu:l2.teu },
          onboardTEU, remainingTEU, utilisationPct,
        };
      });

    Step E: Totals (same logic, different source array)
      peakOnboardTEU    = Math.max(...voyageRows.map(v=>v.onboardTEU), 0)
      peakVoyageIndex   = index of peak
      avgUtilisationPct = mean of non-null utilisationPct values
      totalBookedTEU    = sum of onboardTEU across voyages
      totalBookedUnits  = sum of (l1.units + l2.units)

  CODE REMOVED vs CURRENT:
    - Route and RouteLeg queries (2 DB calls eliminated)
    - portSeqByPortId map construction (~10 lines)
    - Event list build loop (~15 lines)
    - Running sum loop (~10 lines)
    - Segment loop with voyage lookup (~25 lines)
    - Port summary array (~10 lines)
    Total removal: ~70 lines of algorithmic complexity

  PART 9 — RISK ANALYSIS
================================================================================

  R1   Capacity payload shape change breaks frontend consumers
       Severity: Medium. All 4 frontend consumers (VesselDetail, Capacity
       components, RoundCapacityReport, dashboard widget) update in Phase 3
       in the same deploy. There are no external API consumers.
       Mitigation: update all in one atomic release.

  R2   /bookings/manual route captured by /:id
       Severity: Low. Fully mitigated by placing /manual/* routes ABOVE /:id
       in booking.routes.js. Express first-match semantics guarantee correct
       routing. Must be verified in T14 test.

  R3   ManualBooking TEU stored in totalTEU — becomes stale if size changes
       Severity: Low. ContainerType.size is a hard enum (CONTAINER_SIZES).
       Changing size of a container type after bookings exist is a data ops
       concern. Engine invalidation is cache-based (60s TTL). Acceptable.

  R4   Reports double-count if L1 + L2 added naively
       Severity: Low. L1 and L2 come from different collections via separate
       aggregations. As long as the $sum operations are on different data,
       there is no double-count. Code review verifies during Phase 5.

  R5   Layer 2 Final Loading cancels Layer 1 bookings on same voyage
       Severity: Low. Final Loading reconciliation queries Booking collection
       only. ManualBookings are in a different collection — invisible to it.
       No cancel can happen. Confirmed by Q3 in §4 above.
