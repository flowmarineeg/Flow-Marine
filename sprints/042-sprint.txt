# 1. POINT 1 — IMPORT TEMPLATE: REQUIRED = RED HEADER, OPTIONAL = YELLOW HEADER

## 1.1 Current state (built in Sprint 041, confirmed from source)

`frontend/src/modules/bookings/BookingImport.jsx`'s `downloadImportTemplate()`
(added this sprint cycle, per Sprint 041) builds the blank template entirely
client-side using the `xlsx` npm package (SheetJS Community Edition,
confirmed `"xlsx": "^0.18.5"` in `frontend/package.json`):

```js
const downloadImportTemplate = () => {
  const headers = TEMPLATE_FIELDS.map(f => f.col);
  const ws = XLSX.utils.aoa_to_sheet([headers]);
  ws['!cols'] = headers.map(h => ({ wch: Math.max(h.length + 2, 14) }));
  const wb = XLSX.utils.book_new();
  XLSX.utils.book_append_sheet(wb, ws, 'Import Template');
  XLSX.writeFile(wb, 'booking-import-template.xlsx');
};
```
`TEMPLATE_FIELDS` already carries a `req: true/false` flag per column
(shared with the on-page "Expected Excel Columns" guide card), so the data
needed to decide red-vs-yellow already exists — the only missing piece is
applying a cell fill color when writing the file.

## 1.2 Hard technical constraint found — client-side styling is not possible

**SheetJS Community Edition (the `xlsx` package used here) does not write
cell style information (fills/colors/fonts) into the output file — cell
styling (`cell.s`) is a Pro-only feature in this library.** Setting
`ws['!cols']` (column width) works today because it's a structural
property, not a style; a `fgColor`/`fill` on a cell would be silently
dropped by `XLSX.writeFile()`. This is not a bug in this codebase's usage
— it's a documented library-tier limitation of SheetJS CE.

The backend, by contrast, already uses **ExcelJS** (`backend/src/modules/
export/export.service.js`, `"exceljs"` dependency) for every generated
export file, and ExcelJS DOES support header-cell fills — confirmed
working pattern already in this codebase:
```js
const headerRow = worksheet.getRow(1);
headerRow.font      = { bold: true, color: { argb: 'FFFFFFFF' }, size: 11 };
headerRow.fill      = { type: 'pattern', pattern: 'solid', fgColor: { argb: 'FF2E4057' } };
```

## 1.3 Recommended fix — move template generation to the backend (ExcelJS)

Add a new backend endpoint, `GET /bookings/import/template`, in
`backend/src/modules/bookings/booking.routes.js` (alongside the existing
`/import/preview` and `/import/save` routes, same `rbac('bookings',
'import')` guard, no `audit()` needed — a template download mutates
nothing). A new `bookingImport.controller.js#downloadTemplate` calls a new
`bookingImport.service.js#buildImportTemplate()` that builds the workbook
with ExcelJS directly (same low-level mechanism `export.service.js`
already uses, NOT its `buildExcelBuffer()` function itself — that function
also unconditionally adds an "Export Info" metadata sheet, which doesn't
belong on a blank fill-in template).

The frontend's `downloadImportTemplate()` becomes a network call
(`bookingsService.downloadImportTemplate()` → blob → trigger download),
replacing the client-side `XLSX.writeFile()` call. `TEMPLATE_FIELDS` (the
single source of truth for column header + required/optional flag, shared
with the on-page guide card) needs to be mirrored on the backend for this
endpoint to read — **see Open Question Q1 below**, since duplicating this
array in two places (frontend guide card, backend template builder) is
exactly the kind of drift Sprint 041 was careful to avoid elsewhere.

## 1.4 Color coding

- Required column header cell (e.g. Container Number, Container Type,
  Container Status, POL, POD, Rate — the six marked `req: true` in
  `TEMPLATE_FIELDS`): red fill (e.g. `FFF8D7DA` light red or `FFDC3545`
  solid red — see Q2), matching this system's existing "required" red
  accent (`text-red-400`/`text-red-500` already used for asterisks
  system-wide, per §2 findings below).
- Optional column header cell (Booking Number, Shipper, Consignee, Carrier
  Name, Commodity, VGM, Hazardous, IMDG Code): yellow fill (e.g.
  `FFFFF3CD`).
- Only the header cell/row gets the fill — NOT the full column (confirmed
  this is the client's explicit ask: "make its column [header] the cell
  that write the name in it bg red, no the full column, the title text").

## 1.5 Decisions (locked in)

- **Q1 — Canonical column list location → DECIDED: backend is the single
  source.** A new `GET /bookings/import/template-columns` (or the
  template columns embedded in the existing template endpoint's own
  metadata) becomes the one authority; the frontend's "Expected Excel
  Columns" guide card fetches its list from the backend instead of
  keeping a separate hardcoded `TEMPLATE_FIELDS` array — zero drift risk,
  same principle Sprint 041 applied elsewhere.
- **Q2 — Color values → DECIDED: use the example shades.** Light red
  `FFF8D7DA` header background for required columns, light yellow
  `FFFFF3CD` for optional columns.

# 2. POINT 2 — REQUIRED/OPTIONAL FIELD LABELING: "Req" / "Option"

## 2.1 Current state — confirmed inconsistent, exhaustively audited

A full pass over every form component (`frontend/src/modules/**/*.jsx`,
~20 modules) plus the shared `Input.jsx`/`Select.jsx` components and every
backend `*.validation.js` file found **seven different, incompatible
conventions already coexisting in this codebase**, and the specific words
"Req"/"Required"/"Option"/"Optional" as a labeling convention appear
**nowhere** today:

1. `<span className="text-red-400">*</span>` — the majority pattern for
   required fields (RoundForm, VesselForm, ExpenseForm, TrackingForm,
   ContainerTypeForm, ExpenseTypeForm, InvoiceForm's CreateInvoiceForm,
   RouteEditor, BookingImport settings, VoyageAddForm, and the shared
   `Input.jsx`/`Select.jsx` components used by AgentForm/LocationForm/
   UserForm/RoleList).
2. `text-red-500` instead of `text-red-400` — `ServiceForm.jsx` only, a
   plain shade inconsistency on top of the above.
3. `(optional)` literal parenthetical text — AgentForm's Agent Code,
   VoyageAddForm/VoyageEditForm's Voyage Code, and `BookingForm.jsx`/
   `ManualBookingForm.jsx`'s shared local `FieldLabel({required,
   optional})` helper.
4. `(opt)` abbreviated — `RouteEditor.jsx`'s Terminal/Agent fields only, a
   fourth wording nobody else uses.
5. `"X (optional)"` baked directly into the label string —
   `LocationForm.jsx`'s UNLOCODE field only.
6. A gray "expansion" span that looks like a marker but isn't one at all
   — `VoyageAddForm.jsx`/`VoyageEditForm.jsx`'s ETD/ETA/ETP/ATD/ATA
   fields show `<span>Estimated Departure</span>` etc., decorative only.
7. **No marker whatsoever** — the majority of genuinely optional fields
   across nearly every form: every Status select, every Notes/Remarks/
   Description textarea, all ~20 of VesselForm's optional particulars
   (loa, beam, draft, tonnages, bunker capacities, manager, etc.),
   InvoicePaymentPanel's Payment Date/Method/Reference, every
   ManualBookingForm cargo-row table column (table layout, no per-cell
   label at all), InvoiceForm's EditInvoiceForm fields, RoleList's
   Description field.

Two more structural findings worth carrying into the fix:
- Several fields are **conditionally required** (Booking's `imdgCode`
  only when `dg=true`; Vessel's `charterStartDate`/`charterEndDate` only
  when `ownershipType==='Chartered'`) but are shown with an unconditional
  "required" marker once visible — the marker doesn't communicate the
  condition.
- Several UI-required fields are backend-optional or vice versa (e.g.
  Expense's `voyageId`/`portId` are backend-optional but the UI marks
  them required when `linkType` selects that mode; Invoice's
  `EditInvoiceForm` marks `invoiceDate`/`dueDate`/`currency` as
  client-required via React Hook Form even though the backend
  `validateUpdate` has no such requirement).

## 2.2 Fix direction — DECIDED, simplified from the original ask

**Decision:** required fields keep/get a single, consistent red asterisk
`*` (standardized on one shade, `text-red-400`, fixing `ServiceForm.jsx`'s
deviating `text-red-500`) — no "Req" word/tag. **Optional fields get NO
marker at all** — every existing `(optional)`/`(opt)`/`"X (optional)"`
variant found in §2.1 (items 3, 4, 5) is REMOVED, not replaced with an
"Option" word. This replaces the original "Req"/"Option" wording
requirement with a simpler, decided convention: asterisk-only for
required, nothing for optional.

Given the shared `Input.jsx`/`Select.jsx` components already centralize
the asterisk for several forms, and `BookingForm.jsx`/
`ManualBookingForm.jsx` already have a local `FieldLabel` doing a
similar job (just inconsistently, with extra optional-marker text to
now remove), the fix should:
1. Standardize `Input.jsx`/`Select.jsx`'s asterisk color/shade (already
   `text-red-400`) as the one reference implementation.
2. Simplify `BookingForm.jsx`'s local `FieldLabel` to drop its
   `optional` prop/rendering entirely — required fields keep their `*`,
   optional fields render the label plain.
3. Fix `ServiceForm.jsx`'s `text-red-500` → `text-red-400` (shade
   consistency).
4. Remove every `(optional)`/`(opt)`/embedded-"(optional)" instance
   found in §2.1 (AgentForm's Agent Code, VoyageAddForm/VoyageEditForm's
   Voyage Code, RouteEditor's Terminal/Agent, LocationForm's UNLOCODE) —
   label text reverts to plain, no parenthetical.
5. Add the missing `*` to every genuinely-required field currently
   showing NO marker at all (the largest bucket in §2.1 item 7 — but
   note per this decision these fields need ONLY the asterisk added
   when required; truly optional fields in that same bucket, e.g. every
   Status select and Notes/Remarks/Description textarea, get nothing,
   which is already correctly their current state — no change needed
   for those).
6. The decorative gray "expansion" spans on VoyageAddForm/
   VoyageEditForm's ETD/ETA/ETP/ATD/ATA (`<span>Estimated
   Departure</span>` etc.) are NOT part of this convention and are left
   untouched — they were never a required/optional marker, just an
   abbreviation explainer.

## 2.3 Decision

- **Q6 — Conditionally-required fields → DECIDED: current behavior is
  fine, no change.** `imdgCode` and Vessel's `charterStartDate`/
  `charterEndDate` keep their unconditional `*` once visible — no
  dynamic recomputation needed, since the field is only ever rendered in
  the first place when the triggering condition is already true.

# 3. POINT 3 — VALIDATION / MUTATION ERROR TOAST UX

## 3.1 Current state — confirmed uniform, confirmed shallow

Every create/update/delete mutation across every module (~30 files
surveyed, list in the audit — AgentForm/List, VesselForm/List,
ServiceForm/List, RoundForm/List/Detail/VoyageList, VoyageAddForm/
EditForm, BookingForm/ManualBookingForm/List/DetailCard/
ManualBookingDetail/Import, ExpenseForm/List, ExpenseTypeForm,
InvoiceForm/List/PaymentPanel, LocationForm/LevelTable, TrackingForm,
UserForm/List, RoleList/PermissionMatrix, MasterTable) follows the
identical shape:
```js
onError: (e) => toast.error(e.response?.data?.message || 'X failed'),
```
— a single flat string, no title, no distinction between a validation
error, a business-rule block (e.g. "Cannot delete — vessel is assigned to
round R000001"), and an unexpected server error.

**Confirmed: the backend's own validation errors carry more detail than
the frontend ever shows.** Every `*.validation.js` file responds with:
```js
badRequest(res, 'Validation failed', errors.array().map(e => ({ field: e.path, message: e.msg })));
```
i.e. `{ message: 'Validation failed', errors: [{field, message}, ...] }`.
**No frontend `onError` handler anywhere reads `e.response?.data?.errors`
— only the flat `message` field ("Validation failed") is ever shown.**
When express-validator rejects 3 fields at once, the user sees only the
generic string "Validation failed", never which 3 fields or why.

`react-hot-toast` v2.4.1 (confirmed in `package.json`) supports JSX
content in `toast.error()`, not just strings — but **nowhere in the
codebase is JSX ever passed to `toast.error()`; it is a plain string in
every single call found.**

`ConfirmDialog.jsx` (used for every delete confirmation system-wide) has
no error state and no way to render a validation-errors array — it takes
a single static `message` prop set before opening; the actual failure
reason is only ever shown via the toast, never inside the dialog.

## 3.2 The one existing richer pattern (reference, don't duplicate)

`BookingImport.jsx`'s preview/save flow already has bespoke, real
per-field feedback — a per-row `_errors: string[]` array rendered as
bulleted list in an "Issues" column, plus red-bordered cell highlighting
matched by substring against each error string. This is NOT wired to the
standard express-validator `errors[]` shape used by every other module —
it's a special-case mechanism unique to bulk Excel import, and out of
scope to touch (it already does what this point is asking for, for that
one screen).

Two other minor deviations found, not necessarily wrong but worth
reconciling for consistency:
- `RouteEditor.jsx` additionally surfaces its error as a persistent inline
  amber banner alongside the toast (still just the flat message string).
- `InvoiceList.jsx`'s PDF download catch block is the only one that
  doesn't even attempt `e.response?.data?.message` — always shows the
  static `'Failed to generate PDF'`.

## 3.3 Fix direction

1. Every `onError` handler should render a toast with:
   - A clear, short **title** (e.g. "Couldn't delete vessel", "Couldn't
     save round") distinct from the detail line — using `toast.error()`'s
     JSX-content support (already available, unused today) rather than a
     flat string.
   - The backend's actual message as the detail line (e.g. "Vessel is
     assigned to active round R000001") — this part already exists, just
     needs a title added above it.
   - When `e.response?.data?.errors` is present (express-validator's
     per-field array), list each `{field, message}` pair instead of just
     the generic "Validation failed" top-line message.
2. A single shared helper (e.g. `utils/errorToast.js`'s
   `showErrorToast(error, fallbackTitle)`) used everywhere, replacing the
   ~30 duplicated `onError` bodies — same "one shared implementation"
   principle as Point 2's `FieldLabel` promotion.
3. `InvoiceList.jsx`'s PDF-download catch gets brought in line with the
   new shared helper (closes the one confirmed deviation).

## 3.4 Decisions (locked in)

- **Q7 — Title text source → DECIDED: fixed generic title per action
  type.** One shared helper (`showErrorToast(error, actionType)` where
  `actionType` is `'save'|'update'|'delete'`) picks a fixed title —
  "Couldn't save", "Couldn't update", "Couldn't delete" — not a
  per-module custom string. Simpler, one implementation, still a real
  improvement over today's titleless flat string.
- **Q8 — Per-field validation errors → DECIDED: list them inside the
  toast.** When `e.response?.data?.errors` (the express-validator
  `{field, message}` array) is present, the toast body lists each one as
  a short line under the title, instead of only showing the generic
  "Validation failed" top-line message. Field-level inline highlighting
  on the actual form inputs is explicitly OUT of scope for this sprint —
  toast-only.
- **Q9 — `ConfirmDialog` scope → DECIDED: toast is enough.**
  `ConfirmDialog.jsx` stays a simple static-message component; the
  improved toast (title + detail, per Q7/Q8) is the only place a blocked
  delete's reason appears. No inline error state added to the dialog
  itself.

# 4. POINT 4 — BOOKING IMPORT PREVIEW TABLE: MAX-HEIGHT + INTERNAL SCROLL

## 4.1 Current state, confirmed

`frontend/src/modules/bookings/BookingImport.jsx`'s preview table wrapper
(around the current line ~538-540):
```jsx
<div className="card overflow-hidden max-w-full min-w-0">
  <div className="overflow-x-auto">
    <table className="w-full border-collapse text-[12px]" style={{ minWidth: 1600 }}>
```
This already correctly contains HORIZONTAL overflow (per Sprint 032's
established `min-w-0`+`overflow-x-auto` pattern, reused here) — but there
is no VERTICAL constraint at all. A large import file (hundreds of rows)
renders every row in the DOM with no height cap, growing the card (and the
whole page) to match, forcing the user to scroll the entire page past a
very tall table instead of scrolling just the table body.

## 4.2 Fix

Add a max-height + `overflow-y-auto` to the same wrapper that already
handles horizontal scroll — same class-pair convention this codebase
already uses for horizontal overflow, extended to the vertical axis:
```jsx
<div className="overflow-x-auto overflow-y-auto max-h-[65vh]">
```
Sticky header (`<thead>` `sticky top-0` with a solid background) should
be added at the same time so column headers stay visible while scrolling
a long preview — without it, scrolling loses the header, which reads as
a regression next to the fix.

No open question — this is a self-contained CSS fix with an obvious,
low-risk implementation; height value (65vh vs. a fixed px value) is an
implementation detail, not a decision needed up front.

# 5. POINT 5 — ROUND → ACTIVE CASCADES ITS VOYAGES TO DEPARTED

## 5.1 Current state, confirmed

`round.model.js`: `status: { type: String, enum: ['Planned','Active',
'Completed','Cancelled'], default: 'Planned' }`. `round.service.js#create()`
accepts any `data.status` (including `'Active'` directly at creation,
`|| 'Planned'` as the only fallback — no restriction on initial status).
`round.service.js#update()` validates transitions via its own
`STATUS_TRANSITIONS` map (`Planned → [Active, Cancelled]`, `Active →
[Completed, Cancelled]`) before allowing a status change.

`voyage.model.js`: `status: { type: String, enum: ['Scheduled',
'Departed','In Transit','Arrived','Completed','Cancelled'], default:
'Scheduled' }`. `voyage.service.js`'s own `STATUS_TRANSITIONS`:
`Scheduled → [Departed, Cancelled]`, `Departed → [In Transit, Arrived,
Cancelled]`, `In Transit → [Arrived, Cancelled]`, `Arrived → [Completed]`,
`Completed/Cancelled → []` (terminal).

**Confirmed: no cascade from Round status to Voyage status exists
anywhere today.** Voyages are only ever status-transitioned individually,
by an admin, via `VoyageEditForm.jsx`/`voyage.service.js#update()`.

## 5.2 Fix direction — DECIDED

When a Round's status becomes `'Active'` — either at creation
(`round.service.js#create()` with `data.status === 'Active'`) or via
update (`round.service.js#update()` transitioning `Planned → Active`) —
**only the round's FIRST voyage (lowest `sequence`) currently in
`'Scheduled'` status is updated to `'Departed'`** (§5.3 Q10). Later legs
(sequence 2, 3, …) stay `Scheduled` until an admin advances them
individually as the vessel actually progresses, matching how a
multi-leg voyage physically happens one leg at a time.

Implementation would be, inside `create()` (only when
`data.status==='Active'`) and inside `update()` (only on the
`Planned→Active` transition):
```js
const firstVoyage = await Voyage.findOne({ roundId, status: 'Scheduled' }).sort({ sequence: 1 });
if (firstVoyage) {
  firstVoyage.status = 'Departed';
  firstVoyage.updatedBy = updatedBy;
  await firstVoyage.save();
}
```
followed by `invalidateRoundCache(roundId)` (capacity/voyage status is
read by the capacity engine, though status itself doesn't change onboard
math per Sprint 023's rules — cache invalidation is still the
established pattern whenever a Round/Voyage mutates). No
`TrackingHistory` entry is created (§5.3 Q12 — pure status-field change
only).

## 5.3 Decisions (locked in)

- **Q10 — Scope → DECIDED: only the first voyage** (lowest `sequence`,
  currently `Scheduled`), not every voyage in the round.
- **Q11 — Reversibility → DECIDED: not reversible.** If the Round is
  later transitioned `Active → Cancelled`, its now-`Departed` first
  voyage is left untouched — no revert logic, consistent with Voyage's
  own `STATUS_TRANSITIONS` map not allowing `Departed → Scheduled`
  anyway.
- **Q12 — TrackingHistory → DECIDED: no automatic entry.** This is a
  pure status-field change; no `TrackingHistory` record is fabricated
  without a real location/remarks input behind it.

# 6. POINT 6 — VOYAGES TAB: GROUPED-BY-ROUND LAYOUT

## 6.1 Current state, confirmed

`frontend/src/modules/voyages/VoyageList.jsx` renders ONE flat table (all
voyages system-wide, paginated 20/page via `voyagesService.list({ page,
limit: 20, status, serviceId })`) with a "Round" column showing each row's
own `v.roundId?.roundNumber`/`roundName` inline — sorted server-side by
`{ sequence: 1, etd: 1 }` (`voyage.service.js#list()`), NOT grouped or
sorted by Round at all. A voyage from Round A and a voyage from Round B
can appear as adjacent rows with no visual grouping.

This is a DIFFERENT page from `RoundVoyageList.jsx` (used inside a single
Round's own detail page, `/rounds/[id]`) — that component already shows
exactly one Round's voyages as an already-grouped table (since it's
scoped to one Round by definition). The ask here is to bring that same
"one Round, one table" visual pattern to the standalone, system-wide
`/voyages` tab, which today spans potentially many Rounds' voyages in a
single flat list.

## 6.2 Fix direction

Restructure `VoyageList.jsx` so the fetched voyages are grouped by
`roundId` client-side (or the backend list is re-sorted so a round's
voyages are always contiguous), and rendered as repeating sections:
```
[ Round Label: R000005 — "Q3 Red Sea Coffee Run" ]
  [ table of that round's voyages ]

      (gap)

[ Round Label: R000006 — "October Shuttle" ]
  [ table of that round's voyages ]
```
Each Round-label header would show `roundNumber`/`roundName` (and
optionally service/vessel/status, mirroring the header style already
used in `RoundVoyageList.jsx`'s parent Round Detail page for
consistency), with the existing per-row voyage table beneath it, keeping
every existing column (Voyage No, Service, POL, POD, ETD, ETA, ATD, ATA,
Status, Actions) — only the "Round" column itself is removed from the
per-row table, since it becomes redundant with the section's own label.

Backend `voyage.service.js#list()`'s sort needs to change from
`{ sequence: 1, etd: 1 }` to `{ roundId: 1, sequence: 1 }` so voyages
naturally arrive pre-grouped and contiguous (no round's voyages split up
by the current ETD-based ordering).

## 6.3 Decisions (locked in)

- **Q13 — Pagination unit → DECIDED: keep 20-voyages-per-page as-is.** A
  Round's group MAY occasionally split across a page boundary — accepted
  trade-off for keeping the existing pagination contract and the
  existing Service/Status filters working exactly as they do today at
  the individual-voyage level. No Round-based re-pagination.
- **Q14 — Empty rounds → DECIDED: hide entirely.** If a Service/Status
  filter leaves a Round with zero matching voyages on the current page,
  that Round's label section doesn't render at all.
