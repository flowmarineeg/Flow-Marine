# Sprint 042 — Delete Validation Business Rules (System-Wide)
Status: PLANNING — awaiting approval. NO CODE WAS WRITTEN OR MODIFIED,
NO SCHEMA WAS CHANGED, NO ENDPOINT WAS CREATED. This document REPLACES
the previous version of Sprint 042 in full — the prior draft drifted
into implementation detail (proposed schema changes, new endpoints,
phased rollout) that was out of scope. This version is strictly a
business-rule specification: for every module that participates in the
Round → Voyage → Booking → Invoice → Payment / Expense operational
chain, what parent/child relationships exist, when delete is currently
allowed, when it must be blocked, and what the user should be told.
Every claim below was confirmed by reading the actual model/service
file named — nothing is assumed from `claude.md`'s summary.

---

# 1. SPRINT GOAL

Guarantee data integrity across the entire logistics workflow by
defining — in business terms, not code — the validation every delete
operation in the system must perform before it is allowed to proceed.
No delete, on any module, should ever be able to create an orphan
record: a live document elsewhere in the system that still references
an entity the system has just made unreachable.

---

# 2. BUSINESS OBJECTIVE

Every module in the operational and financial chain must answer the
same question consistently before permitting a delete: **"does
anything still depend on this record?"** Today that question is asked
inconsistently — some modules check it thoroughly (Country → City →
Port → Terminal, and Booking's own delete), some check only one of
several real dependencies (Round, Voyage, Vessel, Agent, ContainerType),
and some ask a subtly wrong question (Service and Vessel both block
only on currently Planned/Active rounds, silently allowing deletion
even when Completed rounds carry real historical operational and
financial data). This sprint's objective is to document, module by
module, what the *correct* dependency check is — grounded in the real
foreign-key relationships that exist in the codebase today — so that a
future implementation sprint has an unambiguous, pre-agreed business
specification to build against.

---

# 3. CURRENT DELETE WORKFLOW ANALYSIS

Every deletable module in this system already follows one of three
existing patterns. This section documents which pattern each module
uses today, confirmed from source.

## 3.1 Pattern A — Soft delete with a dependency guard (the majority)
`isDeleted:true` + `deletedAt` set, after a guard clause checks one
specific downstream collection. Used by: Service, Vessel, Agent,
Round, Booking (Layer 2), ManualBooking (Layer 1), Invoice,
ContainerType, ExpenseType, Country, City, Port, Terminal. The guard's
*completeness* varies enormously module to module — this is the
central finding of this document (§5/§6).

## 3.2 Pattern B — Hard delete, partially guarded
Used by exactly one module in the confirmed operational chain: Voyage
(`voyage.service.js#deleteVoyage` — checks only Layer 2 Booking,
excluding Cancelled). Expense (`expense.service.js#hardDelete`) is also
hard-delete but carries **zero** dependency guard of any kind — see
§6.13; this is acceptable *only* because nothing in the system
references an Expense document's `_id` downstream (Expense is a leaf
node in the dependency graph, confirmed by grep — no other model has
an `expenseId` field).

## 3.3 Pattern C — No delete operation exists at all
**Route** has no delete endpoint. Routes are replaced wholesale via
`route.service.js#saveLegs` (`RouteLeg.deleteMany` + re-`insertMany`),
itself guarded against `Round.status IN ('Active','Completed')`
(`route.service.js` lines 38-52) — a **stricter** guard than Service's
own delete (Planned/Active only, Completed not blocked, §6.1). **Payment**
has no delete either — its terminal action is `voidPayment`
(`payment.service.js` lines 112-131), which is a real, working,
audited soft-cancellation (`isVoided`, `voidedAt`, `voidedBy`,
`voidReason`, triggers `recalcInvoiceStatus`) — functionally
equivalent to a delete guard, already correctly implemented, and not a
gap this sprint needs to close.

## 3.4 Two modules with no delete lifecycle at all
**Agent Financial Account** and **Reports** are not stored, deletable
entities — confirmed by grep, no `FinancialAccount` model exists
anywhere in the codebase. Both are computed, read-only views over
`Invoice`/`Payment`/`Booking`/`ManualBooking` at request time. Neither
has, or needs, a delete validation rule of its own — they are
*consumers* of the delete rules defined elsewhere in this document,
not subjects of one.

# 4. SYSTEM DELETE DEPENDENCY GRAPH

Confirmed directly from each model/service file (`ref:`, required vs.
nullable, and every guard clause read for this analysis):

```
Country ──◄── City ──◄── Port ──◄── Terminal
                          Port  ──◄── RouteLeg.portId

                    (Port/Terminal do NOT check Voyage.polId/podId or
                     Booking.polId/podId — see Finding F1, §6.16)

Route   ──◄── RouteLeg.routeId
RouteLeg.agentId ──► Agent (nullable; NOT checked before Agent delete — Finding F2, §6.5)

Vessel ──◄── Round.vesselId (required)
Vessel ──◄── TrackingHistory.vesselId (required)

Round ──◄── Voyage.roundId (required)         [authoritative FK]
Round ── voyageIds[] ──► Voyage               [denormalized cache of the above]
Round ──◄── Expense.roundId (nullable, XOR w/ voyageId)
Round ──◄── Invoice.roundId (nullable, required when invoiceType='Round')
Round ──◄── TrackingHistory.roundId (required)

Voyage ──◄── Booking.voyageId (required)            [Layer 2]
Voyage ──◄── ManualBooking.voyageId (required)      [Layer 1]
Voyage ──◄── Expense.voyageId (nullable, XOR w/ roundId)
Voyage ──◄── Invoice.voyageId (nullable, required when invoiceType='Voyage')
Voyage ──◄── TrackingHistory.voyageId (required)

Agent ──◄── Booking.agentId (required)              [Layer 2]
Agent ──◄── ManualBooking.agentId (required)        [Layer 1]
Agent ──◄── Invoice.agentId (required, ALWAYS)
Agent ──◄── Expense.agentId (nullable)
Agent ──◄── RouteLeg.agentId (nullable)

ContainerType ──◄── Booking.containerTypeId (required)          [Layer 2]
ContainerType ──◄── ManualBooking.cargoRows[].containerTypeId    [Layer 1]

Booking ──◄── Invoice.lineItems[].bookingId (ref:'Booking' ONLY —
              ManualBooking is never invoiced, confirmed from
              invoice.model.js's lineItemSchema)

Invoice ──◄── Payment.invoiceId (required)

ExpenseType ──◄── Expense.expenseTypeId (required)
ExpenseCategory ──◄── ExpenseType.category (string match, not a live ref)

Payment — leaf node once created (never deleted, only voided).
Reports / Agent Financial Account — pure read consumers, not part of the
  delete graph at all (§3.4).
```

**Reading the graph:** an arrow `◄──` into a module is a live
dependency that a correct delete guard for that module must check.
Every module's *actual* current guard (§6) checks fewer arrows than
the ones pointing into it — in every single case, without exception.

# 6. MODULE-BY-MODULE DELETE RULES

## 6.1 Service
- **Parent modules:** none (top of the operational hierarchy).
- **Child modules:** Route (1:1), Round (many).
- **Referenced by:** `Round.serviceId` (required), `Voyage.serviceId`
  (required, denormalized from Round), `TrackingHistory.serviceId`
  (required), `RouteLeg.agentId` is scoped through Route, not Service
  directly.
- **References:** nothing (a Service is a top-level definition).
- **Delete allowed when:** no Round referencing this service is
  currently `Planned` or `Active` (existing rule, `service.service.js`
  lines 98-104).
- **Delete must be blocked when (business gap — not enforced today):**
  any Round referencing this service — including `Completed` ones —
  exists at all, since a Completed round still carries real historical
  Voyage/Booking/Invoice/Expense/TrackingHistory data that a Service
  deletion would orphan from its own parent definition; OR when a
  `Route` still exists for this service (a Service with route legs
  defined represents configured, usable sailing geography, not an
  empty draft).
- **Business validation that should happen:** check for ANY Round
  (any status) referencing the service, not only Planned/Active; check
  whether a Route exists for the service.
- **User-facing message today:** `Cannot delete — service is used by
  round {roundNumber}` (existing, shown only for Planned/Active rounds).

## 6.2 Route (and RouteLeg)
- **Parent module:** Service (1:1).
- **Child modules:** RouteLeg (many, wholesale-owned).
- **Referenced by:** nothing directly — Route itself is never
  `ref`'d by any other model; only its child `RouteLeg.agentId`
  references `Agent`.
- **References:** Service (`serviceId`).
- **No delete operation exists for Route at all** — it can only be
  wholesale-replaced via editing the route's leg list, which itself
  is blocked whenever any Round on the service is `Active` or
  `Completed` (`route.service.js` lines 38-52). This is a different
  mechanism from "delete," but serves the same data-integrity purpose:
  a route with operational history cannot be silently rewritten.
- **Business validation that should happen:** none beyond the existing
  edit-guard — there is no independent Route delete concept to define.

## 6.3 Vessel
- **Parent modules:** none.
- **Child modules:** none (Vessel Particulars are fields on the Vessel
  document itself, not a child collection).
- **Referenced by:** `Round.vesselId` (required), `TrackingHistory.
  vesselId` (required).
- **References:** nothing.
- **Delete allowed when:** no Round referencing this vessel is
  currently `Planned` or `Active` (existing rule, `vessel.service.js`
  lines 79-81).
- **Delete must be blocked when (business gap):** any Round —
  including `Completed` — references this vessel, since a Completed
  round's Voyages/Bookings/Invoices/Expenses/TrackingHistory all trace
  back to this vessel for reporting purposes (Vessel Details KPIs,
  Voyage Performance, Round P&L); or when `TrackingHistory` references
  this vessel directly.
- **Business validation that should happen:** check for ANY Round
  (any status), not only Planned/Active; check TrackingHistory.
- **User-facing message today:** `Cannot delete — vessel is assigned
  to active round {roundNumber}` (existing, Planned/Active only).

## 6.4 Round
(Full detail already covered by this system's dependency analysis;
summarized here for completeness of the module-by-module format.)
- **Parent module:** Service, Vessel.
- **Child modules:** Voyage (via `voyageIds[]`, denormalized cache of
  the authoritative `Voyage.roundId`).
- **Referenced by:** Voyage (required), Expense (nullable), Invoice
  (nullable, `invoiceType='Round'`), TrackingHistory (required).
- **References:** Service, Vessel.
- **Delete allowed when:** the round's status is `Planned` or
  `Cancelled` (no lifecycle check exists today at all — see gap
  below), AND no voyage in the round carries a non-Cancelled Booking
  (existing check, though today it blocks on ANY status including
  Cancelled — stricter than necessary and inconsistent with Voyage's
  own rule, see §8.2).
- **Delete must be blocked when (business gaps):** any voyage in the
  round has a non-Cancelled `ManualBooking` (Layer 1 — entirely
  unchecked today); any non-cancelled `Invoice` references the round
  directly or any of its voyages; any `Expense` references the round
  or any of its voyages; any `TrackingHistory` entry references the
  round; the round's own status is `Active` or `Completed`.
- **Business validation that should happen:** the five checks above,
  plus a decision (business, not technical) on what happens to the
  round's own Voyage documents — they are not currently touched, or
  even inspected, when a Round is deleted (§8.1, the single most
  important open question in this document).
- **User-facing message today:** `Cannot delete — one or more voyages
  have bookings` (existing, Layer 2 + any status only).

## 6.5 Voyage
- **Parent module:** Round.
- **Child modules:** none.
- **Referenced by:** Booking (required), ManualBooking (required),
  Expense (nullable), Invoice (nullable, `invoiceType='Voyage'`),
  TrackingHistory (required).
- **References:** Round, Service, Port (POL/POD).
- **Delete allowed when:** status is `Scheduled` or `Cancelled` (no
  status check exists today), AND no non-Cancelled Booking references
  it (existing check).
- **Delete must be blocked when (business gaps):** any non-Cancelled
  `ManualBooking` references it; any non-cancelled `Invoice` references
  it directly (`invoiceType='Voyage'`) OR through the line items of any
  of its bookings (including a booking that is itself Cancelled but was
  invoiced before cancellation — the current Booking-check's Cancelled
  exclusion does not close this specific case, §8.3); any `Expense`
  references it; any `TrackingHistory` entry references it; status is
  `Departed`/`In Transit`/`Arrived`/`Completed`.
- **Business validation that should happen:** the five checks above.
  Voyage is currently the only module in the confirmed operational
  chain that performs a hard delete rather than a soft one — this
  document does not propose changing that (out of scope, per this
  sprint's explicit instruction), but flags that a hard delete makes
  every one of these checks strictly higher-stakes than the equivalent
  check on any other (soft-deleted) module, since there is no
  after-the-fact recovery if a check is ever wrong or incomplete.
- **User-facing message today:** `Cannot delete — voyage has active
  bookings. Cancel the bookings first.` (existing, Layer 2 non-
  Cancelled only).

## 6.6 Agent
- **Parent modules:** none.
- **Child modules:** none.
- **Referenced by:** Booking (required), ManualBooking (required),
  Invoice (required, always), Expense (nullable), RouteLeg (nullable).
- **References:** nothing.
- **Delete allowed when:** no Layer 2 Booking with status `Pending` or
  `Confirmed` references this agent (existing rule, `agent.service.js`
  lines 77-79).
- **Delete must be blocked when (business gaps — the widest gap of any
  single module in this system):** any Layer 2 Booking in `Final
  Loading` status also references this agent (currently NOT blocked —
  Final Loading is the most operationally "real" status of all, and is
  excluded from today's check entirely, an inversion of intent); any
  non-Cancelled `ManualBooking` references this agent (entirely
  unchecked); ANY `Invoice` references this agent — `agentId` is a
  required field on every Invoice, so an agent with invoicing history
  of any kind should never be deletable while that history exists; any
  `Expense` references this agent; any `RouteLeg` currently assigns
  this agent to a port call.
- **Business validation that should happen:** all five checks above,
  replacing today's single, narrowly-scoped one.
- **User-facing message today:** `Cannot delete — agent has active
  bookings` (existing, but factually incomplete relative to what it
  actually checks).

## 6.7 Booking (Layer 2)
- **Parent module:** Voyage.
- **Child modules:** none.
- **Referenced by:** Invoice (`lineItems[].bookingId`).
- **References:** Voyage, Agent, Port (POL/POD), ContainerType.
- **Delete allowed when:** no non-cancelled Invoice's line items
  reference this booking (existing check, `booking.service.js` lines
  207-213).
- **Delete must be blocked when:** a non-cancelled Invoice references
  it via `lineItems.bookingId` — already correctly implemented.
- **Business validation that should happen:** none — **this is the
  one delete guard in the entire system that is already complete
  relative to its real dependency graph**, and is the reference pattern
  every other module's Invoice-check in this document is modeled on.
- **User-facing message today:** `Cannot delete — a non-cancelled
  invoice references this booking` (existing, accurate).

## 6.8 ManualBooking (Layer 1)
- **Parent module:** Voyage.
- **Child modules:** none.
- **Referenced by:** nothing — confirmed `Invoice.lineItemSchema.
  bookingId` refs `'Booking'` only, never `'ManualBooking'`. Layer 1
  reservations are never invoiced directly in this system's current
  architecture.
- **References:** Voyage, Agent, Port (POL/POD), ContainerType (via
  `cargoRows[]`).
- **Delete allowed when:** always — no downstream dependency exists to
  check.
- **Delete must be blocked when:** never, under the current
  architecture.
- **Business validation that should happen:** none — correctly scoped
  already, precisely because Layer 1 has no downstream financial
  relationship. (If a future sprint ever allows ManualBooking to be
  invoiced directly, this module's delete rule would need to gain the
  same check Booking already has — noted here only as a future
  contingency, not a current gap.)
- **User-facing message today:** none needed (no block condition
  exists).

## 6.9 ContainerType
- **Parent modules:** none.
- **Child modules:** none.
- **Referenced by:** Booking (required, Layer 2), ManualBooking
  (`cargoRows[].containerTypeId`, Layer 1).
- **References:** nothing.
- **Delete allowed when:** no Layer 2 Booking references this
  container type (existing check, `containerType.service.js` lines
  53-55).
- **Delete must be blocked when (business gap):** any Layer 1
  `ManualBooking` cargo row also references this container type —
  currently unchecked, the same "Layer 2 only" gap pattern seen across
  Round/Voyage/Agent.
- **Business validation that should happen:** extend the existing
  check to also query `ManualBooking.cargoRows.containerTypeId`.
- **User-facing message today:** `Cannot delete — container type is
  used in existing bookings` (existing; the word "bookings" already
  reads as if it should mean both layers, but the query behind it only
  covers one).

## 6.10 Country / City / Port / Terminal (Location hierarchy)
- **Parent/child chain:** Country → City → Port → Terminal, each
  strictly one level deep.
- **Referenced by:** each level's own child count (existing, correct,
  cascading guards — `location.service.js` lines 62-73, 122-133,
  203-217, 266-277); Port and Terminal additionally check `RouteLeg`
  references via `countRouteLegsReferencing`.
- **Delete allowed when:** no child-level location record references
  it, AND (Port/Terminal only) no RouteLeg references it (existing,
  correct).
- **Delete must be blocked when (business gap — Finding F1):** a live
  `Voyage.polId`/`podId` or `Booking`/`ManualBooking`
  `polId`/`podId` references this Port directly. Because `RouteLeg`
  documents are wholesale-replaced whenever a route is edited
  (`saveLegs`'s `deleteMany`+`insertMany`, §6.2), a port can have
  **zero** current `RouteLeg` references while still being actively
  used by live Voyages/Bookings created under a now-superseded route
  version — the existing RouteLeg-only check does not catch this.
- **Business validation that should happen:** add a check for live
  `Voyage`/`Booking`/`ManualBooking` documents referencing the port
  directly, alongside the existing RouteLeg check.
- **User-facing messages today:** `Cannot delete — {n} cit{y/ies}
  reference this country`, `... port(s) reference this city`, `...
  terminal(s) reference this port`, `... route leg(s) reference this
  port/terminal` (all existing, all accurate for what they check).

## 6.11 Invoice
- **Parent modules:** Agent, Round or Voyage (depending on
  `invoiceType`), Booking (via `lineItems`).
- **Child modules:** Payment.
- **Referenced by:** `Payment.invoiceId` (required).
- **References:** Agent, Round/Voyage, Booking (snapshot line items).
- **Delete allowed when:** `paidAmount` is 0 (existing check,
  `invoice.service.js` line 270) — this is a derived proxy for "no
  non-voided Payment exists," since `paidAmount` is recalculated as
  `sum(non-voided Payment.amount)` after every payment create/void.
- **Delete must be blocked when:** `paidAmount > 0` — already correct
  in effect.
- **Business nuance worth documenting (not a gap, an edge case):** an
  Invoice can have `paidAmount = 0` while still having one or more
  fully-`voided` Payment documents referencing it — those Payment
  records are not blocking today (correctly, since a voided payment
  represents money that was never actually, finally received), but
  they do still exist and still reference this Invoice's `_id`; a
  deleted Invoice makes those historical Payment records harder to
  contextualize on read (their `invoiceId` will resolve to a hidden
  document). This is noted as a documented edge case (§8.4), not a
  block condition — voided payments are, by design, not live financial
  obligations.
- **User-facing message today:** `Invoices with recorded payments
  cannot be deleted` (existing, accurate).

## 6.12 Payment
- **Parent module:** Invoice.
- **Child modules:** none.
- **Referenced by:** nothing.
- **References:** Invoice, and (via `allocations[]`) Booking.
- **No delete operation exists.** The terminal action is `voidPayment`
  (`payment.service.js` lines 112-131) — sets `isVoided`, `voidedAt`,
  `voidedBy`, `voidReason`, and recalculates the parent Invoice's
  status/`paidAmount` inside a transaction. This already fulfills the
  same data-integrity purpose a delete-guard exists for elsewhere in
  this document, and needs no further business rule defined.

## 6.13 Expense
- **Parent module:** Round OR Voyage (XOR), optionally Port, optionally
  Agent.
- **Child modules:** none.
- **Referenced by:** nothing — confirmed leaf node; no other model in
  the codebase carries an `expenseId` field.
- **References:** Round/Voyage, Port, Agent, ExpenseType.
- **Delete allowed when:** always — there is no downstream dependency
  to check, by construction.
- **Delete must be blocked when:** never, from a pure referential-
  integrity standpoint — no other record can ever become an orphan as
  a result of an Expense being removed.
- **Business validation that should happen:** none required for
  referential integrity. (This document does not weigh in on whether
  Expense's hard-delete/no-audit-trail behavior is otherwise desirable
  — that is a separate, already-documented question in
  `docs/expense-module-analysis.md` Risk 1, and explicitly out of this
  sprint's scope, which is limited to dependency validation, not
  lifecycle/audit design.)

## 6.14 ExpenseType
- **Parent modules:** none.
- **Child modules:** none.
- **Referenced by:** `Expense.expenseTypeId` (required).
- **References:** ExpenseCategory (by name string).
- **Delete allowed when:** no Expense references this type (existing
  check, `expenseType.service.js` lines 139-141).
- **Delete must be blocked when:** any Expense references it —
  already correct.
- **User-facing message today:** `Cannot delete — expense type is used
  in existing expenses` (existing, accurate).

## 6.15 ExpenseCategory
- **Parent modules:** none.
- **Child modules:** none.
- **Referenced by:** `ExpenseType.category`, a case-insensitive string
  match — not a live ObjectId reference.
- **Delete allowed when:** no non-deleted ExpenseType uses this
  category name (existing check, `expenseType.service.js` lines 89-95).
- **Delete must be blocked when:** any ExpenseType uses the category —
  already correct. (Worth noting only as a minor architectural
  inconsistency, not a gap: this is the one deletable module in the
  entire operational chain implemented as a genuine hard delete
  alongside Voyage and Expense — acceptable here given how low-stakes
  a category name is, but named for completeness since the brief asks
  for every module's current mechanism to be documented.)
- **User-facing message today:** `Cannot delete — category is used by
  expense type "{name}"` (existing, accurate).

## 6.16 Agent Financial Account and Reports
Neither is a stored, deletable entity (§3.4) — both are computed views
over Invoice/Payment/Booking/ManualBooking at request time. Deleting
any upstream module correctly and safely (per the rules defined in
this document) is what keeps these views accurate; they carry no
delete rule of their own to define.

# 7. VALIDATION MESSAGES

Every message below is either the exact existing string (confirmed
from source) or a proposed new message for a currently unchecked
dependency, written in the same voice and format as the existing ones
(Cannot delete, dash, reason). No new error-handling mechanism is
implied; this system already has one convention and every message
below follows it.

| Module | Condition | Message |
|---|---|---|
| Service | Round (any status) references it | Cannot delete, service is used by round {roundNumber}. (existing message, scope widened) |
| Service | Route exists for this service | Cannot delete, this service has a defined route. (new) |
| Vessel | Round (any status) references it | Cannot delete, vessel is assigned to round {roundNumber}. (existing message, scope widened) |
| Vessel | TrackingHistory references it | Cannot delete, vessel has tracking history recorded. (new) |
| Agent | Final Loading booking (L2) references it | Cannot delete, agent has bookings in Final Loading status. (new) |
| Agent | ManualBooking (L1) references it | Cannot delete, agent has active manual bookings. (new) |
| Agent | Invoice references it | Cannot delete, agent has existing invoices. (new) |
| Agent | Expense references it | Cannot delete, agent has recorded expenses. (new) |
| Agent | RouteLeg references it | Cannot delete, agent is assigned to a route leg. (new) |
| Round | ManualBooking (L1), non-Cancelled | Cannot delete, one or more voyages have active manual bookings. (new) |
| Round | Invoice references it (direct or via a voyage) | Cannot delete, this round (or one of its voyages) has an existing invoice. (new) |
| Round | Expense references it (direct or via a voyage) | Cannot delete, this round (or one of its voyages) has recorded expenses. (new) |
| Round | TrackingHistory references it | Cannot delete, this round has tracking history recorded. (new) |
| Round | status is Active or Completed | Cannot delete, round is {status}. Only Planned or Cancelled rounds can be deleted. (new) |
| Voyage | ManualBooking (L1), non-Cancelled | Cannot delete, voyage has active manual bookings. Cancel them first. (new) |
| Voyage | Invoice references it (direct or via a booking line item) | Cannot delete, voyage has an existing invoice referencing it. (new) |
| Voyage | Expense references it | Cannot delete, voyage has recorded expenses. (new) |
| Voyage | TrackingHistory references it | Cannot delete, voyage has tracking history recorded. (new) |
| Voyage | status is Departed, In Transit, Arrived, or Completed | Cannot delete, voyage is {status}. Only Scheduled or Cancelled voyages can be deleted. (new) |
| ContainerType | ManualBooking cargo row references it | Cannot delete, container type is used in existing manual bookings. (new) |
| Port/Terminal | live Voyage/Booking references it | Cannot delete, port is referenced by an existing voyage or booking. (new) |

All other messages already exist and are already accurate for what
their current guard checks (Booking, ManualBooking, Invoice, Payment
void, ExpenseType, ExpenseCategory, Country/City/Port/Terminal
existing child-count checks) — listed in section 6, not repeated here.

# 8. EDGE CASES

1. Round delete and its own Voyages. If every gap in section 6.4 is
   closed, a Round becomes deletable only once every voyage inside it
   independently has no live dependency of its own, at which point
   those voyage documents themselves are, by definition, also eligible
   for deletion under section 6.5 rules. This document deliberately
   does not resolve whether Round delete should require its voyages to
   already be individually removed first, or should treat voyages with
   no remaining dependencies as implicitly fine to leave in place. That
   is a business decision for the eventual implementation conversation,
   not a technical detail, flagged here as the single most consequential
   open question in this document.
2. Round booking check today blocks on Cancelled bookings too
   (Booking.exists with no status filter, round.service.js line 219)
   while Voyage equivalent check excludes Cancelled (voyage.service.js
   line 213). These are two different answers to the same business
   question (does a Cancelled booking still count as a live dependency)
   sitting one module apart in the same dependency chain, worth
   reconciling to one rule, not two.
3. A booking that was Final Loading, invoiced, and later Cancelled (the
   Sprint 033 orphaned line item scenario) is excluded from the Voyage
   booking check by virtue of being Cancelled, yet a live, non-cancelled
   Invoice may still reference it through that booking line item.
   Booking own delete guard (section 6.7) already closes this exact
   case correctly for deleting the booking itself; the Voyage guard
   needs the equivalent line-item-aware check to close it for deleting
   the voyage the booking sits on.
4. A fully voided Payment referencing a since-deleted Invoice (section
   6.11) is not a blocking condition under any rule in this document,
   since voided payments represent money that was never finally
   received, but is worth naming so a future reviewer does not mistake
   the absence of a check here for an oversight; it is a deliberate
   non-block, consistent with how voided payments are treated
   everywhere else in the system.
5. A Port with zero current RouteLeg references but live historical
   Voyage/Booking data (section 6.10, Finding F1). Because route legs
   are wholesale-replaced on every route edit, a port used by an
   earlier version of a route can be deleted today with no warning,
   even though real Voyages/Bookings created under that earlier route
   version still reference it directly.
6. Agent deletion and RouteLeg assignment. An Agent assigned to a route
   leg (used for that leg local operations) is not currently checked at
   all before Agent deletion; deleting such an agent leaves the RouteLeg
   agentId pointing at a hidden Agent document with no warning at any
   point in the Agent delete flow.
7. Service deletion and Completed rounds. A Service can be deleted
   today even when it has extensive Completed-round history (real
   revenue, real expenses, real invoices) precisely because the
   existing guard only asks about Planned/Active rounds, mirrored by
   the identical gap on Vessel (section 6.3). Both are the same
   underlying business question asked incompletely in two places.

# 9. RISKS

- Every gap documented in sections 5 and 6 is a gap that exists in the
  system today, right now. This document does not introduce new risk
  by identifying them; it makes visible risk that already exists
  silently. The risk of not acting on this document is that each gap
  remains exploitable (by ordinary user action, not misuse) for as long
  as implementation is deferred.
- Voyage hard-delete nature (section 6.5) makes its gaps the highest
  severity in this document. Every other module soft-delete at least
  leaves the underlying document theoretically recoverable; Voyage
  does not, regardless of what this document ultimately decides about
  its checks.
- The Agent gap (section 6.6) is the widest single-module gap found.
  Agent is referenced by five different downstream modules and today
  guard checks only one of them, and only partially (excludes the most
  operationally significant booking status, Final Loading).
- Reconciling the Cancelled-booking inconsistency (section 8.2) changes
  existing, currently shipped behavior for Round. Any future
  implementation of this document rules needs sign-off that loosening
  Round current (stricter, if accidental) Cancelled-booking check is an
  intended change, not a side effect.
- This document does not size implementation effort, migration risk, or
  rollout sequencing. Per the explicit scope of this sprint, that
  belongs to a separate, later planning conversation once these
  business rules are approved.
