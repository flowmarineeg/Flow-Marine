# 0. WHAT I VERIFIED IN THE CURRENT CODE (and how it changes the proposal)
---------------------------------------------------------------------------

F1. MongoDB is Atlas (mongodb+srv) AND invoice.service.js / payment.service.js
    already use session.withTransaction() in production code. => The proposal's
    open item "confirm replica set" is RESOLVED. Transactions are available.
    (Local dev with mongodb://localhost needs a single-node replica set —
    docker-compose has no Mongo service, so dev uses Atlas too.)

F2. Tracking is VOYAGE-level, not container-level. TrackingHistory =
    {voyageId, roundId, vesselId, portId, status, remarks, lastUpdate}, append-
    only. There is NO container_tracking collection, no move type, no
    "confirmed" flag. The proposal's handling-fee automation ("when container
    moves are confirmed in Tracking") assumes a collection that does not exist.
    What DOES exist per container: Booking.containerNumber, containerStatus
    (Full|Empty), status 'Final Loading' (= loaded), dischargeStatus
    'Discharged' (Sprint 045 = discharged), polId/podId, voyageId.
    => Proposal "Tracking: move type" change is re-scoped (see Decision D3).

F3. Two booking kinds, with a very different job today:
    - Booking (Layer 2): ONE container per document, containerNumber,
      freightRate, totalFreight, status Pending→Confirmed→Final Loading,
      dischargeStatus. ONLY this layer is invoiceable (Final Loading only,
      Sprint 033). Created by manual form + Excel import (Booking / Final
      Loading / Discharge).
    - ManualBooking (Layer 1): header + cargoRows[] (containerTypeId, quantity,
      rate, rowTotal), NO container numbers. A commercial reservation / capacity
      planning layer. Never invoiced.
    This is almost exactly the proposal's "booked qty vs loaded qty":
      booked  ≈ ManualBooking.cargoRows[].quantity
      loaded  ≈ count of Layer 2 Final Loading bookings (same agent+voyage+type)
    but there is NO link between the two layers today.

F4. Invoice is already: header + lineItems[] snapshot, type Booking|Voyage|Round,
    one-sided ownership (Invoice.lineItems.bookingId, multikey index),
    transactional claim-check in create(), Draft→Issued flow, cancel allowed,
    hard delete blocked only when paidAmount>0, Bill-To block, PDF. So the
    proposal's "one invoice per item, enforced in the DB" is an EVOLUTION of
    Sprint 033, not greenfield: today the guard is an app-level exists() inside
    a transaction, not a partial unique index.

F5. Payment (Sprint 033) = per-invoice, explicit allocations[{bookingId,amount}],
    void-whole-only, recalcInvoiceStatus(). Proposal replaces it with
    "settlements" (cash into company bank / partner bank / offset vs agent SOA).
    Money fields everywhere are plain JS Number (float). No Decimal128.

F6. Expense today: roundId|voyageId|portId scope (inferred, Sprint 036),
    agentId optional, amount+currency, attachment. NO estimate/final (PDA/FDA),
    NO paidBy, NO ledger link. Hire Rate is a normal Expense (Sprint 035).

F7. Agent today = master record + contacts. Agent is already BOTH the invoice
    counterparty (Invoice.agentId) and an expense counterparty
    (Expense.agentId) — so the "agent is both debtor and creditor" problem the
    proposal describes is real and the two FKs already exist to build it on.

F8. Vessel has ownershipType/ownerName (free text), NO partners/shares.
    Round has status Planned|Active|Completed|Cancelled and NO close/lock/
    settlement concept. Round.hardDelete guards exist (Sprint 047).

F9. Permissions = {roleId, module, actions{create,read,update,delete,import,
    export,view,hidden,override}} — boolean flags per MODULE, not dotted names.
    The proposal's 13 permissions ("invoice.issue", "round.close", ...) do not
    fit this shape as written. PermissionMatrix.jsx has a hardcoded ACTIONS
    array AND still has no toggles for import/export (known gap, CLAUDE §1).

F10. Audit log is fire-and-forget via res.on('finish') + setImmediate, success-
     only, no before/after snapshot. Proposal wants failed money actions logged
     and before/after/reason => changes a "never change" rule in CLAUDE.md §17
     (fire-and-forget pattern) — needs your explicit OK (Decision D9).

F11. Security items in proposal §4 (C1 CSRF etc.): cookie is sameSite:'none' in
     production and there is NO csrf middleware anywhere in src/ => C1 is
     plausible/true. H7 CONFIRMED: .gitignore ignores /docs/*, /sprints,

     repo (only system-audit-2026-8-4.md exists on disk; 2026-9-1 is a staged

# 1. DECISIONS — OPEN QUESTIONS, ANSWERED FROM THE CURRENT SYSTEM
---------------------------------------------------------------------------
Each ❓ lists options based on what exists today. (R) = my recommendation.

## D1 ❓ Which bookings get Booking Items + invoicing? (proposal §9.4)
 A (R) Layer 2 Booking is the invoiceable truth; ManualBooking stays a planning
   layer. A "Booking Item" = a pricing group of Layer 2 Final Loading bookings
   (Agent + Voyage + ContainerType + FreightRate — same grouping idea as
   Sprint 034 Booking Revenue Details). loadedQty = count of those bookings,
   price = their shared freightRate, billed amount = loadedQty × price.
   bookedQty is OPTIONAL, filled from a matching ManualBooking cargo row when
   one exists (soft link by agent+voyage+type, informational only).
   + zero change to import, capacity, Final Loading flow; matches the
     existing invoice eligibility rule; smallest migration.
   − items are derived, not hand-authored, so "booked vs loaded variance" is
     only shown where a ManualBooking exists.
 B Booking Items live on ManualBooking.cargoRows (booked qty); Final Loading
   import fills loadedQty by matching (agent, voyage, type).
   + true booked-vs-loaded per line.  − invoices would stop being per-container;
     rewrites Sprint 033/044/047 invoice+PDF+Agent-account logic; import must
     now resolve a ManualBooking row (ambiguity when 2 rows share a type).
 C Both layers get items, linked by a new ManualBooking→Booking reference.
   + most complete.  − biggest change; touches capacity-adjacent code paths
     that are explicitly "do not touch".
 → Recommend A.

## D2 ❓ Prepaid/Collect terms and multi-leg voyages (proposal §9.3)
 Multi-leg: ALREADY SATISFIED. A Round is the multi-leg container; each Voyage
   is one leg (Sprint 023); manual shortcut voyages exist (Sprint 016);
   Expense already carries voyageId+portId+agentId (agent per port). No work.
 Prepaid/Collect, three options:
 A (R) Informational only: add Booking.paymentTerm ('Prepaid'|'Collect'|null)
   + optional collectAgentId; shown on lists/PDF, NO accounting trigger.
 B Defer to a later version (not in V2).
 C Full: Collect bookings invoice on arrival/discharge trigger (uses
   dischargeStatus). Needs a posting-trigger design + your rules.
 → Recommend A (cheap, reversible, loses nothing). Ask me if you want C.

## D3 ❓ Handling-fee automation without container-level Tracking (F2)
 A (R) Drive it from data that exists: Layer 2 Final Loading booking ⇒ a "load"
   move (containerStatus Full/Empty), dischargeStatus='Discharged' ⇒ a
   "discharge" move. A "Generate handling charges" action per Round/Agent
   (preview → confirm) creates AgentHandlingCharge rows from the agent's
   agreement fee table. Idempotent per (bookingId, moveType). No change to
   TrackingHistory (stays append-only, voyage-level).
 B Build a new per-container movement collection + confirm screen (what the
   spec literally describes). Duplicates what Final Loading/Discharge import
   already record; extra manual data entry for ops.
 C Defer automation; handling fees entered by hand as Expenses at first.
 → Recommend A. "Confirmed" = the booking import already confirms it.

## D4 ❓ Fate of the existing Payment model (proposal §5 "replaced")
 A (R) Keep the Payment collection READ-ONLY as legacy history; migration
   (Sprint 054) creates matching settlement + ledger records for V2 Rounds;
   new payments only go through settlements.
 B Keep Payment writable and bolt ledger posting onto it (two payment models
   forever).
 C Delete Payment after migration (loses Sprint 033 void audit trail).
 → Recommend A.

## D5 ❓ Money representation
 A (R) NEW collections store integer minor units (amountMinor, Number/int),

 B Decimal128 everywhere new. Exact, but Decimal128 serialises awkwardly in
   JSON/axios/Chart.js and needs conversion at every API edge.
 → Recommend A. The "to the cent" settlement tests need exact arithmetic.
