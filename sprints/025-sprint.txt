================================================================================
  FINDING B — CAPACITY DOES NOT REFLECT LAYER 2 BOOKINGS: EXACT ROOT CAUSE
================================================================================

Manual test result:
  3 bookings created: 20ft (1 TEU) + 40ft (2 TEU) + 40ft (2 TEU)
  Expected onboardTEU: 5
  Actual onboardTEU on capacity page: 0

The following is a complete code trace of exactly why this happens.

────────────────────────────────────────────────────────────────────────────────
B1 — The capacity engine queries L2 by STATUS, not by Pending
────────────────────────────────────────────────────────────────────────────────

File: backend/src/modules/capacity/capacity.service.js
Lines (the L2 query in computeRoundCapacity):

  const L2_STATUSES = ['Confirmed', 'Final Loading'];

  Booking.find({
    voyageId:  { $in: voyageIds },
    isDeleted: false,
    status:    { $in: l2Statuses },   ← l2Statuses = ['Confirmed', 'Final Loading']
  })

The capacity engine ONLY counts Layer 2 bookings with status = Confirmed or
Final Loading.

File: backend/src/modules/bookings/bookingImport.service.js
Lines (saveImport, insert block):
  status: 'Pending',  ← ALL newly imported bookings start as Pending

File: backend/src/modules/bookings/booking.service.js
Lines (create function):
  status: data.status === 'Cancelled' ? 'Pending' : (data.status || 'Pending'),
  ← ALL manually created bookings start as Pending (unless explicitly set otherwise)

CONCLUSION:
  Every new Layer 2 booking starts with status = 'Pending'.
  The capacity engine ignores Pending bookings.
  Therefore: capacity shows 0 TEU for all newly created bookings.

This is the sole and complete root cause of the manual test failure.

────────────────────────────────────────────────────────────────────────────────
B2 — Contrast with Layer 1 behavior (which DID work)
────────────────────────────────────────────────────────────────────────────────

File: backend/src/modules/capacity/capacity.service.js
Lines:
  const L1_STATUSES = ['Pending', 'Confirmed', 'Final Loading'];

Layer 1 (ManualBooking) counts ALL statuses including Pending. This is
intentional: "capacity is a commercial planning indicator" (Sprint 023 spec).

Layer 2 was intentionally designed to only count Confirmed + Final Loading
because operational bookings were considered "committed" only once confirmed.

────────────────────────────────────────────────────────────────────────────────
B3 — The business decision that must be made
────────────────────────────────────────────────────────────────────────────────

There are exactly two options:

  OPTION A — Include Pending in L2_STATUSES:
    Change L2_STATUSES = ['Pending', 'Confirmed', 'Final Loading']
    Effect: Every new booking (Pending) immediately contributes to capacity.
    This matches how Layer 1 behaves.
    Risk: Very low. One constant change.

  OPTION B — Keep L2 at Confirmed + Final Loading only:
    L2_STATUSES stays as-is.
    Effect: Users must manually change booking status to Confirmed for capacity
    to reflect it. This requires a workflow change.
    Risk: Zero code change; but the test scenario (Pending bookings showing 0
    TEU) would remain the expected behavior by design.

The manual test described 3 bookings that were NEWLY CREATED and never
confirmed. If the intent is for all Layer 2 bookings to count toward capacity
immediately (same rule as Layer 1), then OPTION A is the correct fix.

If the intent is that Layer 2 only counts committed cargo (Confirmed +
Final Loading), then the behavior is already correct and the capacity page
showing 0 for Pending is the expected result — the manual test expectation
was wrong.

This requires a product decision from you before implementation.

────────────────────────────────────────────────────────────────────────────────

Assuming the status filter is resolved, the rest of the flow is correct:

    const { teu, matched } = resolveTEU(b.containerTypeId.size);

    ← b.quantity = 1 for manual form bookings (schema default)

────────────────────────────────────────────────────────────────────────────────
B5 — Additional note: capacity.service.js quantity reference is still needed
────────────────────────────────────────────────────────────────────────────────

capacity.service.js line:
  const effectiveTEU = b.quantity * teu;

After Sprint 024, booking.model.js removed quantity from the schema
(confirmed by reading booking.model.js — quantity field is gone from the
current model). However:

  bookingImport.service.js still stores quantity in insert and bulkWrite.
  booking.service.js does not default quantity since the field is gone.

If booking.model.js no longer has a quantity field, then b.quantity from a
manually created booking document will be undefined, and:
  undefined * teu = NaN → NaN is not added correctly, defaults to 0 in
  the accumulation (NaN + 0 = NaN, but 0 + NaN = NaN).

Actually in JavaScript: 0 + NaN = NaN. So the running accumulation becomes
NaN for the first L2 booking, and remains NaN.

HOWEVER: if the model has no quantity field but imports store it, then:
  - Import bookings: quantity is stored as a number in the document
    (because insertMany passes it even without schema enforcement) ✓
  - Manual form bookings: quantity field is absent from the document.
    b.quantity = undefined.
    effectiveTEU = undefined * teu = NaN → 0 after || 0 guard.

Wait — capacity.service.js has NO || 0 guard on effectiveTEU. The line is:
  const effectiveTEU = b.quantity * teu;

If b.quantity is undefined (not in schema, not in doc), then effectiveTEU
is NaN. NaN is pushed into l2Events as the teu value.

Then in Step E:
  loadedTEU[ev.loadVoyageIdx] += ev.teu;  ← += NaN = NaN
  onboardTEU = onboardStart + loaded - discharged;  ← NaN if any loaded is NaN

This means: for bookings created via the manual form (no quantity in doc),
the onboardTEU becomes NaN for that voyage. NaN is not > 0, so the capacity
display may show 0 or NaN depending on how the frontend handles it.

This is a SECOND root cause that compounds with B1. Even if L2_STATUSES were
changed to include Pending, manual form bookings without a quantity field
would still produce NaN TEU.

HOWEVER: Re-reading booking.model.js as it actually exists today:

  The current booking.model.js (confirmed by direct file read above) does NOT
  have a quantity field at all. The field was removed at some point. But
  bookingImport.service.js still stores quantity in the documents it creates.

This means:
  - Bookings from import: have quantity in the MongoDB document (stored even
    though the schema doesn't declare it — Mongoose ignores extra fields by
    default unless strictMode is false, and if strict:true is the default,
    Mongoose would STRIP quantity from the document on save).

IMPORTANT: Mongoose strict mode (default: true) strips fields not in the
schema on save. If quantity is not in booking.model.js schema, then:
  - insertMany via Mongoose: quantity is STRIPPED from the document.
  - The stored document has NO quantity field.
  - b.quantity from any L2 booking = undefined.
  - effectiveTEU = undefined * teu = NaN.

This means ALL L2 bookings (both manual form and import) produce NaN TEU in
the capacity engine regardless of status.

CONCLUSION FOR B5:
  The capacity engine reads b.quantity, which is guaranteed to be undefined
  for all L2 bookings because:
    1. booking.model.js does not declare a quantity field.
    2. Mongoose strict mode strips undeclared fields on save.
    3. Therefore b.quantity is always undefined in a retrieved document.
    4. effectiveTEU = undefined * teu = NaN.
    5. NaN corrupts the cargo-flow accumulation for any voyage containing
       an L2 booking.

This is the ACTUAL primary root cause of 0/NaN TEU in the capacity display,
independent of the status filter issue in B1.

B6 — Complete root cause summary
────────────────────────────────────────────────────────────────────────────────

There are TWO stacked problems:

  Problem 1 (B1): L2_STATUSES = ['Confirmed', 'Final Loading']. Newly created
  bookings are Pending and are excluded from the capacity query.

  Problem 2 (B5): booking.model.js has no quantity field. Mongoose strict mode
  strips quantity from all saved documents. The capacity engine reads b.quantity
  → undefined → effectiveTEU = NaN → capacity calculation corrupted.

  Both must be fixed together. Fixing only Problem 1 (status filter) would
  still show NaN/0 because of Problem 2.
  Fixing only Problem 2 (add quantity back to schema) would still show 0
  because Pending bookings are excluded.

================================================================================
  RISKS
================================================================================

  R1 — booking.model.js: adding quantity: { type: Number, default: 1 }
       Adding a new field with a default value is safe. Existing documents
       in MongoDB that do not have a quantity field will return undefined
       when read via Mongoose, but the schema default applies at save time
       only. For the capacity engine (which reads existing documents), we
       must ensure the default works at READ time, not just save time.

       IMPORTANT: Mongoose schema defaults apply at document creation time,
       NOT when reading existing documents. A document saved without a
       quantity field will still return undefined for b.quantity when read.

       This means: for existing Pending bookings already in the database
       (without a quantity field), the capacity engine will still get NaN
       until those bookings are re-saved. New bookings created after this
       fix will have quantity=1 and will compute correctly.

       For a clean fix that works on existing documents too:
         Option A: In capacity.service.js Step C, add a guard:
           const effectiveTEU = (b.quantity || 1) * teu;
           This is a safe one-line change that makes the engine robust
           against missing quantity on any document, old or new.

         Option B: Run a migration to set quantity=1 on all existing
           Booking documents that lack it.

       Recommendation: Apply Option A (|| 1 guard in capacity.service.js)
       as the robust solution. This is a 1-character change, completely
       safe, and future-proof. Pair it with the schema default.

       If Option A is chosen, it means capacity.service.js IS modified —
       specifically only the effectiveTEU line. This is the minimum change.

  R2 — BookingList.jsx: removing Qty column
       The table has 9 columns currently including Qty. Removing Qty drops
       it to 8. The minWidth style on the table must be reviewed (currently
       800px). After removal, 700–750px is more appropriate. Minor cosmetic.

  R3 — BookingImport.jsx: removing Qty column from preview table
       The preview table has 20 columns. Removing Qty drops it to 19.
       The re-validate payload must also drop quantity to stay consistent.
       No backend change needed (backend already ignores missing quantity).

  R4 — L2_STATUSES change in capacity.service.js
       If Pending is added, capacity will immediately reflect bookings the
       moment they are created. This is the intended behavior based on the
       test scenario. The cache (60s TTL) is already correctly invalidated
       after every create/update/delete. No additional invalidation needed.
