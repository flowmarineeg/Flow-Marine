# Sprint 038 — Reporting Consolidation Implementation Plan
Status: ✅ APPROVED (Revision 2) — approved with 5 minor UI refinements,
applied below: (1) Round Capacity Cards separate "Onboard After" and
"Remaining Capacity" as two distinct figures instead of one value shown
twice; (2) Utilization % is now an explicit mandatory card field; (3)
voyage-scoped warnings render inline inside their own card, not only in
the shared warnings block; (4) Voyage Performance filters are presented
as two named groups — "Booking Source" (Layer 1/Layer 2/Combined) and
"Booking Status" (All/Final Loading) — instead of one generic toggle and
one generic checkbox; (5) Revenue Report explicitly documents, in its
own UI copy, that it represents Operational Revenue only and
intentionally excludes Pending and Confirmed bookings. This document
converts Sprint 037's approved audit findings into one concrete,
file-level implementation plan, now revised per the above. Implementation
proceeds immediately following this revision.

This sprint builds directly on `sprints/037-sprint.txt` (treated as
already-approved, not re-argued here) and on the exact review notes
supplied for this sprint, which are binding and reproduced verbatim
where they resolve a question Sprint 037 had left open.

---

# 1. EXECUTIVE SUMMARY

Sprint 037 found five confirmed issues across the reporting layer: a
dead `Booking.quantity` field rendered as real data in three reports, a
"Revenue" definition that disagreed with itself in three places, an
Expense Report with zero Sprint 036 awareness, a Round Capacity Report
whose voyage-set resolution diverges from Sprint 035's own precedent,
and a VGM figure shown in two different units by two different reports.
The review notes supplied for this sprint resolve the two genuinely open
business questions (Revenue Report's population, and Round Capacity
Report's presentation format) and give four hard constraints: reuse the
Capacity Engine unmodified, reuse the existing Booking architecture,
reuse the Expense architecture from Sprint 036, and introduce no new
models.

**This sprint plans, file-by-file, five pieces of work:**
1. Rebuild `RoundCapacityReport.jsx` from a segment table into a
   full-width, one-card-per-voyage operational timeline — a frontend
   presentation change, consuming the Capacity Engine's existing payload
   unchanged plus one small, additive, non-algorithmic field.
2. Bring `getVoyagePerformance` to dual-layer parity (Layer 1 / Layer 2
   / Combined, plus a Final-Loading-only toggle), reusing the exact
   merge-in-JS pattern already proven by `getBookingReport` (Sprint 034).
3. Narrow `getRevenueReport` to Layer 2 + Final Loading ONLY, per the
   now-final business decision, removing the dead `quantity` field in
   the same pass.
4. Bring `getExpenseReport` to Sprint 036 parity — Port scope filtering,
   display, and Voyage Cost/Other Voyage Cost classification, reusing
   `expense.service.js#deriveScope()` and
   `expenseTypeService.getCostClassificationMap()` exactly as they
   already exist, with zero new logic invented.
5. Resolve the one remaining cross-report inconsistency in scope for
   this sprint — the VGM kg-vs-MT mismatch between
   `getBookingRevenueDetails` and `getRoundPnL` — by standardizing on MT
   everywhere a report displays VGM.

Two Sprint 037 findings are explicitly and knowingly **deferred**, per
this sprint's own binding review notes: the `Round.voyageIds` vs.
`Voyage.find({roundId})` inconsistency in `capacity.service.js`
(deferred because review note 3 says "reuse the existing Capacity
Engine, do not redesign it" — voyage-set resolution is part of that
engine), and whether Revenue Report should ever derive from
Invoice/Payment data instead of raw Booking freight (still an open
business question, not resolved by this sprint's review notes). Both are
listed again under OUT OF SCOPE.

**Every route stays exactly where it is.** Confirmed by reading
`reports.controller.js` in full: every report controller already passes
`req.query` through to its service function unmodified — meaning every
new filter this sprint introduces (`portId` on Expense Report, `layer`/
`finalLoadingOnly` on Voyage Performance Report) requires **zero
controller or route changes**, only service-layer parameter handling.
This sprint adds no new endpoint anywhere.

# 2. BUSINESS VALIDATION

The following are now **closed, binding decisions** (reproduced from
this sprint's review notes, not reopened):

1. **Revenue Report represents Operational Revenue.** Layer 2 ONLY,
   status = Final Loading ONLY. This resolves Sprint 037's Business
   Rule Validation table row "❌ `getRevenueReport`" to "✅", and
   resolves Sprint 037 Section 4's open question #2 in the "booked
   freight, narrowly defined" direction — but does NOT extend to
   deriving from Invoice/Payment (that remains open, see OUT OF SCOPE).
2. **Round Capacity Report is an operational vessel timeline, not a
   summary report.** One full-width card per voyage, chronological
   order, vessel identity repeated per card for readability. This
   resolves Sprint 037 Section 4's open question #1 (whether Capacity
   Report needs a VGM figure) **implicitly by omission** — the mandated
   card field list (reproduced in Section 4.1 below) does not include
   VGM, so no VGM work is planned for this report in this sprint. If the
   business wants VGM added to this report later, that remains a
   separate, explicit future decision — this sprint does not infer it.
3. **The Capacity Engine (`capacity.service.js`) is reused, not
   redesigned.** Its cargo-flow algorithm, `L1_STATUSES`/`L2_STATUSES`,
   `resolveDischargeIdx()`, and onboard-chain math are untouched. The
   one addition this sprint makes (Section 5.1) is a single, additive,
   presentation-only computed field, following the exact precedent
   Sprint 029 already set with `loadedExact` — not a new algorithm.
4. **Booking architecture is reused, not extended.** Layer 1
   (`ManualBooking`) and Layer 2 (`Booking`) keep their current shapes;
   Voyage Performance Report's dual-layer support (Section 4.2) is a
   consumer-side merge, copying `getBookingReport`'s already-proven
   pattern verbatim, not a new booking concept.
5. **Expense architecture from Sprint 036 is reused, not extended.**
   `Expense.portId`, `deriveScope()`, and
   `ExpenseCategory.costClassification` all already exist; Expense
   Report (Section 4.4) only needs to start reading them the same way
   `getRoundPnL` already does.
6. **No over-engineering, no unnecessary new models.** Confirmed
   throughout this plan: zero new Mongoose models, zero new collections,
   zero new API routes. Every backend task below is either a query/
   aggregation change inside an existing service function or one
   additive field on an existing computed payload.

**One new finding surfaced while preparing this plan** (discovered
reading `RoundCapacityReport.jsx` in full for the Section 4.1 rebuild —
not previously caught in Sprint 037, which audited the backend services
but did not line-by-line diff every report's frontend against its
current payload shape): the existing summary KPI cards at the top of
`RoundCapacityReport.jsx` reference `raw.totals?.peakSegmentIndex`,
`raw.totals?.totalBookedTEU`, and `raw.segments?.length` — **none of
these three fields exist** in `capacity.service.js`'s actual current
payload (confirmed: it returns `totals.peakVoyageId` — not
`peakSegmentIndex` — no `totalBookedTEU` field at all (the closest real
field is `totals.totalLoadedTEU`), and `voyages[]` — not `segments[]`).
This is the exact same "segments/ports → voyages" rename claude.md
documents as a completed Sprint 023 change; these three references were
simply never updated on this one page. Since this sprint already
rebuilds this page's entire layout, this finding is folded directly into
Section 4.1's implementation rather than tracked separately — but it is
called out explicitly here because it is currently live, user-visible,
broken UI (three "—"/`0` stat cards) and its root cause is different
from anything Sprint 037 documented.

# 3. ARCHITECTURE DECISIONS (ADR)

**ADR-1 — Round Capacity Report's card rebuild is a frontend-only
change plus one additive backend field, never a Capacity Engine
redesign.** `capacity.service.js#computeRoundCapacity` already returns
every field the mandated card list needs except "Capacity Before
Loading." That one figure — TEU room available before this voyage's own
load/discharge activity — is a pure, already-known derivation
(`vessel.capacity - onboardStart`, both of which the payload already
returns) with no new business logic. Per the precedent already set by
`loadedExact` (Sprint 029 — an additive, presentation-only field
computed alongside the real onboard chain, explicitly documented as
"does NOT feed the onboard chain"), this sprint adds
`capacityBeforeLoading` as one more field in that same category, on the
same `voyageRows.push(...)` object, computed with zero new state and
zero change to the onboard/remaining/utilisation math the rest of the
system depends on.

**ADR-2 — Voyage Performance Report's dual-layer support reuses
`getBookingReport`'s merge-in-JS shape exactly, not a new pattern.**
`getBookingReport` (Sprint 034) already solved "fetch Layer 1 and Layer
2 in parallel, tag each row by layer, merge, sort in JS" for a listing
report. `getVoyagePerformance` needs the same shape but aggregated
per-voyage instead of listed per-booking — the fetch/tag/merge structure
is copied, the aggregation step (currently a single Mongo `$lookup` +
`$group` per voyage) becomes two parallel queries whose results are
merged onto each voyage row in JS, mirroring
`vessel.service.js#getVesselStats`'s "two Promise.all'd aggregates...
merged in JS by status label" pattern (Sprint 032) — the third
established precedent for this exact shape in this codebase, not
Sprint 038 inventing a fourth.

**ADR-3 — Revenue Report's narrowing reuses `getRoundPnL`'s existing
Layer-2/Final-Loading revenue query verbatim, not a new query shape.**
`getRoundPnL`'s `revenueBookings` query (`reports.service.js` lines
165–167: `Booking.find({voyageId:{$in:...}, status:'Final Loading',
isDeleted:false})`) is the exact filter Revenue Report now needs, scoped
by `serviceId`/date range instead of by voyage set. No new filter
semantics are introduced — this is the same rule, applied through a
different grouping dimension (by Service, not by Voyage).

**ADR-4 — Expense Report's Sprint 036 parity reuses
`expense.service.js#deriveScope()` and
`expenseTypeService.getCostClassificationMap()` directly, never
re-implementing either.** Both functions are already exported
(`module.exports` of their respective files already include them); this
sprint adds `require()` calls and calls the existing functions the same
way `getRoundPnL` already does — this is literal code reuse, not a
reimplementation with the same logic duplicated in a second place
(which Cross Report Consistency explicitly asks this sprint to avoid).

**ADR-5 — VGM standardizes on MT (metric tons) everywhere a report
displays it, converted once at the report layer, never on the
`Booking` model.** `Booking.vgm` stays exactly as it is today — stored
in kg, per its own field comment, unmodified (no schema change,
consistent with "introduce no unnecessary new models" and with not
touching `booking.model.js`, which Sprint 037 Section 9/Sprint 035/036
all already list as never-to-be-modified for reporting work).
`getRoundPnL` already does this conversion (`(b.vgm || 0) / 1000`,
Sprint 036); this sprint applies the identical `/1000` conversion inside
`getBookingRevenueDetails`, the only other place VGM is summed, so both
reports agree on the unit without either one's underlying data changing.

**ADR-6 — No new API routes; every new filter is a query-parameter
addition to an existing endpoint.** Confirmed by reading
`reports.controller.js` in full: every controller function already
forwards the entire `req.query` object to its service function
unchanged. `portId` (Expense Report), `layer` and `finalLoadingOnly`
(Voyage Performance Report) therefore require **no controller or route
file changes at all** — only the service functions need to read the new
key off the params object they already receive in full.

# 4. REPORT-BY-REPORT IMPLEMENTATION PLAN

## 4.1 Round Capacity Report

**Backend — `capacity.service.js#computeRoundCapacity`:**
Add one field to each `voyageRows.push(...)` object (same place
`loadedExact` is added today), immediately after `remainingTEU` is
computed:
```js
capacityBeforeLoading: cap != null ? cap - onboardStart : null,
```
No other line in `capacity.service.js` changes. `computeVesselActiveCapacity`,
`computeVoyagePreview`, `invalidateRoundCache`, the cache TTL, and every
warning code are untouched.

**Backend — `reports.service.js#getRoundCapacityReport`:** unchanged —
it already passes `{roundId, statuses}` straight to
`computeRoundCapacity()`.

**Frontend — `RoundCapacityReport.jsx`:**
- Fix the three stale summary-KPI references identified in Section 2:
  `raw.totals?.peakSegmentIndex` → look up the peak voyage's own
  `voyageNumber` via `raw.voyages.find(v => v.voyageId ===
  raw.totals?.peakVoyageId)?.voyageNumber` (peak voyage IS still
  identifiable, just not by the removed `peakSegmentIndex` field);
  `raw.totals?.totalBookedTEU` → `raw.totals?.totalLoadedTEU` (the
  actual, already-correct field); `raw.segments?.length` →
  `raw.voyages?.length`.
- Replace the `CapacitySegmentTable` usage on this page with a new
  presentational component, `VoyageCapacityCard.jsx` (new file,
  `frontend/src/modules/reports/` — a UI component, not a new "model"
  in any backend sense, consistent with "no unnecessary new models"
  which this plan reads as a backend-schema constraint), rendered once
  per entry in `raw.voyages` (already chronologically sorted by
  `sequence` — confirmed in `capacity.service.js`'s own voyage fetch,
  `.sort({ sequence: 1 })`), each card full-width, stacked vertically.
  `CapacitySegmentTable.jsx` itself is left completely unmodified — it
  remains in active use on the Vessel Details page (per claude.md's
  Sprint 023 component list), so it is not deleted, only no longer
  referenced from this one page.
- Each card renders, at minimum, exactly the fields the review notes
  mandate, each mapped to an already-existing (or, for one field,
  newly-added per Section 4.1's backend task) payload field — no field
  in this list requires inventing a new calculation:

  | Card field | Source |
  |---|---|
  | Voyage Number | `v.voyageNumber` |
  | POL | `v.fromPort.name` |
  | POD | `v.toPort.name` |
  | Vessel Name | `raw.vessel.vesselName` (round-level, repeated per card) |
  | Vessel Capacity (TEU) | `raw.vessel.capacity` (round-level, repeated per card) |
  | Capacity Before Loading | `v.capacityBeforeLoading` (new field, Section 4.1 backend task) |
  | Loaded TEU | `v.loadedTEU` |
  | Discharged TEU | `v.dischargedTEU` |
  | Onboard After | `v.onboardTEU` (TEU physically onboard once this voyage's load/discharge activity is complete) |
  | Remaining Capacity | `v.remainingTEU` (`vessel.capacity - v.onboardTEU` — the engine's own already-computed field; a genuinely separate figure from Onboard After, not the same value relabeled) |
  | Utilization % | `v.utilisationPct` (mandatory on every card per refinement 2 — not previously listed) |
  | Layer 1 Loaded | `v.layer1.loadedTEU` |
  | Layer 1 Discharged | `v.layer1.dischargedTEU` |
  | Layer 2 Loaded | `v.layer2.loadedTEU` |
  | Layer 2 Discharged | `v.layer2.dischargedTEU` |

  **Refinement 1 applied:** the original draft mapped both "Capacity
  After Cargo Operations" and "Remaining Capacity" to `v.remainingTEU`,
  treating them as one figure shown twice. Review correctly rejected
  this — "Onboard After" (`v.onboardTEU`, how much cargo is physically
  aboard) and "Remaining Capacity" (`v.remainingTEU`, how much room is
  left against `vessel.capacity`) are two distinct, already-computed
  engine fields and must be shown as two distinct card rows.

- `CapacityTimeline.jsx` (the chart) is kept above the card stack,
  unmodified, as a quick visual overview complementing the detailed
  cards below it — it already consumes `raw.voyages` correctly.
- **Refinement 3 — per-voyage warnings inline.** Every warning
  `capacity.service.js` emits that carries a `voyageId` (confirmed:
  `VOYAGE_OVERBOOKED` already does, `warnings.push({..., voyageId:
  v._id, ...})`) is filtered to that voyage
  (`warnings.filter(w => String(w.voyageId) === String(v.voyageId))`)
  and rendered directly inside that voyage's own card — no new warning
  computation, purely a client-side filter of the engine's existing
  `warnings[]` array by the `voyageId` field it already carries.
  Warnings with no `voyageId` (`CANCELLED_VOYAGES_EXCLUDED`,
  `MISSING_TEU_MAPPING`/`MISSING_CONTAINER_TYPE`/`DELETED_CONTAINER_TYPE`/
  `BOOKING_PORT_NOT_IN_ROUND`, which carry a `bookingId`/`bookingNumber`
  instead — genuinely round- or booking-level, not voyage-level) stay in
  the existing `CapacityWarnings.jsx` block below the card stack, which
  is kept for exactly this residual set — not removed.
- Overbooked voyages (`v.remainingTEU < 0`, the same condition
  `capacity.service.js` already uses to emit a `VOYAGE_OVERBOOKED`
  warning) get a visual treatment on their card (e.g. red accent
  border) IN ADDITION TO the inline warning message above — reusing the
  same warning signal the engine already computes, no new overbooking
  detection logic in the frontend.

## 4.2 Voyage Performance Report

**Backend — `reports.service.js#getVoyagePerformance`:**
- Accepts two new optional params, named to match the UI's two labeled
  filter groups (Refinement 4 — no generic/unlabeled toggle anywhere):
  `bookingSource` (`'L1' | 'L2' | 'combined'`, default `'combined'`) and
  `bookingStatus` (`'all' | 'finalLoading'`, default `'all'`).
- Replace the current single `$lookup` against `bookings` with the
  `getBookingReport`-style fetch/merge shape: for each voyage in the
  filtered `Voyage.find(match)` result set, aggregate Layer 2
  (`Booking`) and/or Layer 1 (`ManualBooking`) bookings depending on
  `bookingSource`, applying `status: 'Final Loading'` instead of `{$ne:
  'Cancelled'}` when `bookingStatus === 'finalLoading'` — reusing the
  exact status-filter pattern `getRoundPnL`'s revenue block and
  `getBookingRevenueDetails` already use for "Final Loading only."
  Concretely: two `Promise.all`'d aggregations (one per layer, skipped
  entirely when `bookingSource` excludes it) grouped by `voyageId`,
  merged onto each voyage row in JS — same shape as ADR-2.
- **Remove `$sum: '$quantity'` entirely** (Sprint 037 Section 7 Item 1).
  Replace the "units" figure with a per-source-aware equivalent: Layer 2
  contributes its booking count (one booking = one container, same rule
  `capacity.service.js` already uses: `totalL2Units = l2Bookings.length`);
  Layer 1 contributes `totalUnits` (its own real, already-correct sum
  field). When `bookingSource === 'combined'`, both are summed, mirroring
  `capacity.service.js#computeRoundCapacity`'s own `totalBookedUnits =
  totalL1Units + totalL2Units` — the exact same combination rule reused,
  not reinvented.
- `roundId`/`serviceId`/`status`/`dateFrom`/`dateTo` voyage-level filters
  are unchanged.

**Frontend — `VoyagePerformanceReport.jsx`:**
- **Refinement 4 — two explicitly labeled filter groups, not one
  generic toggle:**
  - **"Booking Source"** — three-way control, `Layer 1 / Layer 2 /
    Combined` (same visual pattern as `ExpenseForm.jsx`'s Sprint 036
    Round/Voyage/Port toggle), maps to `bookingSource`.
  - **"Booking Status"** — two-way control, `All / Final Loading` (a
    labeled two-way toggle, not a bare checkbox, so its own state is
    self-explanatory without relying on a separate label), maps to
    `bookingStatus`.
- Replace the "units" stat card's source field from `totals.totalQty`
  (dead) to the new, correctly-computed units total.
- No other layout changes required.

## 4.3 Revenue Report

**Backend — `reports.service.js#getRevenueReport`:**
- Replace the `bookings` `$lookup`'s match condition from
  `{$ne: ['$status','Cancelled']}` to `{$eq: ['$status', 'Final
  Loading']}` — the single, business-final rule (Business Validation
  item 1). Layer 2 only remains unchanged (it already was — Sprint 037
  confirmed this half of the rule was already correct).
- **Remove `$sum: '$quantity'` entirely** (Sprint 037 Section 7 Item 1),
  same fix as 4.2. Since this report is Layer 2 only, its replacement
  "units" figure is simply the booking count (`bookingCount`), the field
  this pipeline already computes separately — `totalQty` as a distinct
  column is retired rather than replaced 1:1, since Layer 2's own "one
  booking = one container" rule means `bookingCount` already IS the
  unit count; keeping both would be the same duplicated-concept problem
  Sprint 034 already resolved for the Booking Report ("Total Slots... no
  backing field... removed entirely").
- No other pipeline stages change — `serviceId`/date filters, the
  per-service `$group`, and `grandTotal` reduction all stay structurally
  identical, just operating over the narrowed match condition.

**Frontend — `RevenueReport.jsx`:**
- Remove the "Units" column (both per-row and `grandTotal`), since
  `bookingCount` (already displayed as "Bookings") now fully covers what
  that column was attempting to show, per the backend change above.
- **Refinement 5 — explicit documentation in the report's own UI, not
  just this planning document.** Update the report's subtitle to read
  something to the effect of: *"Operational Revenue — Layer 2, Final
  Loading bookings only. Pending and Confirmed bookings are
  intentionally excluded."* This is stronger than the original plan's
  "state the scope" — it must name Pending/Confirmed explicitly as
  excluded, not just say "Final Loading only," so a reader unfamiliar
  with the booking status lifecycle still understands what is missing
  and why. Same transparency precedent `RoundPnlReport.jsx` already set
  for its Revenue-by-Voyage section, made more explicit here per the
  review note.

## 4.4 Expense Report

**Backend — `reports.service.js#getExpenseReport`:**
- Accept a new optional `portId` param; add `if (portId) match.portId =
  toObjId(portId);` alongside the existing `roundId`/`voyageId` filters.
- Add `.populate('portId', 'name code')` to the existing `Expense.find()`
  query (mirrors `getRoundPnL`'s own `.populate('portId', 'name
  code')`, line 196, verbatim).
- Apply `expense.service.js`'s `deriveScope()` to every returned row —
  either by importing the existing helper directly
  (`const { deriveScope } = require('../expenses/expense.service')` —
  requires `deriveScope` to be added to that file's `module.exports`,
  a one-line addition, not new logic) or by inlining the identical
  three-line inference already documented in `sprints/036-sprint.txt`
  ADR-2 — this plan's preferred approach is the direct import, since it
  guarantees the two reports can never define scope differently in the
  future (the exact duplication risk Cross Report Consistency asks this
  sprint to eliminate).
- Add a second summary dimension alongside the existing category+
  currency `summaryMap`: group by `(costClassification, currency)`
  using `expenseTypeService.getCostClassificationMap()` — the identical
  map `getRoundPnL` already builds and consumes — so Expense Report can
  show "Voyage Cost: $X / Other Voyage Cost: $Y" figures that are
  guaranteed to reconcile with `getRoundPnL`'s own totals for the same
  round, because both read the exact same classification source.

**Frontend — `ExpenseReport.jsx`:**
- Add a Port filter dropdown, cascading from the existing Voyage filter
  (reusing the voyage's own populated `polId`/`podId` the same way
  `ExpenseForm.jsx`'s Sprint 036 Port selector already does — no new
  endpoint, ADR-3 of Sprint 036 reused again here).
- Add a Scope column to the detail table (reusing `ExpenseList.jsx`'s
  existing Scope badge markup/coloring verbatim).
- Change the Port column to prefer `e.portId?.name` over the legacy
  `e.port` string, same fallback order `ExpenseList.jsx` already uses.
- Add a second summary block — "By Classification" — next to the
  existing "Summary by Category" block, rendering the new
  classification-grouped totals from the backend change above.

## 4.5 Cross Report Consistency

**Backend — `reports.service.js#getBookingRevenueDetails`:**
- Change `g.vgm += (b.vgm || 0)` to `g.vgm += (b.vgm || 0) / 1000` —
  the identical conversion `getRoundPnL` already applies (ADR-5). This

**Frontend — `BookingRevenueDetailsReport.jsx`:**
- Update the "Total VGM" stat card's `sub` label from `"kg"` to `"MT"`

- Update the detail table's VGM column header from "VGM" to "VGM (MT)",
  matching `RoundPnlReport.jsx`'s existing "VGM (MT)" column header

**No other cross-report consistency work is required this sprint** —
Section 6 of Sprint 037 confirmed Booking Status (capacity purposes),
TEU, and Capacity itself are already fully consistent; this sprint's
Revenue and Expense work (4.3/4.4) closes the two remaining gaps that
section identified, and the VGM fix above closes the third.

# 8. VALIDATION RULES

- `bookingSource` param on `GET /reports/voyage-performance`, if
  provided, must be one of `'L1'`, `'L2'`, `'combined'` — invalid values
  rejected with 400, same validation convention as every other
  enum-constrained query param in this codebase (e.g.
  `capacity.service.js`'s own `ALLOWED_CAPACITY_STATUSES` check).
- `bookingStatus`, if provided, must be one of `'all'`, `'finalLoading'`
  — same 400-on-invalid convention as `bookingSource` above (both are
  now named, closed enums per Refinement 4, not a boolean flag).
- `portId` on `GET /reports/expenses`, if provided, must be a valid
  Mongo ID — reuses the same `isMongoId()` validation style already
  applied to every other filter of this kind in this codebase, though as
  a GET query filter (not a body field) it follows the existing
  convention of other report filters (`roundId`/`voyageId` on this same
  endpoint) of not hard-validating format at the route layer, since an
  invalid ID simply yields zero results rather than a data-integrity
  risk.
- No new validation is needed for the Round Capacity Report's
  `capacityBeforeLoading` field — it is a pure derivation with no user
  input.

# 9. RISKS

1. **Voyage Performance Report's response shape changes** (per-voyage
   layer breakdown fields, removed `totalQty`) — any external consumer
   of this endpoint beyond `VoyagePerformanceReport.jsx` itself would
   need updating; a repo-wide search for other consumers is required
   before implementation to confirm none exist (expected: none, since
   this report has no cross-module dependents documented anywhere in
   claude.md, but this must be verified, not assumed, during
   implementation).
2. **Revenue Report's headline number will change** (likely downward)
   the moment Pending/Confirmed bookings are excluded — this is the
   entire intent of the business decision, but anyone comparing a
   pre-Sprint-038 screenshot/export to a post-Sprint-038 one will see a
   discontinuity that has no bug behind it. Recommend the release notes
   for this sprint explicitly call this out.
3. **`deriveScope` becoming a public export of `expense.service.js`**
   slightly widens that module's public surface — low risk (it is a
   pure function with no side effects and no DB access), but worth
   noting since Expense module changes have historically been treated
   carefully in this codebase (Sprint 036's own care around not touching
   `expense.model.js`).
4. **The VGM unit fix changes a previously-displayed number**
   (`getBookingRevenueDetails`'s VGM, kg → MT, i.e. divided by 1000) —
   same class of risk as #2: correct, intentional, but a visible
   discontinuity for anyone comparing before/after figures.
5. **Round Capacity Report's full rebuild is the largest frontend change
   in this sprint** — the existing `CapacitySegmentTable`/
   `CapacityTimeline` components are proven and already correctly wired;
   the new `VoyageCapacityCard` component needs equivalent manual QA
   (overbooked-voyage styling, zero-voyage rounds, single-voyage rounds)
   before this is considered done.
