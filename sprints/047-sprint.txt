# 0. HARD CONSTRAINTS (explicit, honored throughout)

- No redesign. No new architecture.
- No new backend endpoints. No bulk-delete API of any kind.
- No discussion of hard delete vs soft delete — each entity keeps whatever
  delete behavior it already has today, untouched (Part B later converts
  the mechanism, but Part A never touched a guard).
- No refactor of existing code — only additive UI + a client-side loop.
- Every "delete selected" action is: loop the selected ids, call the
  EXISTING single-item delete endpoint for each one, one at a time. All
  existing backend validation/business rules fire exactly as they do today
  for a single delete — nothing server-side changes.
- If one item fails (blocked by an existing guard, 404, etc.), record it as
  failed and keep going — do not abort the rest of the loop.

# PART B — REMOVE SOFT DELETE, CONVERT TO HARD DELETE (simple, no cascade)

Full-codebase audit performed (every `.model.js` and `.service.js` under
`backend/src/modules` read/grepped directly — nothing assumed from
claude.md's summary). Everything that WAS a design decision in an earlier
planning round (a shared recursive/transactional "cascade delete" helper)
was explicitly DISCARDED before implementation and replaced with the
simple version below.

## Goal (verbatim scope, per explicit instruction) — ACHIEVED

Convert the system from soft delete to hard delete while keeping the
existing business rules as simple as possible.

For every currently soft-deletable entity, the delete flow is now:
1. Delete is requested.
2. Check whether the entity is still referenced by related business data
   — using the EXACT SAME check that existed in that entity's
   `softDelete`/`remove` function before this sprint, unchanged.
3. If related data exists → reject, with a clear message naming what
   depends on it (same message every guard already gave).
4. If nothing references it → permanently hard-delete the record
   (`Model.findByIdAndDelete(id)`), replacing the old
   `isDeleted=true; deletedAt=...; save()` steps.

No automatic cascade. No recursive delete. No transaction-based delete
engine. No shared/generic delete service. The administrator remains
responsible for deleting dependent records manually first — exactly the
same responsibility as before this sprint. The only user-visible change:
a delete that's allowed to proceed is now permanent, not soft.

**User is the sole, explicit exception** — `user.service.js#softDelete`
was not touched at all, keeps its exact pre-sprint soft-delete behavior.

# 7. KNOWN CONSEQUENCES — accepted as-is, not redesigned

Per explicit instruction, existing business rules were not changed
"unless absolutely required to preserve referential integrity." Neither
item below creates a referential-integrity problem — both are accepted,
documented trade-offs, not bugs:

## 7.1 Capacity engine's soft-deleted-ContainerType branch — removed as dead code

`capacity.service.js` used to populate `containerTypeId` with `'code size
isDeleted'` and branch on `.isDeleted` to emit a `DELETED_CONTAINER_TYPE`
warning while still using the soft-deleted type's `size`. Since
ContainerType's guard is unchanged (still only blocks on an ACTIVE
booking), a ContainerType used only by inactive/cancelled bookings can
still be hard-deleted — `populate()` now returns `null` for those, hitting
the existing `MISSING_CONTAINER_TYPE` fallback instead. The dead branch
and its `isDeleted` populate projection were removed during
implementation. capacity.service.js's cargo-flow algorithm itself was NOT
touched.

## 7.2 Invoice drill-down to a hard-deleted Booking

Booking's guard is unchanged (blocks only if a NON-cancelled Invoice
references it). A Booking that was only ever on a since-cancelled invoice
(or never invoiced) can still be hard-deleted; that invoice's own line
item still displays correctly (Sprint 033 historical snapshot), only the
live "view original booking" link would 404. Accepted, not fixed.

## 7.3 Populate has no `isDeleted` exclusion anywhere — context only

Confirmed zero uses of Mongoose's `populate(...match...)` filtering syntax
anywhere pre-sprint — soft-deleting was already invisible to existing
reads; hard delete simply turns the same reference into `null` once the
row is actually gone. No fix needed/attempted.

# 8. MANDATORY ONE-TIME DATA MIGRATION — SHIPPED, MUST BE RUN

Required and built: `backend/src/config/migrations/
migrate-hard-delete-cleanup.js` (same guarded `require.main === module`
pattern as `migrate-invoice-v2.js`), run via:

```
npm run migrate:hard-delete-cleanup
```

Runs `Model.collection.deleteMany({isDeleted:true})` (raw collection
access, not the Mongoose model, since the schema no longer declares the
field) for each of the 14 converted models, BEFORE or as the very first
step of deploying this sprint's changes to any environment. Without it,
every row that was ever soft-deleted before this sprint would instantly
reappear in every list/report/dropdown the moment the query filters were

be run once against any environment (staging/production) that hasn't had

# 9. UNIQUE-VALUE REUSE — confirmed, accepted side effect

No partial/filtered unique index existed anywhere in this codebase, and
none of the `create()`/`update()` duplicate-checks scoped by
`isDeleted:false` either. Practical effect: hard delete now frees up
previously-blocked unique values (vesselCode, agentCode, serviceCode,
ContainerType.code, ExpenseType.name, Role.name, Country name/code,
City/Port/Terminal compound names) immediately upon deletion — a
deliberate, desirable side effect, not a bug.

**Bonus, incidentally fixed:** Role's duplicate-name check already
excluded `isDeleted:true` rows, but the DB-level unique index on `name`
did not — reusing a soft-deleted Role's exact name used to throw an
unhandled Mongo duplicate-key 500 instead of a clean 400. This is gone now
that Role is hard-deleted (no leftover row, no index collision).

# 12. POST-SHIP REFINEMENTS — Agent + Round (same sprint, explicit follow-up instructions)

Two narrow, explicitly-requested additions after Part B's initial ship —
each is a single, specific relationship, not a reopening of the "no
cascade" decision:

## 12.1 Agent.hardDelete — added a second guard (Invoice)

`agent.service.js#hardDelete` gained a second check, in addition to the
existing active-Booking guard: blocked if a non-cancelled `Invoice`
references the agent (`Invoice.agentId`). Same "non-cancelled only"
threshold as Booking's own invoice guard (§5's table) — not "any invoice
ever." This is a guard STRENGTHENING (Agent could previously be deleted
with invoice history present; now it can't while any active invoice
exists), explicitly requested and confirmed via clarifying question before
implementation.

## 12.2 Round.hardDelete — now also deletes its own Voyages

`round.service.js#hardDelete` now hard-deletes its own Voyage documents
(`Voyage.deleteMany({_id:{$in: round.voyageIds}})`) once its guards
confirm none of them are referenced. Voyages have no independent existence
outside their Round (auto-generated by `utils/voyageGenerator.js`,
exclusively owned) — this is a narrow, single-relationship cleanup
specific to that exclusive ownership, confirmed via clarifying question
NOT to be a reopening of the generic recursive cascade design rejected
earlier in this sprint. It does not reach any further down the graph —
Invoice is untouched (Booking's own guard already blocks its own delete
if a non-cancelled Invoice references it, so an invoiced Booking blocks
the Round delete transitively). Implementation choice (confirmed): direct
`Voyage.deleteMany()`, not a loop calling `voyage.service.js#deleteVoyage`
per voyage (the round-level guards already confirmed nothing references
any of the round's voyages, so a per-voyage re-check would be redundant).

**Post-audit fix (`system-audit-2026-8-3.md` §2.1):** the guard as first
shipped checked only Layer 2 `Booking` — the Voyage cascade could
silently orphan a live Layer 1 `ManualBooking` or an `Expense`
(Round- or Voyage-scoped) referencing one of the round's voyages, since
neither of those has independent existence once its voyage is deleted
either. Fixed by adding two more guard checks, same shape as the existing
Booking one:
```js
const hasManualBooking = await ManualBooking.exists({ voyageId: { $in: voyageIds } });
if (hasManualBooking) throw { status: 400, message: 'Cannot delete — one or more voyages have estimated bookings' };

const hasExpense = await Expense.exists({ $or: [{ roundId: id }, { voyageId: { $in: voyageIds } }] });
if (hasExpense) throw { status: 400, message: 'Cannot delete — expenses are recorded against this round or its voyages' };
```
Expense is checked against BOTH `roundId` (Round-scoped expenses) and
`voyageId` (Voyage/Port-scoped expenses), since `Expense.portId` is only
ever set alongside `voyageId` (Sprint 036 — Port is a refinement of
Voyage scope, never independent), so the `voyageId` half of the `$or`
already covers Port-scoped expenses too.

Both refinements verified via `node --check`; `CLAUDE.md`'s Deletion Rules
table (§9) updated to reflect both.

  strings, `_id:false`) on `invoice.model.js`.
- **NEW `PUT /invoices/:id/bill-to`** route → `invoice.controller.js#
  updateBillTo` → `invoice.service.js#updateBillTo(id, billTo)` — a

## 13.4 Invoice PDF (`utils/invoicePdfGenerator.js`) — final layout

1. Header bar — **"FLOW MARINE"** (was "Flow Dubai" — renamed everywhere:
   header, PDF `Author` metadata, footer). Footer's "| Dubai, UAE" segment
   removed entirely — footer now reads "Flow Marine | Shipping &
   Logistics Operations".
2. Meta strip — status pill, invoice date, due date (unchanged).
3. Billing row — **Bill To** (agent name/code + `invoice.billTo` fields;
   mobile/email fall back to the agent's own contact when not set on the

   render, so an invoice with no Bill To filled in yet shows no
   placeholder wall) | **Shipment Details** (Type/POL/POD/Voyage/Round —
   Voyage/Round no longer gated by `invoiceType`; both resolve from

   type, showing "N voyages"/"N rounds" if they don't all share one).

   details block (Bank Name/Account/SWIFT/Reference) — neither of those
   exists anymore.
6. Footer — "Flow Marine | Shipping & Logistics Operations" + generated
   date + invoice number (unchanged shape, just the rebranded text above).
