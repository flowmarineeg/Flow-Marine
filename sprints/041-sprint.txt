# 1. POINT 1 — ROUND NAME / VOYAGE NAME

## 1.1 Business objective

Today `Round.roundNumber` (e.g. `R000001`) and `Voyage.voyageNumber`
(e.g. `SEN-R000001-01`) are the ONLY human-facing reference for a Round
or Voyage anywhere in the system — in every list table, every `<select>`
dropdown, every detail/view page, and every other module that references
a Round or a Voyage (Bookings both layers, Expenses, Invoices, Tracking,
Capacity Reports, Voyage Performance, Agent Financial Account, Vessel
Details, Export, Dashboard). These codes are useful as unique system
identifiers but meaningless as a business reference — nobody remembers
"R000001" refers to the Q3 Red Sea coffee run. The objective is to let
an admin attach a real name to a Round/Voyage at creation or edit time,
and have that name appear next to the number everywhere the number is
shown today, so operators can recognize records by name instead of code.

## 1.2 What already exists (do not confuse with the new fields)

- `Round.notes` (`round.model.js` line 14) — free-text but semantically
  "operational notes," not a short display name. Kept as-is, untouched.
- `Voyage.voyageCode` (`voyage.model.js` line 9, `String, trim, default:
  null, maxlength: 50`) — an EXISTING optional admin-entered free-text
  field, already editable in both `VoyageAddForm.jsx` and
  `VoyageEditForm.jsx` (e.g. "V2025-001", "SHUTTLE-MAR").
  **DECIDED (§1.7 Q1): `voyageCode` stays untouched, separate purpose.**
  A genuinely new `voyageName` field is added alongside it — two
  distinct free-text fields will sit next to `voyageNumber` on Voyage
  (`voyageCode` for whatever code-like label it's used for today,
  `voyageName` as the new business-facing display name). Both are
  distinct fields going forward; do not merge or conflate them anywhere
  in implementation.
- Confirmed via codebase-wide search: zero existing usages of
  `roundName` or `voyageName` anywhere in backend or frontend today.

## 1.3 Schema changes (additive only)

- `round.model.js` — add `roundName: { type: String, trim: true, default:
  null }`, sitting next to `roundNumber`. Schema-level `required: true`
  is NOT used (see note below) — required-ness is enforced only in
  `round.validation.js#validateCreate`, not at the Mongoose schema layer.
- `voyage.model.js` — add `voyageName: { type: String, trim: true,
  default: null }`, sitting next to `voyageNumber` (and distinct from the
  existing `voyageCode`, per §1.2, DECIDED — both fields coexist).
- No index changes required — **DECIDED (§1.7 Q3): not unique**, this is
  a display label, not an identifier.
- **DECIDED (§1.7 Q7): required going forward for new records only.**
  `validateCreate` for both Round and Voyage will reject a create request
  with no `roundName`/`voyageName`. The schema field itself stays
  `default: null` (not `required: true` at the Mongoose level) precisely
  because every EXISTING Round/Voyage in the database has no name and
  must remain loadable/editable without being force-migrated — the hard
  requirement applies only to the create-time validation layer, not
  retroactively to existing documents. `validateUpdate` does NOT require
  it (an existing unnamed record can be edited without being forced to
  add a name in the same request — only NEW creates are blocked without
  one).

## 1.7 Decisions (all questions answered, locked in)

- **Q1 — Voyage: `voyageCode` vs. new `voyageName` → DECIDED: add a
  genuinely new, separate `voyageName` field.** `voyageCode` is left
  completely untouched (different field, different purpose). See §1.2.
- **Q2 — Fallback display rule → DECIDED: always show both.** Every
  display location in §1.5 renders a name slot next to the Number even
  when no name has been set yet — e.g. a visible placeholder such as
  `"(unnamed)"` or an empty/dash placeholder next to the Number, rather
  than collapsing to Number-only until a name exists. Exact placeholder
  copy (blank vs. "(unnamed)" vs. "—") is an implementation-time UI
  detail, not a further open question — pick one and apply it
  consistently across every one of the ~70 sites in §1.5.
- **Q3 — Uniqueness → DECIDED: not unique.** Pure display label, no
  index, duplicates allowed.
- **Q4 — Invoice line-item snapshot → DECIDED: yes, add it.**
  `Invoice.lineItems[]` gains `roundName`/`voyageName` snapshot fields,
  captured at invoice-creation time going forward
  (`invoice.service.js#buildLineItemSnapshot`/`getEligibleBookings`).
  Historical invoices created before this ships will NOT retroactively
  gain a name (same as every other snapshot field, per the existing,
  deliberate Sprint 033 "snapshot, never re-read live" rule) — this is
  an accepted, unavoidable consequence, not a gap to fix.
- **Q5 — Invoice PDF → DECIDED: yes.** `invoicePdfGenerator.js`'s header/
  line-item table (lines 138-139, 269-270) renders the name next to the
  number too, consistent with Q4.
- **Q6 — Searchability → DECIDED: yes.** `round.service.js#list()`'s
  search `$or` clause (lines 36-41) gains a `{roundName: regex}` third
  clause; the equivalent search in `voyage.service.js#list()` (if one
  exists — verify at implementation time) gains `{voyageName: regex}`
  similarly.
- **Q7 — Required or optional → DECIDED: required, for new records
  only.** See §1.3 for the exact validation-layer-only enforcement
  (schema stays `default: null`, only `validateCreate` blocks a
  nameless create going forward). Existing nameless Rounds/Voyages are
  NOT retroactively invalidated or blocked from being edited.

## 2.2 Booking Import — downloadable Excel template

**Current state, confirmed:** no template-download feature exists
anywhere today (`grep -rni "template"` across the entire `bookings` and
`export` modules returns zero hits related to import). The only related
UI is a static, read-only "Expected Excel Columns" reference grid already
rendered in `BookingImport.jsx` lines 396-430 — informational only, not
a downloadable file.

**Change:** add a "Download Template" button to the Booking Import
screen (`BookingImport.jsx`) that downloads a blank `.xlsx` file
containing ONLY a header row with the column names the import parser
actually recognizes, ready for an admin to fill in and re-upload.

**Design constraint found during research — do NOT reuse the export
module's `bookings` COLUMNS as-is.** `export.service.js`'s existing
`buildExcelBuffer()` (lines 277-324, called with `rows=[]` would already
produce a "headers only" file — a reusable existing mechanism) is a
sound pattern to reuse, but its `COLUMNS.bookings` array (lines 129-151)
is for EXPORT display, not import parsing, and the two header sets
diverge:
- Export's `Voyage Number`, `Agent Code`, `Agent Name`, `Total Freight`,
  `Remarks`, `Status`, `Created At` columns have NO matching key in the
  import's `EXCEL_COLUMN_MAP` (`BookingImport.jsx` lines 30-67) — if
  present in an uploaded file they are silently ignored today.
- Export's `VGM (kg)` header does not match any import alias key (only
  bare `vgm`/`verified gross mass` are recognized) — a re-uploaded
  export file's VGM column would silently fail to map.
- The import map also recognizes several aliases the export COLUMNS
  don't even have as separate columns (`Container Size`/`Size`/`Length`,
  `Cntr No`, `Cntr Type`, `Port of Loading`/`Port of Discharge`).

The template must therefore be built from a NEW, purpose-built column
list matching the import's actual recognized primary headers (one
canonical alias per field — e.g. `Container Number`, `Container Type`,
`Container Size`, `POL`, `POD`, `Freight Rate`, `Shipper`, `Consignee`,
`Carrier Name`, `Commodity`, `VGM`, `Hazardous`, `IMDG Code`, `Container
Status`), NOT copied from `export.service.js#COLUMNS.bookings`.
`Booking Number`/`Container Number` stay as the two identity columns
(Container Number is the primary match key per `claude.md` Sprint 021).
Agent and Round are page-level selections (not per-row columns, per the
existing Import Settings panel), so they are NOT included in the
template's columns — consistent with today's `EXCEL_COLUMN_MAP` which
has no `agentId`/`roundId` key either.

One template covers both `importType='booking'` and
`importType='finalLoading'` — **DECIDED (§2.4 Q1): one universal
template**, since `EXCEL_COLUMN_MAP` is not split by import type today
(confirmed, single shared map).

## 2.3 Import case-sensitivity fixes — full column-by-column audit

Per explicit instruction, every column value the import parser touches
was re-checked for case-sensitivity, not just the Hazardous/`dg` field.
Result: two real bugs found (both already case-sensitive gaps), and
three columns confirmed already correct — nothing else in the file
performs case-sensitive comparison against a fixed value set. Free-text
columns (`shipper`, `consignee`, `commodity`, `carrierName`, `remarks`,
`imdgCode`) are excluded from this audit on purpose — they are stored
verbatim, not matched against an enum, so "case-sensitivity" doesn't
apply to them (forcibly upper/lower-casing a shipper or consignee name
would corrupt real data, not fix a bug).
