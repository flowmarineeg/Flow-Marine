  SPRINT 022 - Dynamic Per-Leg Vessel Capacity Engine (PLANNING - APPROVED)
  Date: 2026-07-19  (Revision 3 — Final)
  Status: COMPLETE — All 5 phases implemented
================================================================================

SPRINT SUMMARY:
  Replace the current "total booked containers per vessel" capacity model with
  a per-leg dynamic capacity engine measured in TEU. The engine calculates
  onboard TEU and remaining free capacity at every route leg of a round,
  accounting for continuous loading and discharging at each port call.

  TEU is derived purely from container size using a small, deterministic
  lookup. Container Type (Dry, Reefer, etc.) has NO impact on capacity and
  is ignored by the engine. NO schema changes required.

  Scope is deliberately focused on the vessel's CURRENT ACTIVE ROUND.
  Tracking, GPS, and vessel position are explicitly OUT OF SCOPE.

  NO CODE CHANGES YET. Awaiting explicit "Start Phase 1" before implementation.

================================================================================
  1. CURRENT ARCHITECTURE — ANALYSIS
================================================================================

  1.1 DATA MODEL AS IT STANDS TODAY

    Service (1) ───< Route (1) ───< RouteLeg (n)   [ordered by sequence]
       │
       └───< Round (n) ───< Voyage (n)
                                │
                                └───< Booking (n) → ContainerType (n)
       │
       └───< Vessel (assigned per Round)

    Key facts verified against the code:
      - Route has ordered RouteLegs; each leg is ONE port.
      - createRound() calls voyageGenerator.js which creates ONE Voyage per
        adjacent leg pair — route with N legs produces N-1 voyages per round.
      - Booking has its own polId + podId; both are validated against the
        service route port list (booking.service.js getVoyagePortIds).
      - Booking has containerTypeId (required, ref: ContainerType).
      - ContainerType has size (enum '20ft' | '40ft' | '40HC' | '45ft') and
        type (enum 'Dry' | 'Reefer' | 'Open Top' | 'Flat Rack' | 'Tank').
      - Vessel.capacity is a TEU number (nullable).
      - vessel.service.js getVesselStats() currently sums booking.quantity
        across all Active+Planned rounds against vessel.capacity — this is
        the flawed logic being replaced.

  1.2 TEU IS A PURE FUNCTION OF CONTAINER SIZE

    The engine computes:

      effectiveTEU = booking.quantity × TEU(containerSize)

    Where TEU(size) is a small deterministic mapping:

      Any size representing 20ft         → 1 TEU
      Any size representing 40ft or 40HC → 2 TEU
      Any size representing 45ft         → 2 TEU
      Unknown / unrecognised size        → 1 TEU  (fail-safe) + warning

    Container Type (Dry, Reefer, Tank, Flat Rack, etc.) is IGNORED for
    capacity purposes.

    The engine resolves the size by looking up the booking's containerTypeId,
    reading .size from the referenced ContainerType, and passing that string
    to the TEU-resolver function. The ContainerType document itself receives
    no schema change.

    NORMALISATION for extensibility:
      The resolver normalises the size string before matching — trims,
      uppercases, strips spaces — so future sizes like ' 40 HC', '40hc',
      '40HC-DRY' all match the 40HC bucket. Regex-based bucketing:

        /(^|[^0-9])20/  → 1 TEU
        /(^|[^0-9])40/  → 2 TEU
        /(^|[^0-9])45/  → 2 TEU
        else            → 1 TEU + MISSING_TEU_MAPPING warning

      This means the client can add a new enum value like '20RF' or '40OT'
      without a code change — the resolver still matches the leading digits.
      Non-numeric-lead sizes would need explicit handling; documented as a
      known future extension point (single function to edit).

  1.3 WHERE CAPACITY IS DISPLAYED / QUERIED TODAY

    Backend:
      - vessel.service.js → getVesselStats() returns { capacityUsed, capacityPct }
        USED BY: GET /vessels/:id/stats
        CONSUMED BY: frontend VesselDetail.jsx (doughnut chart + KPI)

    Frontend:
      - modules/vessels/VesselDetail.jsx renders the doughnut based on
        stats.capacityUsed vs vessel.capacity.
      - No other page currently displays capacity.

    Reports and Bookings: capacity is not currently referenced.

  1.4 EXISTING BUSINESS RULES CARRIED FORWARD

    - Booking POL and POD must both be in the service route leg list.
    - Voyage POL = leg[i], POD = leg[i+1] for auto-generated voyages.
    - Manual voyages may skip legs.
    - vessel.capacity stored in TEU (nullable).
    - Only one Round with status='Active' per vessel at a time (already
      enforced by round.service.js create()). This makes "current active
      round" a clean, unique concept for the vessel detail page.

================================================================================
  2. TARGET STATE — WHAT THE NEW ENGINE MUST DELIVER
================================================================================

  2.1 CORE PRINCIPLE — CAPACITY IS PER-LEG, MEASURED IN TEU

    Given a service route with ports [P1, P2, P3, P4] and vessel capacity C TEU:

      Segment 1:  P1 → P2
      Segment 2:  P2 → P3
      Segment 3:  P3 → P4

    A booking occupies segment[k] iff pol.sequence ≤ k AND pod.sequence ≥ k+1.

    Example:
      Booking A: 10 × 20ft → 10 TEU across its segments
      Booking B:  5 × 40ft → 10 TEU across its segments
      Both consume identical capacity even though quantity differs.

    Onboard TEU on segment k = sum of effectiveTEU for all bookings covering
    that segment.

  2.2 SCOPE FOCUS — CURRENT ACTIVE ROUND ONLY

    The Vessel Details page shows the vessel's current operational journey:
      "Which Active round is the vessel on? What does each leg look like?"

    If the vessel has no Active round, an empty state is shown.

    Historical and completed rounds are OUT OF SCOPE for this sprint. The
    engine's core computeRoundCapacity() can still compute for any roundId —
    this is a UI focus decision, not an engine limitation. Reports (Phase 3)
    may still target any round.

  2.3 REQUIRED OUTPUT SHAPE

    computeRoundCapacity(roundId) returns:

      {
        round:   { _id, roundNumber, status, startDate, endDate },
        vessel:  { _id, vesselCode, vesselName, capacity },  // TEU
        route:   {
          _id,
          ports: [{ sequence, portId, name, code }]           // ordered
        },
        segments: [
          {
            segmentIndex: 1,
            fromPort: { portId, name, code, sequence: 1 },
            toPort:   { portId, name, code, sequence: 2 },
            voyageId: <ObjectId | null>,
            voyageStatus: <string | null>,
            isManualJump: false,
            loadedTEU:      <TEU loaded at fromPort>,
            dischargedTEU:  <TEU discharged at fromPort>,
            onboardTEU:     <TEU carried across this segment>,
            remainingTEU:   <vessel.capacity - onboardTEU | null>,
            utilisationPct: <round(onboardTEU / capacity * 100) | null>
          },
          ...
        ],
        ports: [
          {
            portSequence:   1,
            port:           { portId, name, code },
            loadedTEU:      <TEU loaded here>,
            dischargedTEU:  <TEU discharged here>,
            netChangeTEU:   loadedTEU - dischargedTEU,
            onboardAfterTEU: <onboard after this port call>
          },
          ...
        ],
        totals: {
          peakOnboardTEU:     <max segment.onboardTEU>,
          peakSegmentIndex:   <index of peak>,
          avgUtilisationPct:  <mean of non-null segment.utilisationPct>,
          totalBookedTEU:     <sum of effectiveTEU across included bookings>,
          totalBookedUnits:   <sum of qty>
        },
        warnings: [
          { code, message, bookingId?, containerNumber? }
        ]
      }

  2.4 EDGE CASES

    E1  Booking POL == POD → rejected by validation upstream. Engine ignores.

    E2  Booking with polSeq >= podSeq (data corruption).
        Warning code: 'INVALID_DIRECTION'. Booking excluded.

    E3  Simultaneous load + discharge at intermediate port.
        Discharge netted first (containers off before on) so onboard-after
        correctly reflects final state. Both raw values still surfaced.

    E4  Booking statuses to include.
        Default: ['Confirmed', 'Final Loading'].
        opts.statuses can widen to include 'Pending' for what-if analysis.

    E5  Overbooked segment (onboardTEU > vessel.capacity).
        Warning code: 'SEGMENT_OVERBOOKED' with over-amount.
        Not blocked in Phase 1–2. Enforcement is Phase 4 (feature-flagged).

    E6  Manual voyage skips a route leg.
        Segments without a covering voyage are flagged isManualJump = true.
        Bookings that discharge at a skipped port get warning
        'BOOKING_INTO_UNCALLED_PORT' and are excluded.

    E7  Route legs edited after bookings exist.
        Booking references a port no longer in the route.
        Warning 'BOOKING_PORT_NOT_IN_ROUTE'. Excluded from calc.

    E8  vessel.capacity is null.
        onboardTEU returned; remainingTEU and utilisationPct returned as null.
        UI shows em dash. peakOnboardTEU still present.

    E9  Unrecognised container size (data corruption or new enum not yet
        covered by the resolver).
        Warning code: 'MISSING_TEU_MAPPING' with bookingId + raw size string.
        Fail-safe: treat as 1 TEU. Never silently dropped.

    E10 Mixed container sizes across bookings on the same segment.
        Handled naturally — each booking's effectiveTEU is computed
        independently then summed. No special case.

    E11 Container type isDeleted after booking was created.
        containerTypeId still resolves via populate (Mongo does not enforce
        isDeleted on read). Warning 'DELETED_CONTAINER_TYPE' surfaced for
        audit but calc proceeds using the soft-deleted record's size.

    E12 Round with 0 bookings.
        Every segment: loadedTEU=0, dischargedTEU=0, onboardTEU=0,
        remainingTEU=vessel.capacity, utilisationPct=0.

    E13 Route with only 2 legs → 1 segment → 1 voyage. Trivial case.

    E14 Booking without a containerTypeId (data corruption; field is required
        at model level so should not occur, but defensive).
        Warning 'MISSING_CONTAINER_TYPE'. Booking excluded.

  TEU RESOLVER (backend/src/utils/teuResolver.js):

    /**
     * Derive TEU value from a container size string.
     * Size-only mapping — Container Type is intentionally ignored.
     *
     * @param {string} size — e.g. '20ft', '40ft', '40HC', '45ft'
     * @returns {{ teu: number, matched: boolean }}
     */
    function resolveTEU(size) {
      if (!size || typeof size !== 'string') {
        return { teu: 1, matched: false };
      }
      const norm = size.trim().toUpperCase().replace(/\s+/g, '');
      // Extract the leading numeric length
      const m = norm.match(/^(\d{2,3})/);
      if (!m) return { teu: 1, matched: false };
      const len = Number(m[1]);
      if (len === 20)             return { teu: 1, matched: true };
      if (len === 40 || len === 45) return { teu: 2, matched: true };
      return { teu: 1, matched: false };
    }

    module.exports = { resolveTEU };

    Rationale:
      - Length-based bucketing handles current enum ('20ft','40ft','40HC','45ft')
        AND future variants like '20RF', '40OT', '45HC' without change.
      - Single function; changes localised to one file if business rules
        ever shift.
      - Returns matched flag so the engine can emit MISSING_TEU_MAPPING when
        a size is unrecognised.

  PUBLIC API (functions in capacity.service.js):

          margins: [{ segmentIndex, onboardAfterAdd, remainingAfterAdd }]

  ALGORITHM (computeRoundCapacity):

    Step A — Load in parallel:
      const [round, route, legs, bookings, vessel, voyages] =
        await Promise.all([
          Round.findById(roundId).populate('vesselId serviceId').lean(),
          Route.findOne({ serviceId }).lean(),
          RouteLeg.find({ routeId }).populate('portId','name code')
                                    .sort({ sequence: 1 }).lean(),
          Booking.find({ voyageId in round.voyageIds,
                         isDeleted: false,
                         status in opts.statuses })
                 .select('quantity polId podId containerTypeId containerNumber status voyageId')
                 .populate('containerTypeId','code size isDeleted')
                 .lean(),
          Vessel.findById(round.vesselId).lean(),
          Voyage.find({ _id in round.voyageIds })
                .select('polId podId sequence status')
                .sort({ sequence: 1 }).lean()
        ]);

      NOTE: containerTypeId populate selects `size` only. No teuFactor field
      is read or referenced.

    Step B — Build port sequence map:
      portSeqByPortId = { [portId]: sequence, ... }  from legs

    Step C — Resolve TEU for each booking:
      For each booking:
        if !containerTypeId → warning MISSING_CONTAINER_TYPE, skip
        const size = booking.containerTypeId.size
        const { teu, matched } = resolveTEU(size)
        if !matched:
          warning MISSING_TEU_MAPPING (bookingId, containerTypeCode, size)
        if containerTypeId.isDeleted:
          warning DELETED_CONTAINER_TYPE (informational, proceed)
        booking.effectiveTEU = booking.quantity × teu

    Step D — Build event list:
      For each surviving booking:
        polSeq = portSeqByPortId[polId]
        podSeq = portSeqByPortId[podId]
        if polSeq == null → warning BOOKING_PORT_NOT_IN_ROUTE (POL), skip
        if podSeq == null → warning BOOKING_PORT_NOT_IN_ROUTE (POD), skip
        if polSeq >= podSeq → warning INVALID_DIRECTION, skip
        events.push({ atSeq: polSeq, delta: +effectiveTEU, kind:'load',      bookingId })
        events.push({ atSeq: podSeq, delta: -effectiveTEU, kind:'discharge', bookingId })

    Step E — Per-port aggregation:
      For each port in route.legs (ascending sequence):
        loadedTEU     = sum of load events at this seq
        dischargedTEU = sum of discharge events at this seq
        netChangeTEU  = loadedTEU - dischargedTEU
      Compute onboardAfterTEU as running total:
        running = 0
        for each port: running += netChange; port.onboardAfterTEU = running

    Step F — Per-segment aggregation:
      For each segment k = 1 … (legs.length - 1):
        fromPort = leg at sequence k
        toPort   = leg at sequence k+1
        onboardTEU = ports[k].onboardAfterTEU
        Find covering voyage: voyage where
          voyage.polId == fromPort.portId AND voyage.podId == toPort.portId
        If not found: isManualJump = true, voyageId = null
        remainingTEU = vessel.capacity ? vessel.capacity - onboardTEU : null
        utilisationPct = vessel.capacity
          ? round(onboardTEU / vessel.capacity × 100) : null
        loadedTEU     = fromPort.loadedTEU
        dischargedTEU = fromPort.dischargedTEU

        Overbooking check:
          if remainingTEU != null && remainingTEU < 0:
            warning SEGMENT_OVERBOOKED (segmentIndex, over=-remainingTEU)

    Step G — Totals:
      peakOnboardTEU     = max(segment.onboardTEU)
      peakSegmentIndex   = index at peak
      avgUtilisationPct  = mean of non-null segment.utilisationPct
      totalBookedTEU     = sum of surviving booking.effectiveTEU
      totalBookedUnits   = sum of surviving booking.quantity

    Step H — Return payload.

  COMPLEXITY:
    O(B + P + V) where B = bookings, P = ports, V = voyages.
    Bookings query is indexed by voyageId + isDeleted (Sprint 020).

  CACHING (Sprint 020 cache utility):
    Key: `capacity:round:${roundId}`
    TTL: 60 seconds
    Invalidation triggers (all additions to existing services):
      booking.service.js create()  → cache.del after save
      booking.service.js update()  → cache.del after save
      booking.service.js softDelete() → cache.del after save
      bookingImport.service.js saveImport() → cache.del for the affected round
      voyage.service.js update() (status change) → cache.del
      round.service.js update() → cache.del

    NOTE: containerType.service.js does NOT invalidate the capacity cache.
    TEU is a pure function of the size string, and existing bookings retain
    their size mapping. If the business ever changes the TEU rule (e.g.
    45ft → 2.25), the resolver code changes and a full server restart
    naturally clears in-memory cache.

================================================================================
  PHASE 4 — Optional Pre-flight Capacity Enforcement (FEATURE-FLAGGED)
  Estimate: 4h
  Env: ENABLE_CAPACITY_ENFORCEMENT  ∈ {unset, 'warn', 'strict'}
================================================================================

  MODE 'warn' (default when flag set):
    booking.service.js create() calls computeSegmentPreview() BEFORE save.
    If canFit === false, save proceeds AND response body contains
    capacityWarning: { bottleneckSegment, addedTEU, remainingAfterAdd }.
    Frontend BookingForm shows a yellow banner post-create.

  MODE 'strict':
    Same call, but if canFit === false → throw AppError(400, ...) with
    bottleneck details. Booking NOT created.

  UNSET: No pre-flight call. Zero overhead.

  IMPORT INTEGRATION:
    bookingImport.service.js previewImport() simulates cumulative TEU by
    grouping rows per (roundId) and running the events algorithm in-memory.
    Rows that would push a segment over capacity get:
      new _rowStatus 'overCapacity'
      new warning entry in _errors[]
    Row still previews as valid unless flag = 'strict'.

================================================================================
  6. PERFORMANCE CONSIDERATIONS
================================================================================

  Change from quantity to TEU:
    Adds a size lookup on containerTypeId (small doc populate) plus one
    resolveTEU() call and one multiplication per booking in memory. All
    negligible cost. resolveTEU is a pure function with no I/O.

  Worst realistic case per computeRoundCapacity call:
    - 10 route legs, ~20 voyages, 500 bookings per round
    - 5 parallel Mongo queries (all indexed)
    - O(B) in-memory pass
    - Estimated: < 100ms cold, < 5ms warm (cache hit)

  Vessel active capacity: 1 round → single computeRoundCapacity call.
    Cache TTL 60s → typical page view is a cache hit.

  Fleet dashboard: bounded by active-round count (typically < 20).
    Each call cache-warmed after first hit.

  No additional caching or optimisation required beyond Sprint 020
  conventions.

  Deliberately no cache invalidation on container type updates. Rationale:
  TEU is a pure function of the size string. Editing a ContainerType's size
  is not blocked at the model level today, but since size is a hard enum and
  bookings retain their containerTypeId reference, the engine picks up the
  new size on the next cache miss (within 60s TTL) automatically. If a hard
  business-rule change is ever made to the resolver code itself, a server
  restart naturally purges the cache.

  9. RISKS AND OPEN QUESTIONS

  R1  Should Pending bookings be included in default utilisation?
      Default: NO (Confirmed + Final Loading only).
      Reports page exposes a toggle to include Pending for what-if planning.

  R2  Route leg edits after bookings exist.
      Engine emits BOOKING_PORT_NOT_IN_ROUTE and excludes booking.
      No auto-repair. Ops must reconcile manually.

  R3  Future TEU rule change (e.g. 45ft = 2.25 TEU industry adoption).
      Single-file change to teuResolver.js. Server restart clears in-memory
      cache. No data migration required.

  R4  Unknown container sizes emerging in future.
      Length-based regex bucketing already handles '20*', '40*', '45*' by
      default. Truly non-numeric sizes need explicit resolver code change.
      Documented single extension point.

  R5  Multi-vessel rounds (deferred).
      Current schema is 1 vessel per round. Engine assumes it. Out of scope.
