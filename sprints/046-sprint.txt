# 1. WHAT THE CURRENT ARCHITECTURE ACTUALLY DOES (verified against source)

## 1.1 Status is already partly automatic, partly manual — two separate
## code paths, both in invoice.service.js

**A. Auto-derived (payment-driven) — `recalcInvoiceStatus(invoiceId)`**
  Called ONLY by `payment.service.js` after every payment create/void.
  Unconditionally overwrites `invoice.status` from `paidAmount` math:
    paidAmount <= 0              -> 'Issued' (or 'Overdue' if past dueDate)
    0 < paidAmount < totalAmount -> 'Partially Paid'
    paidAmount >= totalAmount    -> 'Paid'
  This is the ONLY place 'Partially Paid'/'Paid' are ever set.
  **THIS SPRINT DOES NOT TOUCH THIS FUNCTION AT ALL** (locked decision,
  §3 Q3 below) — it stays byte-for-byte as it is today.

**B. Manual (admin-driven) — `update()` + `validateManualTransition()`**
  On `PUT /invoices/:id`, `data.status` is checked against a hardcoded
  whitelist: `MANUAL_TRANSITIONS = { Draft: ['Issued','Cancelled'],
  Issued: ['Cancelled'] }`. Any other target is rejected with a 400.
  The whole `update()` function is ALSO hard-blocked at the top:
    if (invoice.paidAmount > 0) -> 400
    if (status is 'Paid' or 'Cancelled') -> 400
  So today, once a single payment has posted, or once status has
  auto-advanced to Paid/Cancelled, NOTHING on the invoice — including
  status — can be touched again, by anyone, at any permission level.

## 1.2 The frontend enforces the SAME restriction a second time
  `InvoiceForm.jsx#EditInvoiceForm`: `locked = status==='Paid' ||
  status==='Cancelled' || paidAmount>0` — the ENTIRE form is `disabled`
  when locked. `allowedNext` mirrors the backend's narrow whitelist for
  the status `<select>`'s options.
  `CreateInvoiceForm` has no status field at all — `create()` always
  writes `status: 'Draft'` server-side.

## 1.3 RBAC today
  `PUT /invoices/:id` requires only `rbac('invoices')` (defaults to the
  `update` action, from `methodToAction`). Any role with Invoices→Update
  permission — Finance Officer included, not just SuperAdmin — hits the
  exact same `update()` above. There is no existing action beyond the 8
  standard boolean fields on `permission.model.js#actionSchema`
  (create/read/update/delete/import/export/view/hidden), shared as ONE
  schema across every module. `import`/`export` (added Sprint019) are a
  precedent for exactly this: an extra boolean action, meaningful only
  for specific modules/routes, added to the same shared schema.
  One further pre-existing fact, not part of this sprint but relevant to
  the design below: `import`/`export` are NOT currently exposed as
  toggleable columns in `PermissionMatrix.jsx` (its `ACTIONS` array is
  only `['view','read','create','update','delete','hidden']`) — they can
  only be granted today by writing directly to the `Permission`
  collection. This sprint's new `override` action WILL be added to that
  visible `ACTIONS` array (see §4.4) specifically so it is actually
  grantable through the Roles UI, per your decision on Q1 — it does not
  fix the pre-existing `import`/`export` gap, which is out of scope.

# 2. LOCKED DECISIONS (your answers)

**Q1 — Who is "admin"?** → New granular permission. `invoices` gains an
  8th... no, a NEW action key on the shared `actionSchema`: `override`.
  A SuperAdmin can grant `Invoices → Override` to any role (e.g. Finance
  Officer) via the Roles/Permissions page, same mechanism as every other
  action. SuperAdmin itself always has it implicitly (role-identity
  bypass in `rbac.js` already short-circuits everything before any
  action check runs — no special-casing needed there).

**Q2 — Scope of the override?** → Entire invoice. When the requester has
  `invoices:override` (or is SuperAdmin), `update()`'s top-level lock
  (`paidAmount>0` / status Paid|Cancelled) is skipped ENTIRELY — dates,
  currency, notes, AND status all become editable again, not just status.

**Q3 — Does a later payment event overwrite the override?** → Yes,
  intentionally, by doing nothing. `recalcInvoiceStatus()` is not
  touched. An admin override is a point-in-time correction; if a payment
  is later created or voided on that invoice, the normal payment-driven
  math runs exactly as it does today and may recompute `status` again.
  No flag, no "sticky" override, no new field to track this.

**Q4 — Guardrails?** → None. Any of the 6 `INVOICE_STATUS` enum values
  can be forced with no extra business-rule validation, no required
  reason field, no mismatch warning badge. The existing fire-and-forget
  `AuditLog` (already diffs old vs. new on every `PUT`, per
  `auditLogger.js`) is the only trail — unchanged, nothing new to log.

# 4. IMPLEMENTATION SPEC

## 4.1 `permission.model.js`
```js
const actionSchema = new mongoose.Schema({
  create: { type: Boolean, default: false },
  read:   { type: Boolean, default: false },
  update: { type: Boolean, default: false },
  delete: { type: Boolean, default: false },
  import: { type: Boolean, default: false },
  export: { type: Boolean, default: false },
  view:   { type: Boolean, default: false },
  hidden: { type: Boolean, default: false },
  override: { type: Boolean, default: false }, // Sprint046: invoice-only, full manual override
}, { _id: false });
```
No migration needed: existing `Permission` documents simply lack the key
(read as `undefined`), and `can('invoices','override')` on the frontend
already treats anything strictly-not-`true` as false — same effective
default as a schema-level `false` for every already-seeded role.

## 4.2 `rbac.js` — add a companion permission-check helper
The existing `rbac(module, actionOverride)` middleware factory is
untouched. Alongside it, export one more function that performs the
identical cached lookup but returns a boolean instead of calling
`next()`/`forbidden()`, for use inside a controller (not as a route
gate):
```js
const hasPermission = async (req, module, action) => {
  if (req.user?.roleId?.isSystem) return true; // SuperAdmin
  const roleId = String(req.user?.roleId?._id || req.user?.roleId);
  const cacheKey = `perm:${roleId}:${module}`;
  let permission = cache.get(cacheKey);
  if (!permission) {
    permission = await Permission.findOne({ roleId, module }).lean();
    if (permission) cache.set(cacheKey, permission, PERM_TTL);
  }
  return !!permission?.actions?.[action];
};

module.exports = rbac;
module.exports.hasPermission = hasPermission;
```
(Function properties on the exported factory — every existing
`const rbac = require('.../rbac'); router.use(rbac('module'))` call site
is unaffected.)

## 4.3 `invoice.controller.js#update`
```js
const update = async (req, res, next) => {
  try {
    req.auditOldDoc = await invoiceService.getById(req.params.id);
    const canOverride = await rbac.hasPermission(req, 'invoices', 'override');
    return success(res, await invoiceService.update(req.params.id, req.body, req.user._id, canOverride), 'Invoice updated');
  } catch (err) { if (err.status) return error(res, err.message, err.status); next(err); }
};
```

## 4.4 `invoice.service.js#update`
```js
const update = async (id, data, updatedBy, canOverride = false) => {
  const invoice = await Invoice.findOne({ _id: id, isDeleted: false });
  if (!invoice) throw { status: 404, message: 'Invoice not found' };

  if (!canOverride) {
    if (invoice.paidAmount > 0) throw { status: 400, message: 'Invoices with recorded payments cannot be modified' };
    if (['Paid', 'Cancelled'].includes(invoice.status)) throw { status: 400, message: `${invoice.status} invoices cannot be modified` };
  }

  if (data.status && data.status !== invoice.status) {
    if (!canOverride) validateManualTransition(invoice.status, data.status);
    invoice.status = data.status;
  }

  // ...dates/currency/notes exactly as today, unconditionally reachable
  // now that the gate above already decided whether we got this far.
};
```
`validateManualTransition`/`MANUAL_TRANSITIONS` themselves are NOT
deleted — they still run, unchanged, for every non-override request.

## 4.5 `invoice.validation.js`
```js
const { INVOICE_STATUS } = require('../../config/constants');
...
body('status').optional().isIn(INVOICE_STATUS), // was isIn(['Issued','Cancelled'])
```

## 4.7 `InvoiceForm.jsx#EditInvoiceForm`

```jsx
  ? INVOICE_STATUS
```

When `canOverride && (item.status==='Paid'||'Cancelled'||paidAmount>0)`,
replace the existing amber "cannot be modified" banner with a distinct

# 6. ACCEPTANCE CRITERIA

- [ ] A role with no `invoices:override` sees IDENTICAL behavior to
      today: Draft-only creation, narrow Draft→Issued/Cancelled and
      Issued→Cancelled transitions, and a fully locked form once
      `paidAmount>0` or status is Paid/Cancelled.
- [ ] A role granted `invoices:override` (via Roles → Permissions, or by
      being SuperAdmin) can edit an invoice — including forcing `status`
      to ANY of the 6 enum values — even while `paidAmount>0` or status
      is currently Paid/Cancelled.
- [ ] Recording or voiding a payment afterward still runs
      `recalcInvoiceStatus()` exactly as before and may recompute/overwrite
      a manually-forced status — this is expected, not a bug.
- [ ] `PermissionMatrix.jsx` shows a working "Override" toggle for every
      module row; saving persists it exactly like every other action.
- [ ] A user with ordinary Invoices→Update but no Override still cannot
      reach any of the override behavior (403/400 exactly as today) —
      confirms override is additive, not a general relaxation.
