**Revision 2** — updated per the "Architecture Review Update" (7 business

**Revision 3** — updated per "Architecture Review — Final Revision

booking(s) a payment covers and how much goes to each, so every booking's

(REVISION 4) below; every section that referenced the proportional
formula has been updated accordingly. Nothing in this sprint has been
implemented — this document is the complete, approved design ready to
hand to implementation.

# INVESTIGATION 1 — Invoice Module (current state, verified)

`backend/src/modules/invoices/invoice.model.js`:
```js
bookingId: { type: ObjectId, ref: 'Booking', required: true }   // single, not array
amount:    { type: Number, required: true, min: 0 }             // one flat number
status:    { type: String, enum: INVOICE_STATUS, default: 'Draft' }
```
No `voyageId`, no `roundId`, no line items, no payment sub-documents. One
Invoice document = one Booking document, always.

`invoice.service.js`:
- `create()` accepts exactly one `bookingId`, checks the booking exists and
  is not Cancelled, auto-fills `agentId` from the booking.
- `STATUS_TRANSITIONS` is hard-coded: `Draft→[Issued,Cancelled]`,
  `Issued→[Paid,Overdue,Cancelled]`, `Overdue→[Paid,Cancelled]`. "Paid" is
  a value the user picks from a dropdown — nothing computes it.
- `update()` blocks all edits once `status === 'Paid'`. That is the entire
  payment lifecycle: unpaid, or fully paid, decided by hand.

`invoice.validation.js`: validates one `bookingId`, one `amount`, one
`currency` — no path exists at the transport layer for multiple bookings.

`frontend/src/modules/invoices/InvoiceForm.jsx`: one `<select>` populated
from `bookingsService.list({ limit: 200 })` — **every non-cancelled
booking system-wide**, not filtered by agent, by voyage, or by "already
invoiced." Selecting a booking auto-fills `amount` from `totalFreight`.
There is no multi-select anywhere in this form.

`frontend/src/modules/invoices/InvoiceList.jsx`: flat table — Invoice No,
Booking No, Agent, Invoice Date, Due Date, Amount, Status. No paid/balance
columns, because paid/balance do not exist as concepts yet.

### Findings

1. **Structural — an invoice cannot represent more than one booking.**
   Voyage and Round invoicing are not a missing UI screen; they are
   impossible under the current schema without a rewrite.
2. **Structural — no payment ledger exists anywhere in the codebase.**
   "Paid" is one manually-picked enum value. There is no record of when,
   how much, by what method, or by whom money moved.
3. **Data integrity — `invoiceSchema.index({ bookingId: 1 })` (line 26) is
   a plain, non-unique index.** Nothing in the schema or the service layer
   stops the same booking being attached to two different invoices today.
4. **Confirmed correct (no fix needed):** the Layer-1/Layer-2 separation
   rule already holds — `Invoice.bookingId` refs the `Booking` (Layer 2)
   model only; `ManualBooking` is never reachable through it. This works
   by construction (the ref path), not by an explicit guard. Sprint 033
   must preserve this by construction too — line items must only ever
   reference `Booking`, never `ManualBooking`.

# ROOT CAUSE ANALYSIS

The Invoice model was built for the simplest real scenario first (one
container, one bill) and that shape was never revisited as the booking
system grew a Round → Voyage → Booking hierarchy around it (Sprints
007–031). Every later sprint that touched money-adjacent code (Sprint
020's PDF export, Sprint 032's Vessel KPI unification) extended *booking*
and *capacity* to be Round/Voyage-aware, but nothing equivalent ever
happened to Invoice, because no sprint before this one asked the financial
question. This is a scope gap, not a regression in existing code.

# BUSINESS DECISIONS (Architecture Review Update — FINAL, govern everything below)

These 7 decisions were handed down after review of the first draft of this
sprint and supersede anything in the sections above that conflicts with
them. They are not proposals — they are the constraints the design below
was built to satisfy.

## Decision 1 — Invoice Eligibility
Invoices are created ONLY from Layer 2 Bookings whose status is **Final
Loading**. Only. `Confirmed` bookings are NOT invoiceable. `Pending`
bookings are NOT invoiceable. This replaces and closes the "Booking
eligibility status" open question from the first draft — it is no longer
a risk, it is decided. Every business rule, API, workflow, and acceptance
criterion below reflects Final-Loading-only eligibility.

## Decision 2 — Primary Goal
The primary goal of Sprint 033 is **not** "improve the Invoice module" in
isolation. The Invoice module (plus the new Payment ledger) is the
**financial engine**. Agent Details is the **primary consumer** of that
engine's output. Every backend aggregate this sprint introduces is
designed to answer a question Agent Details needs answered, not the other
way around.

## Decision 3 — Agent Details becomes the Agent Financial Account
Agent Details stops being an edit form and becomes the complete financial
and operational history of that agent — a financial account statement.
It must be able to answer, for that one agent: which Rounds they've
worked on, which Voyages they've participated in, which Final Loading
bookings belong to them, which of those bookings are invoiced vs. never
invoiced, which are fully paid / partially paid / unpaid, how much has
been paid, how much remains, and which invoices belong to which Round or
Voyage.

## Decision 4 — Navigation Inside Agent Details
Not a single dashboard screen. A tab strip, using the same pattern already
proven in `BookingList.jsx`'s Operational/Manual tabs:
**Overview · Financial Summary · Rounds · Voyages · Bookings · Invoices ·
Payments.** See AGENT ACCOUNT STATEMENT ARCHITECTURE below for what each
tab owns and how Rounds/Voyages/Bookings connect into one statement
(refined further by Revision 3, refinement 3).

## Decision 5 — Round and Voyage Drill-Down
A user must be able to browse Agent → Round → Voyages → Bookings →
Invoice/Payment status, e.g. Round R00014 → Voyage 1 → its bookings →
Paid/Partial/Remaining → Voyage 2 → its bookings → Paid/Remaining.
Financial information must always be traceable back to the actual Final
Loading bookings that produced it. See AGENT ACCOUNT STATEMENT
ARCHITECTURE below.

## Decision 6 — Booking Visibility in Invoice Composition
Whenever an invoice is created for a Voyage or a Round, the system must
display the included Final Loading bookings in a table, each row showing
at minimum: Booking Number, Container, Voyage, Round, Freight, Invoice
Status, Amount Paid, Remaining Amount. The user must always understand
why the total is what it is.

## Decision 7 — Financial Reporting
Invoice generation is one part of a broader requirement: operational
financial reporting per agent. Agent Details is the final destination
where a user understands the complete financial relationship with that
agent — not just a list of invoices.

Instruction carried through the whole design below: **keep the
architecture as simple as possible; do not redesign unrelated modules.**
Nothing in Rounds, Voyages, Capacity, or ManualBooking is touched by this
sprint beyond reading from them.

# PROPOSED ARCHITECTURE (Sprint 033 — for approval)

## Financial Workflow (revised per Decision 1)
```
Booking reaches status: Final Loading
  → eligible for invoicing (Confirmed and Pending are NEVER eligible)
  → Invoice created (Booking | Voyage | Round) — draws only from
    Final Loading bookings of one agent
  → Issued
  → Partially Paid  (0 < paid < total)
  → Paid            (paid >= total)
```
A booking becomes **invoiced** the moment it is attached to any
non-cancelled invoice, of any type, and is locked out of every other
invoice until that invoice is cancelled. Money only ever enters the system
through a `Payment` record — invoice status is *derived* from the sum of
its payments, never hand-set once payments exist. Because eligibility is
Final-Loading-only, a booking that is later auto-cancelled by the Sprint
031 reconciliation is by definition a booking that already passed through
Final Loading once — see EDGE CASES for what that means for an existing
invoice.

## Payment Workflow (revised per Revision 4 — explicit line-item allocation)
1. User opens an Issued/Partially Paid/Overdue invoice and records a
   payment against one or more of its specific line items (bookings) —
   not a single lump amount against the invoice as a whole. See PAYMENT
   ALLOCATION (REVISION 4) below for the exact shape.
2. For each allocation line `{ bookingId, amount }` the server rejects the
   payment if `amount > that booking's own remaining balance` (its line
   item's `freightAmount` minus whatever has already been allocated to it
   by other non-voided payments) — overpayment is now checked per booking,
   not just against the invoice total, enforced server-side.
3. The payment's own `amount` is simply the sum of its `allocations[]` —
   never entered separately, the same "derived from its parts" pattern
   Invoice itself already uses for `totalAmount` from `lineItems`. Server
   appends the `Payment` document, recalculates and persists
   `invoice.paidAmount` (sum of all its non-voided payments' `amount`),
   and derives `invoice.status`:
   ```
   paidAmount === 0        → Issued (or Overdue if past dueDate)
   0 < paidAmount < total   → Partially Paid
   paidAmount >= total      → Paid
   ```
4. A payment is never hard-deleted. Corrections void it
   (`isVoided, voidedAt, voidedBy, voidReason`) — same append-only spirit
   already used for TrackingHistory/AuditLog — and status recalculates
   excluding voided payments.

## Invoice Architecture (revised per Decision 1)
Invoice becomes a header-plus-line-items document, tagged with a type:

| Type    | Scope field | Line items come from |
|---------|-------------|------------------------|
| Booking | —           | exactly one Final Loading Booking, user-selected |
| Voyage  | `voyageId`  | selected subset of that agent's Final Loading Bookings on that voyage |
| Round   | `roundId`   | selected subset of that agent's Final Loading Bookings across every voyage in that round |

Every eligibility query in every mode carries `status: 'Final Loading'` as
a hard filter — not a default, not a user-adjustable option. An invoice is
always scoped to exactly one `agentId` — a Round invoice does not mix
agents, matching how Bookings themselves are already agent-scoped. Layer 1
(ManualBooking) remains structurally unreachable — line items only ever
reference `Booking`, and the eligible-bookings query never touches
`ManualBooking`, preserving Investigation 1 Finding 4.

## Booking–Invoice Ownership (Revision 3 — single source: `Invoice.lineItems`)
The first two drafts of this sprint proposed `Booking.invoiceId` as a
denormalized back-reference. That is now explicitly rejected: **the
Booking↔Invoice relationship is owned entirely by `Invoice.lineItems`.**
No field is added to `Booking` for this sprint. Reasons this is the better
call, not just a simplification:
- Bidirectional ownership means every mutation path (create, cancel,
  void, orphan) has two places to keep in sync instead of one — exactly
  the kind of two-sided state Investigation 1 Finding 3 already flagged
  as a source of drift (the current non-unique `bookingId` index).
- Keeping `Booking` itself completely unaware of invoicing leaves room for
  future financial workflows this sprint doesn't anticipate (e.g. a
  booking referenced by a superseded/cancelled invoice and then a
  replacement one) without ever touching the Booking schema again.

"Is this booking already invoiced?" is answered by a single query, always
from the Invoice side:
```js
Invoice.exists({
  'lineItems.bookingId': bookingId,
  isDeleted: false,
  status: { $ne: 'Cancelled' },
})
```
This requires a multikey index on `lineItems.bookingId` (see DATA MODEL
CHANGES) — one index, one direction of truth. Eligible-bookings queries
for Voyage/Round composition run the equivalent `$in` form once for the
whole candidate set, not once per booking.

Displayed booking payment state anywhere in the UI is derived the same
way: look up the (at most one) non-cancelled Invoice whose `lineItems`
contains that `bookingId`; if none exists → "Not Invoiced"; otherwise the
parent invoice's derived status (Issued / Partially Paid / Paid /
Overdue), read off that invoice — never off the booking.

**Concurrency, revisited for the array-owned model:** two users composing
a Voyage/Round invoice for overlapping bookings at the same time is
resolved with a MongoDB transaction (Mongoose session — already available
on this Atlas-backed stack, no new infrastructure) around each creation
path: (1) re-run the `'lineItems.bookingId': { $in: bookingIds }` check
inside the transaction, (2) abort if any selected booking is already
claimed by a non-cancelled invoice, (3) insert the new Invoice, all as one
atomic unit. This replaces the first draft's "recheck at write time"
description with a concrete, transaction-backed mechanism — still fully
one-sided (Invoice-owned), no lock field anywhere on Booking.

**Round is never stored on Booking** (confirmed by Sprint 030 — Round is
a UI-only selector on the booking forms). At invoice-creation time this
sprint captures Round (and Voyage, container, ports, shipper, consignee,
commodity) as a **snapshot inside the line item itself** — see INVOICE
LINE ITEM SNAPSHOT below — rather than deriving it live on every read.
Live drill-down views that are not looking at a specific invoice (the
Rounds/Voyages/Bookings statement levels, still browsing current
operational state) continue to derive Round the existing way, via
`Booking.voyageId.roundId` populate — no new field, no contradiction of
the existing rule.

# INVOICE LINE ITEM SNAPSHOT (Revision 3, refinement 2)

Each `lineItems[]` entry stores a financial/historical snapshot taken at
the moment a booking is added to an invoice — not just the two fields
(`bookingNumber`, `freightAmount`) the first two drafts carried. This is
what makes "historically correct even if the booking changes later"
actually true: every field an Invoice Detail page, PDF, or Agent Account
Statement ever needs to render is available on the line item itself, with
no live read of the current `Booking`/`Voyage`/`Round` documents required.

```
lineItems: [{
  bookingId        ObjectId ref Booking   — kept ONLY for drill-down links
                                            and orphan-flagging lookups;
                                            NOT the ownership mechanism
                                            (the array itself is)
  bookingNumber    String   — snapshot
  containerNumber  String   — snapshot
  voyageId         ObjectId ref Voyage    — snapshot link (for drill-down)
  voyageNumber     String   — snapshot label (e.g. "SVC-014-01")
  roundId          ObjectId ref Round     — snapshot link (for drill-down)
  roundNumber      String   — snapshot label (e.g. "R00014")
  polName          String   — snapshot (port of loading name)
  podName          String   — snapshot (port of discharge name)
  shipper          String   — snapshot
  consignee        String   — snapshot
  commodity        String   — snapshot
  freightAmount    Number   — snapshot of booking.totalFreight at the
                              moment it was added to this invoice
  orphaned         Boolean  default false
  orphanedAt       Date     default null
  orphanedReason   String   default null
}]
```

Once written, a line item's snapshot fields are never re-read from the
live Booking/Voyage/Round documents — only `bookingId`/`voyageId`/
`roundId` remain as reference links, used exclusively to (a) let a user
click through from an invoice line to the live booking/voyage/round, and
(b) let the orphan-detection step in `bookingImport.service.js` find the
right line item to flag. If the live booking's shipper, commodity, or
even its container number changes after invoicing, the invoice keeps
showing what was true when it was created — exactly the guarantee
requested.

# AGENT ACCOUNT STATEMENT ARCHITECTURE (Revision 3 — supersedes the prior
# "flat tab" framing of Decisions 3-5)

The Revision 2 draft described Agent Details as seven independent tabs
that each happened to filter the same payload. That undersold Decision
3/5's actual requirement and was refined by the "Final Revision Required"
review: Agent Details must read as **one connected statement**, where the
user follows a single path —
```
Agent → Round → Voyage → Final Loading Bookings → Invoice → Payments
```
— and at *every* step before drilling further, the page states that
level's own **Total Freight / Total Paid / Remaining Balance**. The tabs
from Decision 4 still exist (they are still the right navigational
container — `BookingList.jsx`'s tab-strip pattern is still reused, no new
UI convention invented), but three of them — Rounds, Voyages, Bookings —
now render as **one continuous, expandable statement** instead of three
independently-filtered flat lists, and Invoices/Payments are reachable
both as their own ledger tabs *and* inline at the bottom of whichever
booking or invoice the user is currently looking at.

## The statement, level by level

```
Agent  ─────────────────────────────────────────────────────────
  Financial Summary tab: Total Freight · Total Paid · Remaining Balance
  for the WHOLE agent — the statement's opening line.

  Round R00014  (Rounds tab row / statement section)
    Total Freight  $48,000   Total Paid  $30,000   Remaining  $18,000
    ▾ expand
      Voyage 1  (nested)
        Total Freight  $20,000  Total Paid  $20,000  Remaining  $0
        ▾ expand
          Booking BK-000104  · Container MSCU1234567 · Freight $8,000
            → Invoice INV-000031 (Round invoice, Issued)
                Paid $8,000 · Remaining $0            [Paid in full]
                ▾ Payments: 2026-04-02  $8,000  Bank Transfer
          Booking BK-000105  · Container MSCU1234568 · Freight $12,000
            → Invoice INV-000031 (same invoice — Round type)
                Paid $12,000 · Remaining $0
      Voyage 2  (nested)
        Total Freight  $28,000  Total Paid  $10,000  Remaining  $18,000
        ▾ expand
          Booking BK-000110 · Container MSCU1234570 · Freight $28,000
            → Invoice INV-000031 (same Round invoice)
                Paid $10,000 · Remaining $18,000        [Partially Paid]
                ▾ Payments: 2026-04-10  $10,000  Cheque
```

Every level's Total Freight/Paid/Remaining is a genuine rollup of the
level below it — a Round's numbers are the sum of its Voyages' numbers,
which are the sum of their Bookings' numbers — so the statement is
internally consistent top to bottom, not three separately-computed
figures that might drift apart.

## Rollup formulas (all Final Loading bookings only, per Decision 1)

- **Booking-level Total Freight** = that booking's `totalFreight` (live,
  from `Booking`, since this is describing current operational state, not
  a specific past invoice).
- **Booking-level Total Paid** — see PER-BOOKING PAYMENT ALLOCATION below
  (a booking's freight can be one line item inside a multi-booking
  invoice; per Revision 4 this is now an exact figure read directly off
  `Payment.allocations`, not an estimate — see PAYMENT ALLOCATION
  (REVISION 4) below).
- **Booking-level Remaining Balance** = Total Freight − Total Paid.
- **Voyage-level** Total Freight/Paid/Remaining = sum of its Final Loading
  bookings' figures (for this agent only).
- **Round-level** = sum of its Voyages' figures.
- **Agent-level (Financial Summary)** = sum of its Rounds' figures — this
  is the same "Total Revenue"/"Total Paid" pair from the KPI table below,
  just stated here as the top of the same rollup chain rather than a
  separately-computed aggregate.

This "Remaining Balance" (Freight − Paid, at every level, invoiced or
not) is deliberately a different number from the Financial Summary's
"Outstanding Balance" (Total Invoiced − Total Paid, defined further down)
— they answer different questions and both matter for Decision 7's
reporting goal: Remaining Balance tells the story "what does this agent
still owe us in total," Outstanding Balance tells the narrower story
"what's due on invoices we've already issued." Both are labeled distinctly
in the UI so they are never confused for one another.

## Per-Booking Payment Allocation — PAYMENT ALLOCATION (REVISION 4)

The Revision 3 draft computed a booking's paid amount as an *estimate* —
its proportional share of whatever was paid on the invoice as a whole.
That is now rejected: real agents pay specific bookings ("pay Booking A
only," "pay A + B, leave C," "one container today, another later"), not a
percentage of the invoice. `Payment` now carries the allocation
explicitly:

```
Payment.allocations: [{ bookingId, amount }]
```

Every allocation's `bookingId` must be one of the parent invoice's
`lineItems[].bookingId`; `Payment.amount` is simply
`sum(allocations[].amount)` — derived, never entered as a separate
number, the same "totals are always the sum of their parts" discipline
already used for `Invoice.totalAmount` from `lineItems`. A booking's paid
amount is then an **exact** read, not a formula over an estimate:

```
bookingPaidAmount = sum(Payment.allocations[].amount)
                    for every non-voided Payment on this invoice
                    where allocations[].bookingId === this booking
bookingRemaining  = lineItem.freightAmount − bookingPaidAmount
```

This removes estimation entirely: the Agent Account Statement, the
Bookings level, and Decision 6's invoice-composition table all read the
same exact figure, and recording a payment against Booking A never moves
the needle on Booking B or C sitting on the same invoice unless the user
explicitly allocated money to them too. See DATA MODEL CHANGES for the
full `Payment` schema and REQUIRED BACKEND CHANGES for the validation
rules (every allocation checked against its own booking's remaining
balance, not just the invoice's total).

## Simplicity choice (unchanged from Revision 2, restated)

One backend function, `agent.service.js#getAgentFinancialAccount(id)`,
still produces the entire nested tree in a single call — exactly the way
`vessel.service.js#getVesselStats` already produces the whole Vessel
Details payload in one call today. The frontend renders that one tree as
the expandable Round→Voyage→Booking statement described above; Invoices
and Payments remain separately paginated through their own existing/thin
endpoints. Rounds are bounded to the agent's most recent N (recommend
N=20, matching `getVesselStats`'s own precedent) to keep the payload
bounded for agents with a long history.

Each booking node in the tree carries the same live-operational fields as
before (`bookingNumber`, `containerNumber`, `voyageId`/`roundId` derived
via populate — this is the *live* view, distinct from a specific invoice's
frozen snapshot), plus a resolved `invoiceId` (or null) used only to look
up that booking's current invoice status/allocation for display.

## Agent Financial Account — KPI Definitions (Decision 2, 3, 7)

`agent.service.js#getAgentFinancialAccount(id)` (renamed from the first
draft's `getAgentStats` to reflect Decision 2 — this function IS the
financial engine's primary output, not a side statistic), following the
exact Promise.all-then-merge-in-JS pattern already proven in
`vessel.service.js#getVesselStats`:

| KPI | Definition |
|-----|------------|
| Total Revenue | sum(Booking.totalFreight) for this agent, status = Final Loading (Decision 1 — this is now the entire eligible universe, so Revenue and "eligible for invoicing" are the same population). Same number as the statement's agent-level "Total Freight." |
| Total Invoiced | sum(Invoice.totalAmount), non-cancelled invoices |
| Total Paid | sum(Payment.amount) across this agent's invoices, excluding voided payments |
| Outstanding Balance | Total Invoiced − Total Paid (invoiced-only view — narrower than the statement's Remaining Balance, see above) |
| Remaining Balance | Total Revenue − Total Paid (whole-relationship view, invoiced or not — the statement's top-line number) |
| Bookings Awaiting Invoice | count + sum(totalFreight) of Final Loading Bookings with no non-cancelled invoice referencing them |
| Bookings Awaiting Payment | Final Loading Bookings whose invoice status ∈ {Issued, Partially Paid, Overdue} |
| Bookings Fully Paid | Final Loading Bookings whose invoice status = Paid |
| Payment Progress | Total Paid / Total Invoiced |
| Rounds worked | the statement tree's top level — every Round containing at least one Voyage with a Final Loading booking for this agent, with its own Total Freight/Paid/Remaining rollup |
| Voyages participated | nested under each Round in the same tree, same rollup shape |
| Final Loading bookings | the tree's leaf level, per AGENT ACCOUNT STATEMENT ARCHITECTURE above |
| Invoice history | via existing `GET /invoices?agentId=` — number, type, scope label, total, paid, balance, status |
| Payment history | via new `GET /payments?agentId=` — date, invoice number, amount, method, reference |

## Payment — new collection (Revision 4 — explicit line-item allocation)
```
invoiceId    ObjectId ref Invoice, required, indexed
agentId      ObjectId ref Agent, required (denormalized for reporting)
allocations  [{ bookingId: ObjectId ref Booking, amount: Number, min 0.01 }]
             required, non-empty; every bookingId must appear in the
             parent invoice's lineItems — see PAYMENT ALLOCATION (REVISION 4)
amount       Number, required, min 0.01 — DERIVED as sum(allocations[].amount),
             stored (not virtual) purely so agent/invoice-level aggregates

             change (payments are otherwise immutable once created — see
             void flow below, not an edit flow)
paymentDate  Date, required

reference    String, trim, default null
notes        String, trim, default null
isVoided     Boolean, default false
voidedAt     Date, default null
voidedBy     ObjectId ref User, default null
voidReason   String, default null
createdBy    ObjectId ref User
```
A payment is created once with its full set of allocations and is never
edited afterward — only voided (as a whole; there is no partial-void of
one allocation within a payment, keeping this as simple as the "do not
over-engineer it" instruction asks for). If a user needs to correct one
allocation, they void the whole payment and record a new one — same
append-only spirit already used for TrackingHistory/AuditLog.

# UI FLOW

1. User clicks "+ New Invoice" → picks Invoice Type (Booking / Voyage /
   Round).
2. **Booking**: pick Agent, then one of that agent's Final Loading
   bookings (dropdown now filtered to `status: 'Final Loading'` — this is
   the one behavior change to the "unchanged from today" flow, required
   by Decision 1). Amount auto-fills.
3. **Voyage**: pick Agent, then Voyage (scoped to that agent's rounds,
   reusing the Round→Voyage cascading filter already built in Sprint 030)
   → eligible-bookings table loads (Final Loading only, not-yet-invoiced),
   pre-checked → user can uncheck any → running total shown.
4. **Round**: pick Agent, then Round → eligible-bookings table loads
   across every voyage in that round, grouped by voyage, each row showing
   which voyage and round it belongs to and whether a sibling booking on
   the same round was already paid on a prior invoice (Scenario E) →
   select/unselect → running total.
5. Submit → inside one transaction, the server re-verifies none of the
   selected bookings appear in another non-cancelled invoice's
   `lineItems`, snapshots each selected booking's current fields into its
   line item, and inserts the Draft invoice — all atomically, so a
   booking is locked the instant the invoice exists, even while Draft,
   with no separate field to set on the booking itself (see BOOKING–
   INVOICE OWNERSHIP).
6. On Invoice Detail: Issue it, then record payments via
   `InvoicePaymentPanel` — pick which specific line item(s) this payment
   covers and how much for each (pay one booking, several, or all; leave
   others untouched for later); balance and status update live, per
   booking and for the invoice as a whole.
7. From Agent Details, a user reaches the same information the opposite
   way, following the statement path (Decision 5): Financial Summary for
   the whole-agent headline numbers, then Round → Voyage → Final Loading
   Bookings, each level narrating its own Total Freight/Paid/Remaining
   before the user expands the next, then a booking's Invoice → Payments
   inline at the bottom (Decisions 3-5, 7).

# REQUIRED BUSINESS SCENARIOS — COVERAGE CHECK

All scenarios below now implicitly assume every referenced booking has
already reached **Final Loading** — per Decision 1, that is the only
status from which an invoice can ever be created.

**Scenario A** — One Booking → One Invoice → Paid. Works exactly as
today's flow, now restricted to Final Loading bookings and backed by a
real Payment record instead of a manual status flip.

**Scenario B** — One Voyage → One Invoice → 100% paid. Voyage invoice with
N Final Loading line items; single payment equal to `totalAmount` → Paid.

**Scenario C** — One Voyage → One Invoice → 40% then 60%. Voyage invoice,
total = X; payment of 0.4X → Partially Paid; payment of 0.6X → Paid.

**Scenario D** — One Round → One Invoice, multi-voyage → partial → final.
Round invoice with Final Loading bookings from every voyage in the round;
partial payment → Partially Paid; final payment → Paid.

**Scenario E** — Round invoice where some bookings are already paid from
previous invoices. Solved structurally: a booking already referenced in
`lineItems` of a different non-cancelled invoice never appears in another
invoice's eligible-bookings list (the `Invoice`-side query from BOOKING–
INVOICE OWNERSHIP), so there is no ambiguity to explain — it is already
accounted for elsewhere, traceable via that invoice, and also visible
directly in the Agent Account Statement's Bookings level without needing
to open an invoice at all (Decision 3/5).

**Scenario F** — Selectable table before generating the invoice. Delivered
by `EligibleBookingsTable.jsx` against
`GET /invoices/eligible-bookings` (UI FLOW steps 3–4), matching the exact
column set required by Decision 6.

# EDGE CASES

1. **Final Loading import auto-cancels a booking that's already
   invoiced.** Sprint 031's reconciliation cancels any booking in a
   Round/Agent scope not present in the manifest. Because Decision 1 means
   only Final Loading bookings are ever invoiced, this is now the single
   most important edge case in the sprint — every invoiced booking is, by
   definition, a Final Loading booking, i.e. exactly the population this
   reconciliation can cancel. If a booking that is orphaned this way still
   has a non-cancelled Invoice referencing it in `lineItems` and that
   invoice isn't fully paid, the invoice would silently overstate its
   total. Fix: the reconciliation step must locate that line item
   (`Invoice.findOneAndUpdate` with `arrayFilters` matching
   `lineItems.bookingId`) and set `orphaned: true` / `orphanedAt` /
   `orphanedReason` on it directly — there is no Booking-side field to
   clear (per BOOKING–INVOICE OWNERSHIP, ownership was never
   bidirectional) — surfaced as a warning badge on Invoice Detail AND on
   the Agent Account Statement's Bookings level, never silently left in
   the total unflagged.
2. **Overpayment.** Per Revision 4, this is now checked per allocation
   line, not just against the invoice total: any `allocations[].amount`
   greater than that specific booking's own remaining balance must be
   rejected server-side, not only validated client-side. Because every
   allocation is bounded this way, the invoice-level total can never
   exceed `invoice.totalAmount` either — the per-line check is sufficient
   on its own, with no separate aggregate check needed.
3. **Cancelling an invoice that already has payments.** Recommend
   extending the existing "Paid invoices cannot be deleted/modified" guard
   to: any invoice with `paidAmount > 0` cannot be cancelled. A
   refund/credit-note flow is explicitly out of scope for this sprint —
   flagged, not solved.
4. **Concurrency.** Two users composing a Voyage invoice for the same
   voyage at the same time could both select the same not-yet-locked
   booking. Resolved via the transaction described in BOOKING–INVOICE
   OWNERSHIP: the `'lineItems.bookingId': { $in: bookingIds }` check
   against non-cancelled invoices and the new invoice's insert happen
   inside one Mongoose session/transaction, so a booking claimed by
   another request between the eligible-bookings read and this request's
   submit is caught atomically at write time, not just at query time.
5. **A booking sits in Final Loading indefinitely without ever being
   invoiced.** Not a bug — Decision 1 makes this a valid, expected state
   (visible directly as "Bookings Awaiting Invoice" in the Financial
   Summary level of the statement). No status-transition change is
   implied by this sprint — Booking's own lifecycle
   (Pending→Confirmed→Final Loading→Cancelled) is untouched.
6. **Concurrent payments allocating to the same booking (Revision 4).**
   Two users recording separate payments against the same invoice at the
   same time could both allocate money to the same booking, together
   exceeding its remaining balance. `payment.service.create()` must
   re-read that booking's already-allocated, non-voided total inside a
   transaction immediately before inserting the new payment — the same
   pattern as the invoice-creation transaction in BOOKING–INVOICE
   OWNERSHIP, applied one level down at the allocation level.

# RISKS / OPEN DECISIONS (remaining after this revision)

Decision 1 above closed the "booking eligibility status" risk from the
first draft. Revision 4 closes the "per-booking payment allocation
method" risk from Revision 3 — explicit `allocations[]` is now the
approved design, proportional allocation is rejected. One item remains:

- **Currency consistency.** `Booking` has no currency field at all
  (removed from import in Sprint 026) — `totalFreight` is a bare number.
  Invoice currency is chosen independently at creation time. A Voyage/Round
  invoice spanning bookings agreed in different currencies would silently
  sum incompatible values. Pre-existing gap, not introduced by this
  sprint, but more visible once invoices routinely span many Final Loading
  bookings — needs a decision: assume one operating currency
  system-wide, or add a currency field to Booking.
- **Refunds/credit notes** are explicitly out of scope per Edge Case 3 —
  confirm that's acceptable for this sprint.

# MIGRATION STRATEGY

Follows the existing `backend/src/config/migrations/` convention (same
guarded, manually-run pattern as `migrate-dashboard-auditlogs.js` — never
auto-run from `server.js`).

```
// migrate-invoice-v2.js — one-time, idempotent
for each existing Invoice:
  const booking = await Booking.findById(invoice.bookingId).populate('voyageId')
  const voyage  = booking.voyageId
  const round   = await Round.findById(voyage.roundId)
  const [pol, pod] = await Port.find({ _id: { $in: [booking.polId, booking.podId] } })

  invoiceType = 'Booking'
  lineItems   = [{
    bookingId: booking._id,        bookingNumber: booking.bookingNumber,
    containerNumber: booking.containerNumber,
    voyageId: voyage._id,          voyageNumber: voyage.voyageNumber,
    roundId: round._id,            roundNumber: round.roundNumber,
    polName: pol.name,             podName: pod.name,
    shipper: booking.shipper,      consignee: booking.consignee,
    commodity: booking.commodity,  freightAmount: invoice.amount,
  }]
  totalAmount = invoice.amount
  paidAmount  = (invoice.status === 'Paid') ? totalAmount : 0

  if invoice.status === 'Paid':
    backfill one synthetic Payment {
      allocations: [{ bookingId: booking._id, amount: totalAmount }],  // Revision 4:
                                                                        // trivial here since
                                                                        // every pre-migration
                                                                        // invoice has exactly
                                                                        // one line item
      amount: totalAmount, paymentDate: invoice.updatedAt,
      method: 'Other', notes: 'Backfilled — pre-migration paid invoice',
    }
```
Note: because ownership is Invoice-side only (Revision 3), the migration
has nothing to backfill on `Booking` at all — no field is written back to
the Booking collection, which is simpler than the first two drafts'
migration (which also had to set `Booking.invoiceId`).

Every migrated line item gets a real historical snapshot at migration
time, taken from whatever the booking/voyage/round/ports actually were at
that moment — this is a one-time "as of migration" snapshot for
pre-existing invoices; going forward every new invoice's snapshot is taken
at the moment it's created (see INVOICE LINE ITEM SNAPSHOT).

Some existing invoices may reference a booking that was Confirmed (not
Final Loading) at the time it was invoiced, since Decision 1 is a new rule
going forward, not retroactive. The migration does not reject or alter
those historical invoices — it only backfills the new fields. Going
forward, `invoice.service.js` enforces Final-Loading-only at creation
time; pre-existing invoices are grandfathered as-is.

Run order: after the model changes deploy, before the new UI ships, so no
invoice is ever created under the old shape mid-migration. `npm run seed`
continues to work unmodified since it seeds fresh data directly under the
new schema.

# ACCEPTANCE CRITERIA

1. An invoice (Booking, Voyage, or Round type) can only ever be created
   from Bookings whose status is Final Loading — attempting to include a
   Pending or Confirmed booking is rejected server-side (Decision 1).
2. A Booking invoice behaves like today's flow from the user's point of
   view (minus Confirmed/Pending now being unselectable), now backed by a
   real Payment ledger.
3. A Voyage invoice can be created selecting a subset of one agent's
   Final Loading bookings on one voyage; totals match the sum of selected
   freight exactly.
4. A Round invoice can be created selecting a subset of one agent's
   Final Loading bookings across every voyage in the round.
5. A booking already attached to a non-cancelled invoice never appears in
   another invoice's eligible-bookings list.
6. A payment is recorded against one or more specific line items
   (bookings) with an explicit amount for each — never as a single lump
   sum against the invoice with no stated breakdown (Revision 4). A user
   can pay Booking A only, pay A + B and leave C, or pay one container
   today and another later, all on the same multi-booking invoice.
7. Recording a payment whose allocations sum to less than the invoice's
   full balance sets status to Partially Paid and never allows any
   booking's own remaining balance to go negative.
8. Recording payments whose allocations sum, in total, to the invoice's
   full remaining balance sets status to Paid automatically — no manual
   status edit required or possible.
9. Voiding a payment recalculates paid/balance/status correctly — at the
   invoice level and for every booking that payment had allocated money
   to — and the void is visible in payment history (never deleted).
10. Agent Details is a tab strip — Overview, Financial Summary, Rounds,
    Voyages, Bookings, Invoices, Payments (Decision 4) — not a single
    dashboard and not just the edit form.
11. Within Agent Details, Rounds/Voyages/Bookings read as one connected
    account statement, not three independent flat lists: a user can
    expand a Round to see its Voyages, expand a Voyage to see its Final
    Loading bookings, and expand a booking to see its Invoice and that
    invoice's Payments — and at every level, Total Freight / Total Paid /
    Remaining Balance is shown before the user drills further (Decision 5
    and the "Final Revision Required" review's refinement 3).
12. Whenever a Voyage or Round invoice is composed, the bookings table
    shown to the user includes Booking Number, Container, Voyage, Round,
    Freight, Invoice Status, Amount Paid, and Remaining Amount
    (Decision 6).
13. Agent Details' Financial Summary shows Total Revenue, Total Invoiced,
    Total Paid, Outstanding Balance, Remaining Balance, Bookings Awaiting
    Invoice, and Bookings Awaiting Payment, all scoped to Final Loading
    bookings only.
14. A Final-Loading-triggered booking cancellation on an already-invoiced,
    unpaid booking surfaces as an orphaned-line-item warning both on the
    parent invoice and in the Agent Account Statement's Bookings level —
    detected and flagged entirely from the Invoice side (no field is ever
    read or written on the Booking document for this).
15. Existing pre-migration invoices display correctly under the new schema
    with no data loss, including invoices originally created against a
    Confirmed (pre-Decision-1) booking — grandfathered, not rejected — and
    each migrated invoice's line item carries a real historical snapshot
    (container, voyage, round, ports, shipper, consignee, commodity), not
    just a booking number and an amount. A migrated, previously-Paid
    invoice's backfilled synthetic Payment carries a real `allocations[]`
    entry, not a lump `amount` with no breakdown.
16. `Booking.model.js` has no `invoiceId` field, and no other Booking-side
    field records invoicing state — confirmed by code review that
    ownership lives exclusively in `Invoice.lineItems` (Revision 3,
    refinement 1).
17. Two invoice-creation requests racing to claim the same booking cannot
    both succeed — the transaction described in BOOKING–INVOICE OWNERSHIP
    guarantees exactly one of them wins. Two payment-recording requests
    racing to allocate money to the same booking cannot together exceed
    its remaining balance — the equivalent transaction in
    `payment.service.create()` guarantees this (Edge Case 6).
18. A booking's displayed Paid/Remaining figure, wherever shown (statement,
    Bookings tab, invoice composition table), is an EXACT sum read
    directly from `Payment.allocations` for that booking — never an
    estimate or a formula over the invoice's aggregate paid amount
    (Revision 4) — and is internally consistent with its parent invoice's
    own `paidAmount`/`balanceAmount`.
19. No change to `capacity.service.js`, `teuResolver.js`,
    `manualBooking.model.js`, `rounds/*`, `voyages/*`, or any Sprint
    028/029/030/031 logic — confirmed by code review before merge.

# IMPLEMENTATION NOTES (as actually delivered)

All six phases were implemented in this pass. No deviations from the
approved architecture — every backend rule and frontend flow below
matches the design above exactly, with a few implementation-level notes
worth recording:

**Backend**
- `invoice.model.js`, `payment.model.js` — rewritten/created exactly per
  DATA MODEL CHANGES, including the `lineItems[]` snapshot schema, the
  `'lineItems.bookingId'` and `'allocations.bookingId'` multikey indexes,
  and the `balanceAmount` virtual on Invoice.
- `invoice.service.js` — `create()` runs the three invoice types through
  one shared path, wrapped in a Mongoose `session.withTransaction()` that
  re-checks `'lineItems.bookingId'` against non-cancelled invoices
  immediately before insert (BOOKING–INVOICE OWNERSHIP's concurrency
  guarantee). `recalcInvoiceStatus()` is the single place that ever
  derives Partially Paid/Paid/Overdue — `update()` can only move
  Draft→Issued→Cancelled manually, and is blocked entirely once
  `paidAmount > 0`.
- `payment.service.js` — `create()` validates every allocation's
  `bookingId` against the invoice's own `lineItems`, re-reads each
  booking's already-allocated total inside a transaction before
  accepting a new allocation (Edge Case 6), and calls
  `recalcInvoiceStatus()` in the same transaction. `voidPayment()` voids
  the whole payment only — no partial-void, as designed.
- `booking.service.js#softDelete` — the old `Invoice.exists({ bookingId
  })` guard was replaced with `Invoice.exists({ 'lineItems.bookingId',
  status: { $ne: 'Cancelled' } })` — no field was ever added to
  `Booking.model.js`.
- `bookingImport.service.js` — the Sprint 031 Final Loading reconciliation
  now runs an `Invoice.updateMany(... arrayFilters ...)` immediately after
  its cancellation sweep, flagging `lineItems.$[li].orphaned` on any
  non-cancelled invoice referencing a booking it just cancelled (Edge
  Case 1) — this was the one cross-module change outside the invoices/
  agents modules.
- `agent.service.js#getAgentFinancialAccount` — one function builds the
  whole Round→Voyage→Booking tree plus the agent-level KPI block in a
  single call, mirroring `vessel.service.js#getVesselStats`'s shape,
  bounded to the most recent 20 rounds.
- `export.service.js` (invoices case) and `invoicePdfGenerator.js` were
  both updated to read `totalAmount`/`paidAmount`/`balanceAmount` and
  iterate `lineItems[]` — the PDF now renders one row per invoiced
  booking entirely from each line item's own snapshot, never a live
  Booking read, and shows BALANCE DUE (not a static total) as the accent
  callout.
- `migrate-invoice-v2.js` — new, guarded by `require.main === module`,
  run manually via `npm run migrate:invoice-v2` (added to
  `backend/package.json`). Idempotent (`{ lineItems: { $exists: false }
  }` selector); writes nothing to `Booking`; backfills one synthetic
  `Payment` with a proper `allocations[]` entry for any previously-Paid
  legacy invoice.
