# Sprint 036 — Expense Module Port-Level Costing Evolution (extends Sprint 035)
Status: ✅ APPROVED (Revision 1) — approved with one required architecture
revision, applied below: the explicit `scope` field proposed in the
original draft is REMOVED. Scope is inferred from the existing
`roundId`/`voyageId`/`portId` relationship fields, never stored
separately, so an inconsistent state (e.g. `scope="Port"` with
`portId=null`) is structurally impossible rather than merely
validated-against. This document extends Sprint 035; it does not modify
or reopen anything Sprint 035 already delivered and shipped.

This sprint originates from business findings surfaced during manual
testing of Sprint 035, not from new unprompted scope. It builds directly
on `docs/expense-module-analysis.md` (already-established finding: the
Expense module's `port` field is free text, not a real relationship —
flagged there as a data-quality risk, now confirmed as a hard blocker by
the business) and on Sprint 035 itself (its `voyages[].voyageCost.byPort`
grouping, added in Phase 2, is the exact place this sprint's changes
land).

---

# SPRINT GOAL

Evolve the Expense module so an Expense can be scoped to exactly one of
**Round**, **Voyage**, or **Port-within-a-Voyage**, with Port always a
real reference to one of that voyage's own two ports (POL/POD) — not
free text — and extend the Sprint 035 Voyage Profitability Report so
Revenue-by-Voyage carries POL, POD, Total TEU, Total VGM, and Total
Revenue, with VGM mandatory.

---

# SCOPE

**In scope:** `Expense` model/service/validation/routes changes to add a
real Port scope; `ExpenseForm.jsx` 3-way cascading scope selector;
`RoundPnlReport.jsx`/`getRoundPnL` changes needed to consume the new
Port scope correctly and to add VGM to Revenue-by-Voyage; one migration
script for existing Expense documents.

**Out of scope:** everything already declared out of scope by Sprint 035
(Bunker Cost implementation, Expense lifecycle/approval/soft-delete/audit
work, multi-round time-series "rolling" view, currency conversion/FX);
retroactively resolving historical free-text `port` values into real
`portId` references (see RISKS — this is a one-way migration limitation,
not a gap this sprint closes); any change to `capacity.service.js`,
`teuResolver.js`, `booking.model.js`, `manualBooking.model.js`,
`invoice.model.js`, `payment.model.js`.

# PHASE 0 — BUSINESS VALIDATION

## EXPENSE PORT-SCOPE BUSINESS SPECIFICATION

1. **Revenue by Voyage — required fields (business-confirmed, Decision 1)**
   POL, POD, Total TEU, Total VGM (MT), Total Revenue. VGM is mandatory
   — it must never be omitted or shown as "—" when data exists.
   Confirmed against the schema: `Booking.vgm` (Layer 2) already exists
   and is already read by Sprint 034's `getBookingRevenueDetails`
   (`g.vgm += (b.vgm || 0)`), so this is a **read of an existing field**,
   not a new one. Sprint 035's `voyages[].revenue` block does not
   currently expose `polName`/`podName`/`vgm` inside itself (POL/POD
   currently live one level up, on the voyage row, not inside the
   `revenue` object) — this sprint adds `vgm` to that block and mirrors
   POL/POD into it so the Revenue-by-Voyage table is self-contained.

2. **The current Expense module cannot support Port-level costing
   (business-confirmed, Decision 2).**
   Confirmed root cause, per `docs/expense-module-analysis.md`:
   `Expense.port` is a plain free-text `String`, entered by hand, with no
   relationship to the `Port` collection and no validation that it
   matches anything real about the voyage it's attached to. Sprint 035
   Phase 2 already had to group `voyages[].voyageCost.byPort` on this
   raw string as a stopgap (documented there as reusing what exists,
   not inventing new behavior) — this is the exact spot that breaks
   down under real data (typos, inconsistent casing/abbreviations,
   "Jeddah" vs "JEDDAH" vs "Jed" never being recognized as the same
   port), which manual testing surfaced.

3. **Expense scope — exactly one of Round / Voyage / Port
   (business-confirmed, Decision 3).**
   This is a three-way exclusivity rule replacing the current two-way
   Round-XOR-Voyage rule (`docs/expense-module-analysis.md`,
   `expense.service.js#create/update`). Port scope is not a third
   independent field alongside Round/Voyage — it is a **refinement of
   Voyage scope**: a Port-scoped expense still belongs to exactly one
   Voyage, plus one of that voyage's own two ports.

4. **Round Expense — applies to the entire Round, selection: Round.**
   Unchanged from current behavior (`Expense.roundId` set, `voyageId`
   and the new `portId` both null).

5. **Voyage Expense — applies to the whole Voyage, selection: Round →
   Voyage.** Unchanged from current behavior (`Expense.voyageId` set,
   `roundId` and `portId` both null). The Round step in the selection UI
   is unchanged from today's `ExpenseForm.jsx` — it already exists purely
   to narrow the Voyage dropdown, is not itself stored, and requires no
   new work.

6. **Port Expense — applies only to a specific Port inside a Voyage,
   selection: Round → Voyage → Port. "The available Ports must be loaded
   from the selected Voyage" (business-confirmed, Decision 6).**
   Direct schema fact, confirmed by reading `voyage.model.js`: a Voyage
   is a **single leg** (Sprint 023 capacity-engine correction — "walks
   actual Voyage documents... one capacity row per voyage," no synthetic
   intermediate stops). Every `Voyage` document has exactly two ports:
   `polId` and `podId`. There is no third, intermediate port anywhere on
   a Voyage document today. Therefore "the available Ports... loaded
   from the selected Voyage" resolves, with the current schema, to
   **exactly the selected voyage's own POL and POD** — a 2-option
   dropdown, not an open port picker. This reconciles the illustrative
   3-port example in the business findings (Stevedoring/Jeddah,
   Pilotage/Aqaba, Port Charges/Alexandria "on Voyage 001") with the
   real data model: that example only makes sense if it describes THREE
   SEPARATE VOYAGES within the same Round (each contributing its own
   POL/POD), not three ports on one voyage document. Business Decision
   6 is implemented exactly as stated — "loaded from the selected
   voyage" — using the two ports that voyage actually has.

   **Reviewer note (applied):** this two-port constraint is a **current
   schema limitation**, not a permanent business rule — it exists only
   because `Voyage` today models a single leg with exactly `polId`/
   `podId`. It is not hardcoded as a rule anywhere in this sprint's
   design: `Expense.portId` validation checks "does this port belong to
   this voyage" generically (`portId ∈ {voyage's own ports}`), it does
   not assume the count is always two. If `Voyage` routing ever evolves
   to carry more than two ports (e.g. intermediate calls), the same
   validation shape extends without any change to the `Expense` model —
   only the source of "this voyage's ports" would need to widen from two
   fields to a list. This sprint does not build that generalization now
   (no such Voyage capability exists to generalize for — see OUT OF
   SCOPE item 7), it only avoids baking the number two into the
   architecture as a rule.

7. **A Voyage may contain both Voyage Expenses and Port Expenses
   (business-confirmed, Decision 7).** No new rule needed — this falls
   directly out of Decision 3/6: distinct Expense documents, one
   Voyage-scoped, others Port-scoped against either of that voyage's two
   ports, can coexist freely. No exclusivity is implied between them.

8. Reporting, migration, and backward-compatibility implications are
   covered under their own headings below (ARCHITECTURE DECISIONS,
   DATA MODEL DECISIONS, BACKEND TASKS).

9. Per the explicit instruction for this sprint: do not over-engineer,
   reuse the existing architecture wherever possible. Concretely this
   sprint deliberately does NOT: add a new `Port` picker endpoint (the
   two ports are already present, populated, on the Voyage document the
   frontend already fetches — see ADR-3); add a `scope` concept to any
   model other than `Expense`; touch the Voyage or Round schema at all.

## BUSINESS QUESTIONS REQUIRING CONFIRMATION

1. **Historical free-text `port` values.** Existing Expense documents
   have a free-text `port` string with no reliable way to auto-match it
   to a real `Port` document (see Decision 2's own root-cause finding —
   the whole reason this sprint exists is that the string can't be
   trusted). Confirm: should historical records simply keep their old
   free-text `port` value forever (read-only, excluded from the new
   `portId`-based per-port grouping, shown in a legacy/"Unspecified"
   bucket), or does the business want a one-time manual cleanup pass
   after this sprint ships? This sprint's default (see RISKS/Migration
   Strategy) is the former — no forced backfill, since guessing wrong
   would misattribute real cost to the wrong port.

2. **Editing an existing Voyage-scoped Expense to Port scope.** If a
   user changes an existing Voyage Expense to Port scope after the fact,
   should the system require they now also pick one of that voyage's two
   ports (blocking save until they do), or silently leave it in Voyage
   scope until they explicitly complete the Port selection? Default
   assumed here: block save (same "explicit, not silent" pattern already
   used by the existing Round-XOR-Voyage validation).

3. **VGM unit consistency.** Decision 1 states VGM in MT (metric tons).
   Confirm `Booking.vgm` is already stored in MT (Sprint 034's report
   sums it with no unit conversion) — if the underlying data entry is
   inconsistent, that is a data-quality issue outside this sprint's
   Expense-evolution scope, not a report bug.

# ARCHITECTURE DECISIONS (ADR)
# ═══════════════════════════════════════════════════════════════════

**ADR-1 — Port scope is a refinement of Voyage scope, not a fourth
independent axis.**
A Port-scoped Expense always has `voyageId` set (to the voyage the port
belongs to) AND `portId` set (to one of that voyage's own `polId`/
`podId`). This mirrors the sprint's own stated selection path (Round →
Voyage → Port) and lets every existing "voyage-scoped expenses" query in
the codebase (Sprint 035 Phase 2's `Expense.find({voyageId:{$in:...}})`)
keep working unchanged — Port-scoped expenses are automatically included
in "this voyage's expenses" without any extra `$or` clause, since they
carry `voyageId` too.

**ADR-2 — Scope is ALWAYS inferred from `roundId`/`voyageId`/`portId`,
never stored as a separate field. (Revised per review — supersedes the
original draft's proposed explicit `scope` enum.)**
The original draft proposed a stored `scope` enum for the same reason
Sprint 034 Decision 3 centralized a status/Cancelled rule — to avoid the
same rule being re-derived in two places and drifting. Review correctly
identified a sharper problem with doing that *here*: a stored `scope`
field alongside the relationship fields it's supposed to summarize opens
a NEW inconsistency class the codebase doesn't have today —
`scope="Port"` with `portId=null`, or `scope="Voyage"` with a stray
`portId` — states that are impossible to prevent structurally and can
only be caught by remembering to keep two representations in sync on
every write path. The relationship fields (`roundId`/`voyageId`/
`portId`) are already the complete, minimal, unambiguous description of
where an expense belongs; a parallel `scope` field would duplicate that
information rather than centralize a rule. The one, single-owner
inference is instead a small pure function reused everywhere scope needs
to be known:

```js
// backend/src/modules/expenses/expense.service.js
const deriveScope = ({ roundId, voyageId, portId }) => {
  if (portId)  return 'Port';   // implies voyageId also set (enforced at write time)
  if (voyageId) return 'Voyage';
  if (roundId)  return 'Round';
  return null; // unreachable post-validation; see VALIDATION RULES
};
```

This single function is the one place "how do I know an expense's
scope" is answered — called by `reports.service.js` (per-port grouping),
by the API response mapping (so the frontend never re-implements the
inference), and by `ExpenseList.jsx`'s Scope badge. It reads the
relationship fields; it never writes a competing summary of them.

**ADR-3 — No new backend endpoint for "ports of a voyage."**
Confirmed by reading `voyage.service.js`: every voyage list/get query
already does `.populate('polId', 'name code').populate('podId', 'name
code')`. `ExpenseForm.jsx`'s existing Voyage dropdown, once a voyage is
selected, already has that voyage's full populated document available
(same data source `BookingForm.jsx`/`RoundPnlReport.jsx` already use).
The Port dropdown is built **client-side** from the selected voyage's
own `polId`/`podId` — no new API route. (Reusing
`GET /bookings/voyage-ports/:voyageId` was considered and rejected: it
is gated by `rbac('bookings')`, and Finance Officer — the role that
actually manages Expenses — has no `bookings` permission per the RBAC
table in claude.md; introducing a cross-module RBAC dependency to reuse
one endpoint is a worse trade than reading two already-populated fields
client-side.)

**ADR-4 — `Expense.port` (free-text) is kept, unmodified, as a
legacy-only field; `Expense.portId` (ref `Port`) is the new
source of truth going forward.**
No forced migration of historical strings into `portId` (see Business
Question 1 / RISKS). New Port-scoped expenses populate `portId` only —
the legacy `port` string field is no longer written by the Port-scope
flow (it remains available for Round/Voyage-scoped historical records
that had it filled in, purely for display, exactly as before).

**ADR-5 — `reports.service.js#getRoundPnL`'s Voyage Cost per-port
breakdown regroups on `portId`, with a `port` (free-text) fallback
bucket for records that have neither `portId` nor Port scope.**
Extends Sprint 035 Phase 2's `voyageCostByVoyage.byPort` map (currently
keyed on the raw `e.port` string) to key on `portId` when present,
falling back to the existing `'Unspecified'` bucket otherwise — additive
change to an internal grouping key only, the `voyages[].voyageCost`
response shape gains fields (`portId`, `portName`), it does not remove
the existing `port` string field from that payload.

# BUSINESS DECISIONS

1. Revenue by Voyage row = POL + POD + Total TEU + Total VGM (MT) +
   Total Revenue. VGM is mandatory (never silently omitted).
2. Expense scope is exactly one of Round / Voyage / Port.
3. Port scope is only reachable through Round → Voyage → Port, and the
   Port options are always exactly the selected voyage's own POL and POD
   — never a free port picker.
4. A voyage may simultaneously have Voyage-scoped and Port-scoped
   expenses; no exclusivity between them.
5. Historical free-text `port` values are not auto-converted to
   `portId` — kept read-only/legacy (see Business Question 1; default
   assumed unless the business says otherwise).

# DATA MODEL DECISIONS

**`Expense` model — ONE additive field only (`expense.model.js`), no
`scope` field (removed per review):**

```js
portId:  { type: mongoose.Schema.Types.ObjectId, ref: 'Port', default: null },
// existing fields unchanged:
roundId, voyageId, port (free-text, kept, legacy-only going forward)
```

Scope is inferred, never stored (ADR-2):
- Round Expense  → `roundId` set, `voyageId` null, `portId` null.
- Voyage Expense → `voyageId` set, `roundId` null, `portId` null.
- Port Expense   → `voyageId` set AND `portId` set, `roundId` null.
- New index: `expenseSchema.index({ voyageId: 1, portId: 1 })` — mirrors
  the existing `{voyageId:1}` index pattern, supports the new per-port
  report grouping without a collection scan.
- No change to `Round`, `Voyage`, `Port`, `ExpenseType`, or
  `ExpenseCategory` models. `ExpenseCategory.costClassification`
  (Sprint 035 Phase 1) is untouched and continues to work identically
  for Port-scoped expenses — classification is per-category, not
  per-scope, so nothing about Sprint 035's Voyage Cost / Other Voyage
  Cost distinction changes.

**Backward compatibility:** `portId` is a new, optional
(`default: null`), additive field. Every existing `Expense` document
already satisfies exactly one of the Round/Voyage inference rules above
(the current Round-XOR-Voyage rule already guarantees this), and
`portId` defaults to `null` for all of them — so every pre-Sprint-036
document is automatically and correctly read as `'Round'` or `'Voyage'`
scope with zero data migration required. **No migration script is
needed for this sprint** (a change from the original draft, which
proposed one solely to backfill the now-removed `scope` field).

# VALIDATION RULES

No `scope` input exists to validate (ADR-2) — the rules below apply
directly to whichever of `roundId`/`voyageId`/`portId` are present in
the request:

- Exactly one of the three inferred scopes must result: `roundId` only,
  `voyageId` only, or `voyageId`+`portId`. Any other combination
  (nothing set; `roundId` together with `voyageId`; `portId` without
  `voyageId`; `roundId` together with `portId`) is rejected with 400.
- `portId` present ⇒ `voyageId` required; `roundId` forced null;
  `portId` must equal that voyage's own `polId` or `podId`
  (server-enforced, 400 otherwise — Decision 6, current schema
  limitation noted above).
- `voyageId` present without `portId` ⇒ `roundId` forced null.
- `roundId` present without `voyageId`/`portId` ⇒ valid as today.
- `update()` re-runs the full check above against whichever of the
  three ID fields are present in the update payload after applying it,
  not the document's prior state (matches Business Question 2's default
  assumption — block an inconsistent result, don't silently leave it).
- All pre-existing validators (`amount` ≥ 0, `currency` required,
  `expenseDate` ISO 8601, optional `agentId`) unchanged.

# ACCEPTANCE CRITERIA

1. Creating a Round-scoped expense behaves identically to today (scope
   is inferred from `roundId` alone, exactly as it already implicitly
   is; no stored field, no behavior change).
2. Creating a Voyage-scoped expense behaves identically to today.
3. Creating a Port-scoped expense requires Round → Voyage → Port
   selection; the Port dropdown shows exactly the selected voyage's own
   two ports; submitting without a port is blocked client- and
   server-side.
4. Submitting a `portId` that does not belong to the selected voyage is
   rejected with a 400.
5. A single voyage can hold both a Voyage-scoped expense (e.g. Hire
   Rate) and multiple Port-scoped expenses (e.g. Stevedoring at its POD)
   simultaneously — verified via Sprint 035's Voyage Cost per-voyage
   table showing both contributing to the same voyage's total.
6. `GET /reports/round-pnl` (round or voyage scope) — Voyage Cost
   per-port breakdown groups Port-scoped expenses correctly by real
   port, distinct from the legacy free-text `'Unspecified'` bucket.
7. `GET /reports/round-pnl` — Revenue-by-Voyage always includes POL,
   POD, Total TEU, Total VGM, Total Revenue for every voyage row; VGM is
   never blank when underlying `Booking.vgm` data exists.
8. Every pre-Sprint-036 Expense document is correctly read as `'Round'`
   or `'Voyage'` scope by `deriveScope()` with zero migration and zero
   change to `roundId`/`voyageId`/`amount`/etc.
9. Existing Round P&L / Voyage Profitability output for data that
   predates this sprint (no `portId` anywhere) is unchanged in every
   field Sprint 035 already produced, except the new additive fields.
10. No change in behavior for `capacity.service.js`, `teuResolver.js`,
    Invoice/Payment flows, or any Sprint ≤ 034 report.

# RISKS

1. **Historical free-text `port` values remain permanently
   unreconciled with real `Port` documents** (Business Question 1). Any
   pre-Sprint-036 expense with a `port` string stays in the legacy
   fallback bucket forever unless someone manually re-enters it as a
   proper Port-scoped expense. This is a real, accepted data-quality gap
   in the migrated dataset, not a bug in this sprint.
2. **Voyage-scoped Hire Rate expenses could be miscategorized as
   Port-scoped by a user who doesn't understand the distinction** —
   mitigated by the UI only offering Port scope as an explicit third
   choice (not the default) and by the fact that Voyage Cost vs Other
   Voyage Cost classification (Sprint 035) already runs off
   `ExpenseCategory.costClassification`, independent of scope, so a
   miscategorized scope does not silently corrupt the Voyage Cost /
   Other Voyage Cost split — only the per-port breakdown's granularity.
3. **A Voyage's POL and POD could theoretically be edited after
   Port-scoped expenses already reference them via `portId`.** Confirmed
   out of scope by cross-checking Sprint 030: POL/POD are already
   immutable post-creation on both Booking layers, and nothing in the
   current codebase allows editing a Voyage's own `polId`/`podId` after
   creation either — so this risk is theoretical under the current
   system, not exploitable today.
4. **(Superseded by the removal of the `scope` field.)** With scope no
   longer stored, there is no backfill/migration timing risk at all —
   `deriveScope()` reads `roundId`/`voyageId`/`portId` directly and
   produces a correct answer for every document, old or new, the moment
   this sprint ships. `reports.service.js`'s per-port grouping already
   falls back to the legacy `port` string when `portId` is absent, which
   covers older records without any extra code.
5. **VGM data completeness** — Total VGM is only as good as
   `Booking.vgm` entry discipline (Business Question 3); this sprint
   surfaces the aggregate honestly (summing whatever is there, including
   zeros for unset values) rather than inventing a placeholder or
   estimate.

   out-of-scope item, unaffected here).

   two-port-per-voyage constraint is a **current schema limitation**
   (Voyage models a single leg — Sprint 023), not a business rule this
   sprint asserts or depends on; see Business Validation section 6's
   "Reviewer note" for why the `Expense.portId` validation is already
   written generically enough not to need changes if this ever expands.
