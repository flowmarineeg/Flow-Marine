================================================================================
SPRINT 016 — MANUAL VOYAGE CONTROL IN ROUND DETAIL
================================================================================

STATUS: ⏳ Pending
GOAL:
  Give users full control over voyages within a round.
  The auto-generation stays as-is (leg1→2, leg2→3...) but users can
  ALSO manually add custom voyages (leg1→leg3, leg4→leg6, etc.).
  Users can control all voyage fields including the new ETP field.
  Users can also delete any system-generated OR manually-added voyage
  from the round detail tab.

================================================================================
PROBLEM STATEMENT
================================================================================

CURRENT BEHAVIOUR:
  When a round is created, voyages are auto-generated as consecutive leg pairs:
    Route: [A, B, C, D, E]
    Voyages: A→B, B→C, C→D, D→E  (always leg[i] to leg[i+1])

REQUESTED CHANGE:
  Sometimes the business needs non-consecutive legs as a single voyage:
    - Leg 1 → Leg 3 (skipping Leg 2 as a direct voyage)
    - Leg 4 → Leg 6 (grouping 3 legs into one voyage)
    - Leg 1 → Leg 6 (the whole route as a single voyage)

  The user must be able to:
  1. View auto-generated voyages in the round detail tab (unchanged)
  2. Add new custom voyages manually: choose any POL from route legs
     and any POD from route legs (POL ≠ POD, both must be in the route)
  3. Set all voyage fields on create: ETD, ETA, ATD, ATA, ETP, Status, Voyage Code
  4. Delete any voyage from the round (soft delete guarded if bookings exist)
  5. Edit existing voyages (already exists — unchanged)

================================================================================
CHANGES SUMMARY (what changes vs what stays)
================================================================================

STAYS UNCHANGED:
  - Auto-generation on Round.create (leg[i]→leg[i+1] consecutive pairs)
  - Existing VoyageEditForm (edit ETD/ETA/ATD/ATA/status)
  - All voyage status transition rules
  - bookingImport (uses voyageId, unaffected)
  - Global /voyages list page (unaffected)
  - Round creation flow (unaffected)

NEW CAPABILITIES:
  Backend:
    A. New field `etp` on voyage.model.js (Estimated Time of Port — or passage)
    B. New field `voyageCode` on voyage.model.js (user-defined code, optional, free text)
    C. New service function: createManualVoyage(roundId, data, userId)
    D. New service function: deleteVoyage(id, userId)
    E. New validation: validateCreate for manual voyage
    F. New routes: POST /voyages (manual create) + DELETE /voyages/:id
    G. Update validateUpdate to include etp, voyageCode

  Frontend:
    A. RoundVoyageList: Add "+ Add Voyage" button in header
    B. New VoyageAddForm modal: full form for manual voyage creation
    C. RoundVoyageList: Add delete button per row (guarded: has bookings?)
    D. VoyageEditForm: Add ETP + VoyageCode fields
    E. RoundDetail: update subtitle from "Auto-generated" to reflect both modes
    F. RoundVoyageList: visual distinction between auto-generated and manual voyages

A2. voyage.service.js — Add createManualVoyage + deleteVoyage
────────────────────────────────────────────────────────────────────────────────

FUNCTION: createManualVoyage(roundId, data, createdBy)
  Validates:
    1. Round exists, not deleted, not Cancelled or Completed
    2. polId and podId are Port documents that exist
    3. polId ≠ podId
    4. polId and podId both exist as portId values in the round's route legs
       (validate via: Route→RouteLeg lookup for that service)
       {We allow any port from the route, not just consecutive ones}
    5. voyageNumber uniqueness if user provides voyageCode
  
  Generates voyageNumber:
    Same format as auto-gen: {serviceCode}-{roundNumber}-{seq:02}
    seq = current highest voyage sequence in this round + 1
  
  Creates Voyage with:
    voyageNumber, roundId, serviceId (from round), polId, podId,
    sequence (next available), etd, eta, atd, ata, etp, status,
    voyageCode, isManual: true, createdBy

  Updates Round.voyageIds: push new voyage._id

  Returns: created voyage (fully populated)

FUNCTION: deleteVoyage(id, deletedBy)
  Validates:
    1. Voyage exists
    2. No active bookings on this voyage
       Booking.exists({ voyageId: id, isDeleted: false, status: {$ne:'Cancelled'} })
       → if found: throw 400 "Cannot delete — voyage has active bookings"
    3. (No other guards — both manual and auto-generated voyages can be deleted)
  
  Action:
    - Remove voyage from Round.voyageIds array ($pull)
    - Delete voyage: Voyage.findByIdAndDelete(id) [hard delete — voyages have no isDeleted]
  
  Note: Hard delete is appropriate because:
    - Voyages have no isDeleted field (they were never deletable before)
    - Cancelled bookings are OK to leave (booking has voyageId but it's historical)
    - We check for NON-cancelled bookings specifically

UPDATE: update() function
  Extend allowed fields list: add 'etp', 'voyageCode'
  Both are optional, nullable

DATA DESIGN NOTES
================================================================================

WHY NOT ADD isDeleted TO VOYAGE?
  Voyages never had isDeleted. Adding it now would require updating all existing
  queries that filter by isDeleted. Instead, use hard delete but ONLY after
  checking for active bookings.

WHY ALLOW DELETING AUTO-GENERATED VOYAGES?
  Business need: sometimes the auto-generation creates voyages the user doesn't
  need (e.g. they want leg1→leg3 as a single voyage instead of leg1→leg2 + leg2→leg3).
  They should be able to delete the auto-generated ones and add their custom ones.

WHY NOT VALIDATE PORT IS IN ROUTE FOR MANUAL VOYAGE?
  We DO validate this. The frontend POL/POD dropdowns are pre-filtered to route
  leg ports only. The backend also validates:
    RouteLeg.exists({ routeId, portId: polId }) and same for podId.
  This prevents completely arbitrary ports being used.

SEQUENCE NUMBER ON MANUAL VOYAGES:
  Auto-generated: sequence = index (1, 2, 3...)
  Manual: sequence = max(existing sequences) + 1
  Sequence is just for ordering in the table, not enforced uniquely.
