                        Needed because Sprint 051 commission reads these agreements.
 E4  Agent SOA          GET /agent-accounts/:id/soa - a QUERY over journal lines (accounts 1100/1110/2000),
                        no duplicate table. Running balance, closing position, ageing buckets 0-30/31-60/
                        61-90/90+ by days past due date. Positive = agent owes us.
 E5  Netting            POST /agent-accounts/:id/offset {batchId, strategy: oldest|sameRound, roundId?}.
                        Applies what we owe the agent (2000) to their open V2 invoices as 'Offset'
                        settlements: DR 2000 / CR 1100, through the same atomic over-payment guard as cash.
                        batchId is unique: pressing twice returns the first result, applies nothing new.
                        POST .../offset/:batchId/reverse voids every settlement of the batch. Direct Line
                        agents are refused (DIRECT_LINE_NO_OFFSET).
 E6  Pay agent          POST .../pay (DR 2000 / CR bank; refused above what we owe), plus advances
                        (DR 1110 / CR bank) and advance returns (DR bank / CR 1110).
 E7  Handling charges   GET .../handling/preview?roundId then POST .../handling/confirm. Built from the
                        agent's Final Loading bookings in the round (Load move, Full/Empty from the booking)
                        and Discharged ones (Discharge move), priced from the active agreement. Idempotent
                        per (booking, move) via a unique index. One ledger entry DR 5300 / CR 2000.
                        Unpriced moves (no fee, or no Full/Empty on the booking) are listed, not guessed.
 E8  Final settlement   GET/POST .../statement?roundId, then agree, then settle. Lines are derived from the
                        ledger for that agent + round (Invoices, Advances, Receipts, Port costs, Handling,
                        Commission, Paid/offset) so net = the closing position. Settle runs a sameRound
                        offset (batch id stmt-<id>) and stores the residual cash still to move.
                        The OGA example (120,000 + 10,000 - 40,000 - 8,400 - 3,000) = 78,600 = 7,860,000
                        minor units is an automated test (from a fee table and from raw ledger lines).
 E9  Frontend           Agent page: AgentV2Panel (Statement of Account, Agreements, Round Settlement,
                        Cash & Netting), Accounting profile on the agent form, Expense form (kind, paid by,
                        partner), Expenses list (PDA/FDA badge, To FDA / Post / Reverse). Permission matrix
                        gained approve and offset columns.

NOT DONE / ASSUMPTIONS TO CONFIRM
 - Handling charges are computed for the agent on the BOOKING (booking.agentId). In reality the handling is
   done by the PORT agent at the load/discharge port. The plan (D3-A) says per agent over their bookings, so
   that is what is built; if port agents differ from booking agents this needs an agent-per-port mapping.
 - Advances use account 1110 Agent Advances, not 1300 PDA Prepaid (the PDA estimate itself posts nothing).
 - Pay Agent's "not above payable" check is not atomic against a concurrent payment (a ledger read, not a
   single conditional update like the invoice guard). Low risk with manual entry; worth hardening later.
 - Offset 'oldest' pays only same-currency invoices (default USD); no cross-currency netting.
 - Handling charges cannot be reversed from the UI yet; credit/debit notes still cannot be cancelled.
 - Agent Financial Account (V1 tab) still reads legacy payments; the SOA tab is the ledger view.
 - Agent receivable/payable account overrides are stored but ignored (all agents use 1100/2000).
 - Agent SOA report page with Excel/PDF export (S6 in 053) is not built; the data is the SOA endpoint.
