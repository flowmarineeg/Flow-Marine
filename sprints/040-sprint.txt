# Sprint 040 — Bulk Export Module Audit & Update Plan
Status: 🟡 PLANNING (Revision 2 — corrected scope) — awaiting
architecture approval. NO CODE WAS WRITTEN OR MODIFIED.

**Revision 2 note:** Revision 1 of this document misread the sprint's
intent as "design new Report-based exports" (Revenue Export, Voyage
Performance Export, Round Capacity Export, Voyage Profitability Export,
Agent Financial Export, Dashboard Export). That entire direction is
explicitly withdrawn and superseded by this revision. Sprint 040 is
**only** an audit of the existing, already-shipped Export tab (the Bulk
Export module — `export.service.js`, `export.controller.js`,
`export.routes.js`, `ExportPanel.jsx`, `ExportButton.jsx`) against every
schema/architecture change made in Sprints ≤ 039. No new export
category, no Report-based export, no new endpoint category is proposed
anywhere in this revision. Every finding below was confirmed by reading
the actual current Mongoose schema for each exported collection side by
side with `export.service.js`'s `COLUMNS`/`fetchData()` definitions for
that same module — not assumed.

---

# 1. EXECUTIVE SUMMARY

The Bulk Export module (`/export` tab) supports exactly twelve modules
today: `vessels, agents, containerTypes, expenseTypes, services, rounds,
voyages, bookings, expenses, invoices, tracking, auditLogs`. Comparing
each module's export column list against its current Mongoose schema
(not the schema at the time the export was built) surfaces a clear,
consistent pattern: **every export whose source collection was
restructured by a later sprint has drifted — fields removed from the
schema are still "exported" as blank/dead columns, and fields added by
a later sprint are silently absent.** No export is broken in the sense
of throwing an error; every one of them still runs and produces a
file — the problem is entirely about **column-level correctness and
completeness**, exactly the audit this sprint asks for.

**Confirmed defects, ranked by how much real business data they hide:**
1. **Booking export is missing `containerNumber`** — the field Sprint
   021 made the **primary match key** for the entire booking/import/
   Final-Loading architecture — and is missing `dg`/`imdgCode`/
   `containerStatus`/`vgm`/`remarks`, all added in Sprint 021/026. Its
   `quantity` column is a dead field (`Booking.quantity` was removed in
   Sprint 025/026 when the schema moved to "one booking = one
   container"). It also has no Layer 1 (`ManualBooking`) counterpart at
   all — Sprint 023 introduced Layer 1 as a first-class parallel
   booking collection, and it has never been exportable.
2. **Vessel export is missing all thirteen Vessel Particulars fields**
   added in Sprint 021 (`manager, loa, beam, summerDraft, grossTonnage,
   netTonnage, suezGT, suezNT, totalBunkerCapacity, vlsfoCapacity,
   mdoCapacity, fwCapacity`) plus `charterStartDate`/`charterEndDate` —
   confirmed present on `vessel.model.js`, confirmed absent from
   `COLUMNS.vessels`.
3. **Expense export has zero Sprint 036 awareness** — no `portId`, no
   populated port name, no computed scope (Round/Voyage/Port), no
   Voyage Cost/Other Voyage Cost classification — it is the same
   free-text-only `port` column that existed before Sprint 036 ever
   introduced a real `Expense.portId` relationship.
4. **Voyage export is missing `etp`** (estimated time of position — a
   real, current field on `voyage.model.js`) and `isManual`.
5. **Invoice export doesn't surface `orphaned` line items** — Sprint
   033's `bookingImport.service.js` reconciliation can flag a line item
   `orphaned:true` when its booking gets auto-cancelled; the export
   currently has no way to tell an accountant that an invoice contains
   an orphaned line.

**Every export continues to run without error** — this is a
completeness/correctness gap, not a crash risk, which matches the
audit's own framing ("verify every existing export still matches the
latest architecture," not "fix a broken feature").

# 2. CURRENT EXPORT ARCHITECTURE (unchanged by this sprint)

```
Frontend
  ExportPanel.jsx (standalone /export page — bulk, multi-module picker)
  ExportButton.jsx (embedded in 6 List pages: BookingList, ExpenseList,
    InvoiceList, RoundList, VoyageList, AuditLogList)
        │
        ▼
  exportService (frontend) → POST /export/excel | POST /export/zip

Backend
  export.routes.js   — rbac('export') + per-module checkModuleExportPermission
  export.controller.js — exportExcel / exportZip
  export.service.js
    COLUMNS{}    — one column-set literal per module (12 modules)
    fetchData()  — one switch-case per module, each a direct Mongoose query
    buildExcelBuffer() — generic ExcelJS workbook builder (reused as-is)
    buildZipStream()   — archiver-based ZIP of multiple exportSingle() calls
```

This architecture itself is **not being redesigned**. Every fix in this
plan is a column/filter addition or correction inside an existing
`fetchData()` case and its matching `COLUMNS` entry — the same pattern
already used by all twelve modules today.

# 3. EXPORT-BY-EXPORT REVIEW

Each entry: schema fields confirmed present vs. what `COLUMNS`/
`fetchData()` currently exports.

## 3.1 Vessel Export
**Schema (`vessel.model.js`) vs. export:** exported today —
`vesselCode, vesselName, imoNumber, flag, callSign, ownershipType,
ownerName, ownershipDescription, capacity, dwt, builtYear, status,
notes, createdAt`. **Missing, confirmed present on the schema:**
`charterStartDate, charterEndDate` (charter period — present since
before Sprint 021) and all thirteen Vessel Particulars fields (Sprint
021): `manager, loa, beam, summerDraft, grossTonnage, netTonnage,
suezGT, suezNT, totalBunkerCapacity, vlsfoCapacity, mdoCapacity,
fwCapacity`. **Nothing removed from the schema is still exported** —
this module's problem is purely "newly added fields not exported,"
exactly the audit's own example case.

## 3.2 Agent Export
**Schema vs. export:** matches current `agent.model.js` field-for-field
for every top-level field. **One confirmed limitation:** `contacts` is
an array (`[contactSchema]`); the export flattens only
`contacts[0]` (`primaryContact`/`primaryMobile`/`primaryEmail`/
`primaryDesc`) — an agent with 2+ contacts silently loses every contact
past the first in the export. This is a pre-existing, deliberate
flattening choice (arrays don't map cleanly to flat Excel columns), not
something a later sprint broke — flagged as a real but low-severity gap
since Agent contacts predate this audit's sprint range.

## 3.3 Container Type Export
**Schema vs. export:** exact match — `code, description, size, type,
createdAt` covers every current field on `containerType.model.js`. **No
issue found.**

## 3.4 Expense Type Export
**Schema vs. export:** `expenseType.model.js` itself (`name, category`)
is fully covered. **Confirmed gap relative to Sprint 035/036:** the
export shows the raw `category` string but never surfaces that
category's `costClassification` ("Voyage Cost" / "Other Voyage Cost"),
the business-configurable field Sprint 035 added to the separate
`ExpenseCategory` collection specifically so this decision would be
visible and auditable outside the report layer. An Expense Type export
that can't show which classification a category carries is missing the
single most consequential fact about that category today.

## 3.5 Service Export
**Schema vs. export:** exact match — `serviceCode, serviceName,
defaultVessel, status, description, createdAt` covers every current
field on `service.model.js`. **No issue found.**

## 3.6 Round Export
**Schema vs. export:** exact match — `roundNumber, serviceCode,
serviceName, vesselCode, vesselName, startDate, endDate, status, notes,
createdAt` covers every current top-level field on `round.model.js`
(`voyageIds` is an internal linking array, not a flat exportable value —
correctly omitted). **No issue found.**

## 3.7 Voyage Export
**Schema (`voyage.model.js`) vs. export:** exported today —
`voyageNumber, roundNumber, serviceCode, polName, podName, etd, eta,
atd, ata, status, sequence`. **Missing, confirmed present on the
schema:** `etp` (estimated time of position — a real, current field,
distinct from `eta`) and `isManual` (whether this voyage was manually
created — a real, current, currently-invisible-in-export flag used
throughout the Capacity Engine/UI, e.g. `CapacitySegmentTable.jsx`'s
"manual" badge).

## 3.8 Booking Export (Layer 2 — `bookings`)
**Schema (`booking.model.js`) vs. export:** exported today —
`bookingNumber, voyageNumber, agentCode, agentName, carrierName,
shipper, consignee, polName, podName, containerType, quantity,
freightRate, totalFreight, commodity, status, createdAt`.
**Confirmed dead field:** `quantity` — `Booking.quantity` does not
exist on the current schema (removed Sprint 025/026, replaced by "one
booking = one container"); this column is always blank.
**Missing, confirmed present on the schema:** `containerNumber` (the
field Sprint 021 made the PRIMARY match key for import/Final-Loading
reconciliation — its complete absence from the export is the single
most significant finding in this whole audit), `vgm` (Verified Gross
Mass), `dg`/`imdgCode` (Hazardous/IMDG Code, Sprint 026), and
`containerStatus` (Full/Empty). `remarks` is also present on the schema
and absent from the export.
**Missing entirely: Layer 1 (`ManualBooking`).** Confirmed — no
`ManualBooking` require anywhere in `export.service.js`. Sprint 023
made Layer 1 a first-class, parallel booking collection with its own
`bookingNumber` sequence (`MB-000001`), and it has never had any export
path, bulk or otherwise. Per this sprint's own framing ("Booking export
reflects the current Booking architecture"), the current Booking
architecture is dual-layer — an export module claiming to cover
Bookings while only ever touching one of the two collections is the
clearest instance of "not matching the current architecture" in this
whole review.

## 3.9 Expense Export
**Schema (`expense.model.js`) vs. export:** exported today —
`expenseDate, expenseTypeName, category, roundNumber, voyageNumber,
agentName, port, amount, currency, description, createdAt`.
**Confirmed gap (Sprint 036):** `Expense.portId` (the real Port
reference, added Sprint 036 specifically to replace the free-text
`port` field's data-quality problem) is neither populated nor exported
— the export still shows only the legacy free-text `port` string, with
no way to tell whether a given expense is Round-, Voyage-, or
Port-scoped (the `scope` concept Sprint 036 introduced, already
computed and reused by `getExpenseReport`/`ExpenseList.jsx` via
`expense.service.js#deriveScope()`, but never touched by this
independent export query).

## 3.10 Invoice Export
**Schema (`invoice.model.js`, Sprint 033 structure) vs. export:**
exported today — `invoiceNumber, invoiceType, bookingNumbers, agentCode,
agentName, invoiceDate, dueDate, totalAmount, paidAmount, balanceAmount,
currency, status, notes, createdAt`. This is the **best-aligned export
in the module** — it already correctly reflects the Sprint 033
header+lineItems restructure (`paidAmount`/`balanceAmount` instead of a
pre-Sprint-033 flat `amount`). **One confirmed gap:** none of the
`lineItems[].orphaned` flags are surfaced — an invoice with an
auto-orphaned line item (Sprint 033's Final-Loading-reconciliation edge
case) looks identical in the export to one with none, even though the
UI (`Invoice Detail`) already shows this as a warning badge.

## 3.11 Tracking Export
**Schema (`trackingHistory.model.js`) vs. export:** exported today —
`lastUpdate, voyageNumber, roundNumber, vesselCode, vesselName,
serviceCode, portName, terminalName, status, remarks, createdBy`.
**Minor gap:** `countryId`/`cityId` (present on the schema, populated
nowhere in this export) are not surfaced — low severity, since
port/terminal already carry most of the useful geography, but a real,
confirmed absence.

## 3.12 Audit Log Export
**Schema (`auditLog.model.js`) vs. export:** exported today —
`timestamp, userEmail, action, module, recordNumber, ipAddress`.
**Confirmed, deliberate-looking omission:** `oldValues`/`newValues`
(the actual before/after diff payload) and `userAgent` are present on
the schema and absent from the export. Unlike the other gaps in this
review, this one plausibly reflects an original design choice (a
`Mixed`-type diff object doesn't flatten cleanly into an Excel cell)
rather than schema drift — flagged for a decision (Section 6), not
asserted as a defect the same way the others are.

| Invoice line items | `orphaned` flag (Sprint 033) | ❌ not surfaced |

**Every row above is the same shape of finding: a real, current field
or rule that the export module has never been updated to reflect.**
None of the 12 exports actively contradicts a business rule (e.g. none
of them shows Cancelled/removed data as if it were current) — the
consistent problem is omission, not incorrect computation, which
matches the fact that every export is a flat, unaggregated record dump
with no business logic of its own to get wrong in the first place.

# 5. EXPORT CONSISTENCY REVIEW

- **Filters:** inconsistent coverage of `ExportPanel.jsx`'s own global
  Date Range filter — confirmed by reading each `fetchData()` case,
  only `rounds`... **correction, precise reading:** `dateFrom`/`dateTo`
  are in fact **not read by any of the 12 cases at all** (`rounds`
  filters only by `status`; no case in the file references
  `filters.dateFrom`/`filters.dateTo`). `ExportPanel.jsx`'s own copy
  ("Applied to modules that support date filtering — expenses,
  invoices, rounds, audit logs, etc.") is therefore inaccurate for
  every module today, including the four it names as examples. This is
  a confirmed, currently-live UI/backend mismatch, independent of any
  later sprint's schema changes.
- **Columns:** each export's column set is internally consistent with
  itself; the gaps are all "missing," never "wrong type/mislabeled."
- **Sorting:** each module sorts by its own natural key
  (`createdAt`/`etd`/`expenseDate`/`invoiceDate`/`lastUpdate`) —
  reasonable, no inconsistency worth changing.
- **Totals:** no export includes a summary/totals row — acceptable for
  a raw record dump (a totals row across `totalFreight`/`amount`/
  `totalAmount` would be a reasonable, low-risk addition, but is not
  required to bring these exports "up to date" with schema changes,
  so it is listed as optional, not required, in Section 6).
- **Currency:** `expenses`/`invoices` already carry a `currency`
  column; no cross-currency summing happens anywhere in export (correct
  — a flat dump should not silently sum mixed currencies).
- **Grouping:** none — consistent with every export being a flat detail
  dump, not a report.
- **Formatting:** dates are consistently formatted via one shared
  `fmtD()` helper (in `fetchData()`) and a nearly-identical `fmtDate()`
  (in `buildExcelBuffer()`'s `flattenDoc()`) — **two separate, slightly
  different date-formatting functions exist in the same file** doing
  the same job (`fmtD` is used inside each `fetchData()` case;
  `flattenDoc`'s `fmtDate` is a fallback for any column value that
  looks like an ISO date string that slipped through un-formatted) —
  not a bug today (both produce the same `en-GB` format), but a minor,
  confirmed instance of duplicated logic worth consolidating into one
  function while this file is being touched anyway.
- **Data Source:** every export is a direct Mongoose query — this
  remains architecturally correct and unchanged for this sprint (Sprint
  040 is not converting any of these to reuse a Report, per the
  corrected scope).

# 6. BACKEND IMPACT

Every item below is a column/filter addition or dead-field removal
inside an existing `fetchData()` case + its matching `COLUMNS` entry —
no new switch-case pattern, no new file, no new dependency.

**Required (schema drift — brings an export back in sync with a
schema change already shipped):**
1. `COLUMNS.vessels` — add `charterStartDate, charterEndDate, manager,
   loa, beam, summerDraft, grossTonnage, netTonnage, suezGT, suezNT,
   totalBunkerCapacity, vlsfoCapacity, mdoCapacity, fwCapacity`; the
   `vessels` `fetchData()` case already does `{...r}` spread so these
   flow through automatically once added to `COLUMNS` — **no
   `fetchData()` change needed for this one, `COLUMNS` alone is
   sufficient.**
2. `COLUMNS.voyages` + `fetchData()`'s `voyages` case — add `etp`
   (formatted the same way `etd`/`eta`/`atd`/`ata` already are) and
   `isManual` (boolean → `'Yes'/'No'` for a readable column, following
   the same mapping style already used for other boolean-like display
   fields elsewhere in this codebase).
3. `COLUMNS.bookings` + `fetchData()`'s `bookings` case —
   remove the dead `quantity` column; add `containerNumber` (placed
   right after `bookingNumber`, matching its role as the row's second
   identifying key), `vgm`, `dg` (→ `'Yes'/'No'`, UI label
   "Hazardous," matching `BookingForm.jsx`'s own label choice),
   `imdgCode`, `containerStatus`, `remarks`.
4. **New module: `manualBookings`** — a new `COLUMNS` entry + new
   `fetchData()` case, following the exact same flat-record-dump
   pattern as every existing case (populate `voyageId`/`agentId`, map
   to a flat row). Column set covers `ManualBooking`'s own header
   fields (`bookingNumber, voyageNumber, agentCode, agentName,
   totalFreight, totalTEU, totalUnits, remarks, status, createdAt`) —
   `cargoRows[]` itself (a nested array of per-container-type lines) is
   summarized by the header's own `totalTEU`/`totalUnits`/
   `totalFreight` rather than flattened row-by-row, consistent with how
   `agents.contacts[]` is already handled elsewhere in this same file
   (Section 3.2) — not a new flattening convention, the existing one
   applied to a new collection.
5. `COLUMNS.expenses` + `fetchData()`'s `expenses` case — add
   `.populate('portId', 'name code')`; add a `scope` column computed
   via the already-exported `expense.service.js#deriveScope()`
   (available since Sprint 038 — reused directly, not
   re-implemented); add `portName` (from the new populate).
6. `COLUMNS.expenseTypes` + `fetchData()`'s `expenseTypes` case — join
   each `ExpenseType.category` string against
   `expenseTypeService.getCostClassificationMap()` (already exported
   since Sprint 035/036, reused directly) to add a `costClassification`
   column.
7. `COLUMNS.invoices` + `fetchData()`'s `invoices` case — add an
   `orphanedCount` column (`r.lineItems.filter(li => li.orphaned).length`,
   a simple, already-available in-memory count — no new query).

**Optional (worth doing while these files are open, not required to
close a schema-drift gap):**
8. Consolidate `fetchData()`'s `fmtD()` and `buildExcelBuffer()`'s
   `flattenDoc()`-local `fmtDate()` into one shared date-formatting
   helper (Section 5) — a cleanup, not a correctness fix.
9. A totals/summary row for the `expenses`/`invoices`/`bookings`
   exports — genuinely optional, since a raw record dump is not
   required to carry a totals row to be "correct."

**Explicitly NOT changed:**
- `containerTypes`, `services`, `rounds`, `agents` `fetchData()` cases —
  confirmed already correct (Sections 3.2, 3.3, 3.5, 3.6).
- `auditLogs` — `oldValues`/`newValues`/`userAgent` inclusion is left as
  an open question (Section 9), not a required fix, since it may be a
  deliberate design choice.
- `buildExcelBuffer()`/`buildZipStream()`'s own logic — both already
  generic and correct; no export in this review needs a change to how
  the workbook itself is assembled, only to what data feeds it.
- `export.routes.js`/`export.controller.js` — no route, permission, or
  controller change is required for any item above; every fix is
  internal to `export.service.js`.

# 10. ARCHITECTURE DECISIONS (ADR)

**ADR-1 — Every fix is additive to an existing `COLUMNS`/`fetchData()`
pair; no export's existing columns are removed or renamed**, except the
one confirmed dead field (`bookings.quantity`) whose removal is itself
required specifically because it no longer corresponds to any real
data (Section 3.8) — consistent with "removed fields are no longer
exported" being one of this sprint's own explicit examples.

**ADR-2 — `manualBookings` is added as a new module in the exact same
architectural shape as the other 12, not as a variant of the existing
`bookings` case.** Layer 1 and Layer 2 are separate collections with
different shapes (header+`cargoRows[]` vs. flat one-container-per-row);
merging them into one export would require an in-export merge/tagging
step this module has never needed for any other pair of collections —
keeping them as two separate, independently-selectable tiles in
`ExportPanel.jsx` (exactly how `rounds` and `voyages` are already two
separate tiles despite being related) is the established convention,
reused rather than reinvented.

**ADR-3 — Cross-collection joins added to existing exports (Expense
Type → ExpenseCategory classification, Expense → Port) are read-only
lookups via already-exported service functions, never a new
aggregation pipeline.** This keeps every fix consistent with "Export is
a presentation layer, not a reporting engine" even though this sprint
is explicitly not about Report-based exports — the same discipline
applies to record-level exports too: a classification lookup is a
join, not a calculation, and reusing `getCostClassificationMap()`
guarantees this export can never show a different classification than
`getRoundPnL`/`getExpenseReport` would for the same category.

**ADR-4 — The Date Range filter gap (Section 5/7 item 2) is fixed by
implementing the four cases `ExportPanel.jsx` already claims support
it, not by narrowing the UI copy to "nothing currently supports this."**
Since each of the four modules named already has an obvious date field,
implementing is strictly less work and more useful than documenting a
limitation — chosen here as the default recommendation, but explicitly
listed as a decision this sprint's approval should confirm, not assume.

# 11. RISKS

1. **`bookings.quantity` removal changes an existing export's column
   count** — any external process/spreadsheet template that expects
   that (currently always-blank) column to exist at a fixed position
   would need updating. Low risk (a blank column carries no information
   to lose), but a real compatibility note.
2. **Vessel Particulars fields are frequently `null`** (many vessels
   predate Sprint 021 and were never backfilled) — adding these 13
   columns will produce a very sparse export for older vessel records;
   this is accurate, not a bug, but should be expected, not mistaken
   for a new defect.
3. **`manualBookings` as a new module requires new `Permission` rows
   per role before non-SuperAdmin users can use it** — same one-time
   seeding cost every one of the existing 12 modules already required
   when first added; not a new category of risk, just restated for
   completeness.
4. **Implementing Date Range filtering on `expenses`/`invoices`/
   `rounds`/`auditLogs` (ADR-4) changes those exports' row counts** for
   anyone who has been exporting "everything" and unknowingly relying
   on the date filter being silently ignored — a visible, intentional
   behavior change, same class of risk Sprint 038 already flagged for
   its own report-level fixes.
5. **The `auditLogs` `oldValues`/`newValues` open question (Section 9)
   has a real tradeoff either way** — including raw diff objects in an
   Excel export is either genuinely valuable (full audit trail export)
   or unreadable noise (nested JSON crammed into one cell), depending
   entirely on who consumes this export and how — this sprint
