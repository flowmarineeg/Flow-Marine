================================================================================
SPRINT 019 — RBAC CONSISTENCY AUDIT & ENFORCEMENT
================================================================================

STATUS: ✅ Complete

GOAL:
  Make RBAC 100% consistent across the entire system — backend and frontend.
  No new features. No workflow changes. Pure security and consistency hardening.

  The audit revealed two critical unprotected endpoints, zero page-level route
  guards on the frontend, sidebar visibility gaps, missing permission actions,
  and several UI components ignoring permission state entirely.

================================================================================
AUDIT FINDINGS
================================================================================

CRITICAL (no RBAC at all):
  - GET /dashboard/stats    → auth only, any authenticated user
  - POST /export/excel      → auth only, any authenticated user
  - POST /export/zip        → auth only, any authenticated user

HIGH:
  - No frontend page-level guards — layout.jsx only checked isAuthenticated
  - Sidebar used isHidden() only, not can(module,'read')
  - Booking import used rbac('bookings') → create, not a dedicated import action
  - Final Loading import (which cancels other bookings) never checked update+delete
  - dashboard not in MODULES[] — no permission docs could be created for it
  - export module in MODULES[] but never enforced on its own routes

MEDIUM:
  - BookingList Edit button hid for Cancelled but NOT for Final Loading
  - Export buttons in VesselList (inline) and ExportButton component
    never checked can('export','read') or can(module,'export')
  - BookingList Import button visible to users without import permission
  - All detail/sub pages (/:id, /new, /edit) had no guard

1E. modules/dashboard/dashboard.routes.js

────────────────────────────────────────────────────────────────────────────────
1F. modules/export/export.routes.js
────────────────────────────────────────────────────────────────────────────────

  ADDED: rbac('export') to both POST /excel and POST /zip
  ADDED: checkModuleExportPermission middleware (inline in routes file)

  checkModuleExportPermission:
    - SuperAdmin bypasses
    - Reads roleId from req.user
    - Extracts requested module(s) from req.body.module (excel)
      or req.body.exports[].module (zip)
    - For each module: checks Permission.actions.export === true
    - If any module denied → 403 with { denied: [...moduleNames] }
    - All pass → next()

  This closes the gap where a user could export any module's data
  regardless of their per-module permissions.

────────────────────────────────────────────────────────────────────────────────
1G. modules/bookings/booking.routes.js
────────────────────────────────────────────────────────────────────────────────

  CHANGED: POST /import/preview
    was: rbac('bookings')           → derived action = 'create'
    now: rbac('bookings', 'import') → explicit 'import' action

  CHANGED: POST /import/save
    was: rbac('bookings')           → derived action = 'create'
    now: rbac('bookings', 'import') + inline finalLoading guard

  finalLoading guard (inline middleware on save route):
    If req.body.importType === 'finalLoading' AND user is not SuperAdmin:
      - Load Permission doc for roleId + module 'bookings'
      - Check actions.update === true AND actions.delete === true
      - If either false → 403 "Final Loading import requires update and
        delete permissions on bookings"
      - Otherwise → next()

    Rationale: Final Loading reconciliation cancels all non-matching
    voyage bookings (effectively a bulk delete + bulk status update),
    so it legitimately requires both update and delete permissions,
    not just import.

────────────────────────────────────────────────────────────────────────────────
2B. components/ui/Can.jsx  (NEW FILE)
────────────────────────────────────────────────────────────────────────────────

  Inline RBAC guard component.
  Renders children only when can(module, action) === true.
  Optional fallback prop for the denied case (default: null).

  Usage:
    <Can module="bookings" action="create">
      <Button>+ New Booking</Button>
    </Can>

    <Can module="vessels" action="delete" fallback={<span>—</span>}>
      <DeleteButton />
    </Can>

────────────────────────────────────────────────────────────────────────────────
2C. components/ui/PageGuard.jsx  (NEW FILE)
────────────────────────────────────────────────────────────────────────────────

  Page-level RBAC guard.
  Waits for permissionsLoaded (shows spinner while loading).
  If isHidden(module) OR !can(module, action) → renders Access Denied block.
  Otherwise renders children.

  Default action: 'read'
  Access Denied block:
    - Red circle with warning icon
    - "Access Denied" heading
    - "You don't have permission to view this section. Contact your
      administrator to request access."

  Usage:
    <PageGuard module="users">          → requires read
    <PageGuard module="vessels" action="update"> → requires update (edit pages)
    <PageGuard module="bookings" action="create"> → requires create (new pages)
    <PageGuard module="bookings" action="import"> → requires import

NEW PATTERNS — NEVER BREAK
================================================================================

  1. rbac(module, actionOverride)
     Use for any endpoint where the HTTP method doesn't map to the right action.
     Example: POST /import/preview → rbac('bookings', 'import')

  2. Every new page.jsx MUST wrap content in <PageGuard module="x">
     Detail pages: default action="read"
     Create pages: action="create"
     Edit pages:   action="update"
     Import pages: action="import"

  3. Every export button MUST check:
     can('export', 'read') && can(module, 'export')
     Use <ExportButton> (already enforces this) for consistency.
     Inline export buttons must add the same guard manually.

  4. permissionsLoaded from PermissionContext
     Wait for this before making permission decisions in components.
     PageGuard handles this automatically — use PageGuard on all pages.

================================================================================
LIVE DB MIGRATION NOTE
================================================================================

  The seed is idempotent (upsertOne = insert-if-not-exists).
  Existing permission documents will NOT be updated by re-running seed.

  For a live database, run a one-time migration:
    1. Add import:false, export:false to all existing Permission docs
       db.permissions.updateMany({}, { $set: { 'actions.import': false,
                                               'actions.export': false } })

    2. Create missing 'dashboard' Permission doc for each role:
       For each role, insert Permission { module: 'dashboard', actions: {...} }
       matching the role's intended access level.

    3. Grant import:true on bookings for Operations Manager
    4. Grant export:true on relevant modules per role (per seed logic above)
