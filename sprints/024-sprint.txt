================================================================================
  IMPLEMENTATION NOTES — Differences Found During Code Review
================================================================================

  NOTE 1 — Capacity engine already reads BOTH layers
  ─────────────────────────────────────────────────────────────────────────────
  The sprint brief stated: "Capacity reads Layer 1 only."
  Reality (capacity.service.js, confirmed by direct file read):
    The engine already queries both Booking (l2Bookings) AND ManualBooking
    (l1Bookings) in a parallel Promise.all (Step A).
    l2Events are computed in Step C. l1Events in Step D.
    allEvents = [...l2Events, ...l1Events] feeds the cargo-flow accumulation.
    GOAL 2 WAS ALREADY IMPLEMENTED IN SPRINT 023. No capacity.service.js change.

  NOTE 2 — quantity stays in schema and import
  ─────────────────────────────────────────────────────────────────────────────
  quantity is kept in the DB for capacity TEU calc:
    effectiveTEU = b.quantity * resolveTEU(b.containerTypeId.size).teu
  Manual form bookings: quantity not sent in payload → backend defaults to 1.
  Import bookings: quantity from Excel (or 1 if absent) → stored.
  TEU calculation remains accurate with no capacity.service.js change.

  NOTE 3 — BookingList Qty column (cosmetic, not fixed this sprint)
  ─────────────────────────────────────────────────────────────────────────────
  The Qty column in the operational table will show 1 for all form-created
  bookings. This is cosmetically redundant but causes no functional issue.
  Not changed this sprint.
