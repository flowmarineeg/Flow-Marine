# PART A — Vessel Details KPI Investigation

## A.1 Call chain (verified)


`getVesselStats` is the SINGLE function that produces the entire page
payload — KPI row, "Bookings by Status" doughnut + panel, Agents table,
Round/Voyage history, active-round capacity block, recent tracking. No
other backend function contributes to this page. Confirmed by grep
(`vessels/*.js`) — `Booking`/`ManualBooking` are referenced in exactly two
places in the whole `vessels` module: the booking-stats aggregate
(line 139) and the agents aggregate (line 175). Decision 6 (§full-module
review) is therefore fully covered by fixing these two aggregates — no
other section of the Vessel Details module (Round/Voyage counts, active-
round capacity, recent tracking) touches Booking/ManualBooking data at
all, so no other section can be "legacy Booking-only" by definition.

  `CapacitySegmentTable.jsx:112` ("Sprint 029: exact-segment only").

## A.3 What is INCONSISTENT — the booking-derived KPI block

`vessel.service.js:139-153` (booking status/revenue aggregate) and
`vessel.service.js:175-183` (agents table aggregate):

```js
// vessel.service.js:139-142
const bookingStats = voyageIds.length ? await Booking.aggregate([
  { $match: { voyageId: { $in: voyageIds }, isDeleted: false } },
  { $group: { _id: '$status', count: { $sum: 1 }, totalFreight: { $sum: '$totalFreight' }, totalQty: { $sum: '$quantity' } } },
]) : [];
```

Three concrete inconsistencies, each verified directly against the model
and against the capacity engine's own rules on the very same page:

1. **Layer 1 (ManualBooking) is completely excluded.** `vessel.service.js`
   only ever `require('../bookings/booking.model')` (line 109) — no
   `ManualBooking` import or query anywhere in this file. "Total
   Bookings," "Total Revenue," the per-status counts, and the "Bookings
   by Status" doughnut/panel reflect Layer 2 operational bookings only,
   while the capacity gauge on the same page already counts Layer 1
   toward TEU usage — an internal contradiction on one page.
2. **No status exclusion — Cancelled bookings inflate Total
   Revenue/Total Bookings.** The `$match` at line 140 filters only
   `isDeleted: false`; no `status: { $ne: 'Cancelled' }` anywhere in this
   aggregate or the agents aggregate (line 176). `totalRevenue` (line 148)
   therefore includes Cancelled bookings' `totalFreight`, contradicting
   the capacity engine's own Cancelled-exclusion rule on the same page.
3. **Dead reference to a removed schema field.** `totalQty: { $sum:
   '$quantity' }` (line 141) references a `quantity` field that does not
   exist on the current `Booking` schema (removed Sprint 025/026, "one
   booking = one container"). Produces `0` silently for every group;
   never read anywhere else — confirmed absent from the returned `stats`
   object (lines 195-214). Dead code, to be removed.

**Revenue source confirmation (Decision 3):** `totalFreight` is confirmed,
by direct model inspection, as the correct and ONLY appropriate revenue
field for both layers:
- `Booking` (Layer 2): `booking.model.js:18` — `totalFreight: { type:
  Number, required: true, min: 0 }`, flat rate per container (Sprint
  024/025 — one booking = one container, no quantity multiplier).
- `ManualBooking` (Layer 1): `manualBooking.model.js:37` — `totalFreight:
  { type: Number, required: true, min: 0 }` — server-computed as
  `sum(cargoRows[].rowTotal)` (line 36 comment).
Both models use the identical field name `totalFreight` with the
identical semantic meaning ("this booking/reservation's total freight
value"), so no other field is or should become the official revenue
source. No alternative field is being introduced — `totalFreight` from
both models, summed together, is the closed decision.

**Status enum confirmation (Decision 4):** both models share the exact
same `BOOKING_STATUS` enum from the same shared constant
(`backend/src/config/constants.js:27` — `['Pending', 'Confirmed', 'Final
Loading', 'Cancelled']`, referenced identically by both
`booking.model.js` and `manualBooking.model.js`). A combined
per-status merge (Decision 4) requires no label reconciliation — the
status strings are byte-identical across both layers.

**Agents table field confirmation (Decision 5):** `ManualBooking` DOES
contain `agentId` (`manualBooking.model.js:27` — `agentId: {
type: ObjectId, ref: 'Agent', required: true }`), confirmed present and
required, in the exact same shape (`ObjectId` ref to `Agent`) as
`Booking.agentId` (`booking.model.js:10`). This is the "expected" case
per Decision 5 — no unexpected data inconsistency was found, so the
Agents table gains full Layer 1 + Layer 2 inclusion with no caveat, no
schema change.

None of these fixes require touching Sprint 030/031 (polId/podId
derivation, Round-scoped import). This block never reads `polId`,
`podId`, or `roundId` — only `voyageId`, `status`, `agentId`,
`totalFreight`. Every `Booking`/`ManualBooking` document still has
exactly one `voyageId` regardless of how Sprint 031 resolved it at import
time, so this aggregate's `voyageId: { $in: voyageIds }` join is
structurally unaffected.

## A.4 Business impact

- A vessel with meaningful Layer 1 activity shows an artificially low
  "Total Bookings"/"Total Revenue" while the capacity gauge on the same
  page correctly reflects that activity — fixed by Decisions 1/2/4.
- "Total Revenue" silently including cancelled deals' freight overstates
  realized/likely revenue — fixed by Decisions 2/3.
- Low urgency, no data corruption: read-only aggregate, no documents
  mutated, `getVesselStats` called only from `vessel.controller.js:41-45`
  — no other module consumes this output.

# PART B — Booking Import Page Layout Overflow

## B.1 Root cause (verified against actual JSX/CSS)

**Gap 1 — the table's immediate wrapper has no `overflow-x-auto`.**
`frontend/src/modules/bookings/BookingImport.jsx:508-510`:
```jsx
<div className="card overflow-hidden max-w-full">
  <div className="">
    <table className="w-full border-collapse text-[12px]">
```
Line 509 is an empty, no-op div — no `overflow-x-auto`, no width
constraint. The outer card (line 508) has `overflow-hidden` (clips, no
scrollbar) and no `min-w-0`. The table carries `min-w-[Npx]` on nearly
every one of its ~19 `<td>`s (e.g. the Sprint 031 Voyage column,
`min-w-[150px]`), giving it a large intrinsic min-content width
(~1900px+) with no local place to scroll.

Every sibling list page already implements the correct pattern —
`BookingList.jsx:201-210`:
```jsx
{/* Table — overflow-x-auto clips the table, min-w-0 on the card prevents page blowout */}
<div className="card overflow-hidden min-w-0">
  ...
  <div className="overflow-x-auto">
    {/* minWidth ensures the table scrolls internally rather than expanding the page */}
    <table className="w-full border-collapse" style={{ minWidth: 800 }}>
```
Same pair (`min-w-0` on the card + `overflow-x-auto` on the inner div)
appears in `VoyageList.jsx`, `VesselList.jsx`, `ExpenseList.jsx`,
`ServiceList.jsx`, `RoundList.jsx`, `InvoiceList.jsx`, `TrackingList.jsx`.
`BookingImport.jsx` is the one outlier missing both.

**Gap 2 (diagnosed, NOT to be fixed here per Decision 7 — "do not modify
the dashboard layout") — the dashboard layout's content column has no
`min-width: 0`.** `frontend/src/app/(dashboard)/layout.jsx:71-80`:
```jsx
<div style={{ display: 'flex', height: '100vh', background: 'var(--surface)', overflow: 'clip' }}>
  <Sidebar />
  <div style={{ flex: 1, display: 'flex', flexDirection: 'column', overflow: 'clip' }}>
    <Header />
    <main style={{ flex: 1, overflowY: 'auto', padding: 24 }}>
      {children}
    </main>
  </div>
</div>
```
The content column (line 74) is a flex item whose default `min-width` is
`auto` (content min-content size), not `0` — without an explicit
`minWidth: 0`, it can't shrink below the widest descendant. This is a
real, latent gap in the shared layout, but **per Decision 7 it is
explicitly NOT to be touched in this sprint**: fixing Gap 1 alone (adding
`overflow-x-auto` at the table's own wrapper) is sufficient, because it
stops the table's oversized min-content width from ever reaching this
ancestor in the first place — the table will scroll internally before
its width has a chance to propagate up to `layout.jsx:74`. Gap 2 remains
diagnosed-but-unfixed, consistent with "Fix BookingImport.jsx only."
`overflow: 'clip'` at lines 72/74 is confirmed to be the correct existing
convention for paint-clipping (per `CLAUDE.md`'s Modal/`createPortal`
note) and is not itself wrong — it simply isn't a substitute for
`min-width: 0`, and is not being changed either way.

`globals.css`: `body`/`html` have no `overflow-x` rule (no document-level
safety net — consistent app-wide design, not being changed). `.card` is
purely cosmetic, carries no overflow/width behavior of its own by design
— every page supplies its own `overflow-x-auto`/`min-w-0`, which
`BookingList.jsx` and its siblings do and `BookingImport.jsx` will now
also do.

## B.2 Why this page in particular, and why now

Sprint 031 added a new "Voyage" column (`min-w-[150px]`) to every preview
row, pushing the table's total intrinsic width past whatever margin
existed before the missing wrapper's absence became visually obvious.
The gap was latent before Sprint 031 (this page never had the wrapper,
unlike its siblings); the added column made the resulting page-wide
overflow actually noticeable. No change to the Voyage column or any
Sprint 031 logic is needed — only the containment plumbing around the
table.

## B.3 Business impact

- Directly obstructs the Sprint 031 workflow: users previewing a
  multi-voyage Round import are the ones most likely to see the widest
  possible table, making this the worst possible page for the bug.
- Forces horizontal scrolling of the entire browser window, scrolling the
  sidebar/header out of view.
- No data-correctness impact — purely a CSS/layout defect.

# CURRENT ARCHITECTURE (as verified)

```
Layout containment convention (project-wide):
  Root layout (app/(dashboard)/layout.jsx) provides overflow:clip at the
  row and column level, and overflowY:auto on <main> — it does not cap
  horizontal width itself, by design. Horizontal overflow containment is
  a PER-PAGE responsibility: each table-bearing page supplies its own
  min-w-0 (outer .card) + overflow-x-auto (table's direct wrapper) pair.
  Used by BookingList, VoyageList, VesselList, ExpenseList, ServiceList,
  RoundList, InvoiceList, TrackingList. BookingImport.jsx is the outlier.

Vessel Details KPI architecture (as it stands, pre-fix):
  Two independent, differently-scoped booking data paths feed one page:
    (1) capacity.service.js — dual-layer (Booking + ManualBooking),
        Pending+Confirmed+Final Loading, Cancelled/deleted excluded.
        This is the CORRECT, reference definition (Decision 1).
    (2) vessel.service.js#getVesselStats booking aggregate — Layer 2
        (Booking) ONLY, no status exclusion at all. This is the block
        being corrected by this sprint.
```

# APPROVED ARCHITECTURE (Decisions 1-7, FINAL — no longer open questions)

## Decision 1 — Vessel Details KPI Standard (system standard, going forward)
Every booking-related statistic on the Vessel Details page that
represents vessel business activity MUST include both Layer 1
(ManualBooking) and Layer 2 (Booking), using the capacity engine's
already-established inclusion pattern as the reference. Mixing
Layer-2-only data with combined data on the same page is no longer
permitted anywhere in this module. (No "specific business reason"
exception is invoked in this sprint — every KPI reviewed qualifies as
"vessel business activity.")

## Decision 2 — Total Bookings (FINAL)
```
Total Bookings = (Layer 1 count, status != Cancelled)
                + (Layer 2 count, status != Cancelled)
```

## Decision 3 — Total Revenue (FINAL)
```
Total Revenue = (Layer 1 sum(totalFreight), status != Cancelled)
               + (Layer 2 sum(totalFreight), status != Cancelled)
```
Revenue source confirmed: `totalFreight` on both models (§A.3) — no other
field is introduced or considered.

## Decision 4 — Bookings By Status (FINAL — single combined summary)
```
Pending      = Layer1.Pending      + Layer2.Pending
Confirmed    = Layer1.Confirmed    + Layer2.Confirmed
Final Loading= Layer1.FinalLoading + Layer2.FinalLoading
Cancelled    = Layer1.Cancelled    + Layer2.Cancelled
```
One combined status breakdown (doughnut + panel) — NOT split by layer.
Cancelled remains visible in this breakdown (it is a status slice, not a
headline total) — only the headline Total Bookings/Total Revenue figures
exclude Cancelled, per Decisions 2/3. Status label reconciliation is a
non-issue (§A.3 — identical `BOOKING_STATUS` enum on both models).

## Decision 5 — Agents Table (FINAL)
`ManualBooking.agentId` confirmed present, required, same shape as
`Booking.agentId` (§A.3) — no unexpected inconsistency found, so no stop-
and-report is triggered. Every metric in the Agents table (bookingCount
per agent) becomes Layer 1 + Layer 2 combined, same Cancelled-exclusion
rule as Decisions 2/3. No schema changes; reuses the existing models
exactly as they are.

## Decision 6 — Legacy Booking Logic (module-wide review, FINAL)
Confirmed by grep (§A.1): the entire `vessels` backend module references
`Booking`/`ManualBooking` in exactly two places — the booking-stats
aggregate (line 139) and the agents aggregate (line 175). Both are fixed
by this sprint. Round/Voyage counts, the active-round capacity block, and
recent tracking do not touch Booking/ManualBooking data and are therefore
not "legacy Booking-only" — confirmed, not assumed. No other section of
the Vessel Details page or its backend requires migration.

## Decision 7 — Booking Import Layout (FINAL)
Apply the existing `min-w-0` (card) + `overflow-x-auto` (table wrapper)
pattern to `BookingImport.jsx` only, identical to `BookingList.jsx`.
`app/(dashboard)/layout.jsx` is NOT modified (§B.1, Gap 2 diagnosed but
intentionally left as-is — fixing Gap 1 is sufficient and is the approved
scope).
