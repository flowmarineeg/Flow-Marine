# 1. THE PROBLEM, CONFIRMED FROM SOURCE

`utils/voyageGenerator.js#generateVoyages()` auto-creates one Voyage per
consecutive route-leg pair when a Round is saved: leg pair (1,2) → sequence
1, (2,3) → sequence 2, (3,4) → sequence 3, etc. For these, `sequence`
already equals the leg's true physical position — auto-generated voyages
are naturally in the right order today.

`voyage.service.js#createManualVoyage()` (the "Add Voyage" feature, Sprint
016) lets an admin add a voyage between ANY two ports that each individually
exist somewhere in the route's legs — e.g. a shortcut voyage POL=leg 1,
POD=leg 3, skipping the intermediate stop. Its `sequence` is NOT derived
from leg position at all — it's simply `(lastVoyage.sequence || 0) + 1`,
i.e. "whatever number comes after every voyage that currently exists" (line
127-129). So a manual (leg1→leg3) voyage added after the three auto-voyages
above gets `sequence = 4`, sorting AFTER the (leg3→leg4) voyage in every
view that orders by `sequence` — even though, physically, the vessel
completes the leg1→leg3 run before it can depart on the leg3→leg4 run.

Every one of the three places the client named orders by this same
`sequence` field today, confirmed from source:
- `voyage.service.js#list()` — `.sort({ roundId: 1, sequence: 1 })` (Sprint
  042 changed this from `{sequence,etd}` to `{roundId,sequence}` for the
  grouped Voyages tab; both feed `VoyageList.jsx` and, via the same
  `voyagesService.list({roundId})` call, `RoundVoyageList.jsx`).
- `capacity.service.js#computeRoundCapacity()` — `Voyage.find({...}).sort({
  sequence: 1 })` (line ~85), and its cargo-flow chain (`onboardStart[n] =
  onboardTEU[n-1]`) walks the resulting array in that same order. This
  chain is a REAL calculation dependency, not just a display artifact —
  which is exactly why the client's instruction to leave capacity
  calculation/engine logic untouched is doing real work here: this sprint
  must NOT reorder the array `capacity.service.js` itself computes over,
  only re-sort a presentational COPY of its already-finished `voyages[]`
  result before rendering it.

# 3. THE DATA NEEDED TO COMPUTE DISPLAY ORDER ALREADY EXISTS

`GET /voyages/round-ports/:roundId` (`voyage.service.js#getRoundRoutePorts`,
already used today by `VoyageAddForm.jsx` to populate its POL/POD
dropdowns) returns exactly the leg-position data needed:
```js
[{ sequence, portId, name, code }, ...]   // one entry per route leg, ordered
```
For each voyage, its POL/POD can be resolved to a **leg position** by
looking up `polId`/`podId` against this list — giving a `(polLegPos,
podLegPos)` pair per voyage, INDEPENDENT of that voyage's own possibly-
wrong `sequence` value. Auto-generated voyages don't strictly need this
lookup (their `sequence` already equals `polLegPos` by construction) but
manual voyages do.

# 4. PROPOSED SORT KEY — derived from the client's own example, confirmed

Given the client's example order — `1,2` / `2,3` / `1,3` / `3,4` / `1,4` —
(each pair written as `polLegPos,podLegPos`), the ordering that reproduces
it exactly is:

**Primary key: `podLegPos` ascending. Tie-break: `polLegPos` DESCENDING.**

Verified by hand against every pair in the example:
- `podLegPos=2`: only `(1,2)`.
- `podLegPos=3`: `(2,3)` and `(1,3)` tie → `polLegPos` descending puts
  `2` before `1` → `(2,3)` then `(1,3)`. Matches.
- `podLegPos=4`: `(3,4)` and `(1,4)` tie → `polLegPos` descending puts `3`
  before `1` → `(3,4)` then `(1,4)`. Matches.

Read in business terms: voyages are grouped by where they END, in the
order the vessel physically reaches that point; within the same
destination, the most DIRECT (shortest-range, most immediate) voyage to
that point is shown first, and voyages that skipped over more intermediate
stops to reach the same destination are shown after — i.e. "view the
voyage with the range of how the vessel will flow," reading destination-
first. This fully explains 5 of the 6 pairs in the client's example — see
§5 Q1 for the sixth (`4,1`), which does not fit this formula and needs a
decision before implementation.

# 5. Decisions (all questions answered, locked in)

- **Q1 — The `4,1` example pair → DECIDED: it is a real round-trip case.**
  Confirmed by the client: a voyage whose resolved `podLegPos <
  polLegPos` (end comes before start along the route's leg sequence) is
  real and must always sort at the very END of the list, regardless of
  its own numeric leg positions. Final algorithm (combining this with
  §4's derived rule):
  1. Resolve every voyage's `(polLegPos, podLegPos)` from the round's
     route legs (§3).
  2. Split into two groups: **forward** (`podLegPos >= polLegPos`) and
     **backward** (`podLegPos < polLegPos`).
  3. Sort the forward group by `podLegPos` ascending, tie-break
     `polLegPos` descending (§4's rule — reproduces the client's
     `1,2 / 2,3 / 1,3 / 3,4 / 1,4` order exactly).
  4. Sort the backward group with the same rule, for internal
     consistency (no example covers >1 backward voyage, but this avoids
     an arbitrary order among them if it ever happens).
  5. Final display order = forward group, then backward group appended
     after — backward voyages are always last, never interleaved.
- **Q2 — Repeated ports (round-trip routes) → DECIDED: does not apply.**
  Per the client: manual voyages are created against a **leg position**
  (POL Leg / POD Leg), not a bare port name — so there is no ambiguity
  even when the same port physically appears at more than one leg in the
  route. Each voyage's `(polLegPos, podLegPos)` is resolved directly, with
  no repeated-port tie-break logic needed.
- **Q3 — Shared logic → DECIDED: yes, one shared function.** A single
  sort utility is implemented once and reused by all three views (Voyage
  Tab, Round Details → Voyages, Capacity Engine tables) — never
  reimplemented per view.
