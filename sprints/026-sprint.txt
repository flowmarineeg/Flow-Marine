================================================================================
  OBJECTIVE
================================================================================

Improve the Layer 2 Booking and Final Loading Import workflow.

This sprint is NOT a Layer 2 architecture redesign.
This sprint does NOT touch booking.model.js beyond the minimum, booking.service.js,
or capacity.

The Layer 2 architecture is already complete and stays as-is.
All schema fields, business rules, and the capacity engine remain unchanged.

Specifically this sprint achieves:

  1. Excel column alias expansion
       Multiple header names now map to the same existing backend field.
       This makes the import template more flexible and future-proof.

  2. Hazardous + IMDG Code
       Two new UI-facing concepts replace the old DG + DG% columns.
       They map to the EXISTING dg (Boolean) and a NEW imdgCode (String) field.
       The dg schema field name does NOT change.

  3. Remove Currency
       Currency is removed from validation, preview, and save.
       No business logic depends on it.

  4. Remove DG% (dgPercent)
       Replaced by IMDG Code (free-text string). The schema field dgPercent
       is removed and imdgCode is added to booking.model.js.
       This is the ONLY schema change in Sprint 026.

  5. Make Container Status required in both import modes
       Currently optional. Now required. Both modes share validateRow().

  6. Import mode documentation
       Formally document the two import modes (Booking vs Final Loading),
       their correct matching rules, and their effect on Capacity.

================================================================================
  IMPORT SCOPE — VOYAGE + AGENT
================================================================================

  The import scope is NOT the entire Voyage.
  The import scope is:  (Voyage + Agent)

  Workflow:
    1. User selects a Voyage.
    2. User selects an Agent.
    3. The system loads ONLY the bookings that belong to that Agent on that Voyage.
    4. Inside that scope, matching is performed using Container Number alone.

  Import Scope  =  (Voyage + Agent)
  Matching Key  =  Container Number

  Bookings belonging to other Agents on the same Voyage are NEVER compared,
  NEVER updated, and NEVER cancelled. They are completely outside scope.

  This applies to BOTH import modes.

  Code implications:
    previewImport(): existingBookings query must include agentId filter.
      Current code: Booking.find({ containerNumber: {$in:...}, voyageId, isDeleted:false })
      Correct code: Booking.find({ containerNumber: {$in:...}, voyageId, agentId, isDeleted:false })

    saveImport() Final Loading reconciliation: the cancel query must include agentId.
      Current code: { voyageId, isDeleted:false, status:{$nin:['Cancelled']}, containerNumber:{$nin:...} }
      Correct code: { voyageId, agentId, isDeleted:false, status:{$nin:['Cancelled']}, containerNumber:{$nin:...} }

  These are the only two query changes needed to enforce the Agent scope.
  All other save logic is already correct (agentId is already set on insert and $set).

================================================================================
  TWO IMPORT MODES — FORMAL DOCUMENTATION
================================================================================

  Both modes use the same previewImport() and saveImport() backend functions.
  The importType parameter controls the differences documented below.

────────────────────────────────────────────────────────────────────────────────
  MODE 1: Booking Import  (importType = 'booking')
────────────────────────────────────────────────────────────────────────────────

  Purpose:
    Day-to-day operational booking updates.
    Creates new bookings and updates existing bookings.
    Never cancels other bookings on the voyage.
    Never performs reconciliation.

  Matching rule (Business Identity = Voyage + Agent + Container Number):
    IF Container Number exists in the (Voyage + Agent) scope:
      rowStatus = 'update'  ->  UPDATE the existing booking
    IF Container Number does NOT exist in the (Voyage + Agent) scope:
      rowStatus = 'valid'   ->  CREATE a new booking

  Booking Import must NEVER skip an existing container.
  Its purpose is Create OR Update. Nothing is ever skipped because it already exists.
  Reconciliation (cancelling missing containers) is ONLY performed by Final Loading.

  On save:
    - Create new bookings (status: 'Pending')
    - Update existing bookings with new data from the file
    - No bookings on the voyage are cancelled
    - Cache invalidated after save

  Effect on Capacity:
    New bookings: status 'Pending' -> L2_STATUSES includes Pending -> counted
    Updated bookings: status unchanged unless explicitly set -> capacity reflects update
    No cancellations -> existing capacity not reduced

────────────────────────────────────────────────────────────────────────────────
  MODE 2: Final Loading Import  (importType = 'finalLoading')
────────────────────────────────────────────────────────────────────────────────

  Purpose:
    Final vessel loading manifest. Authoritative list of containers on the vessel.

  Matching rule (Business Identity = Voyage + Agent + Container Number):
    IF Container Number exists in the (Voyage + Agent) scope:
      rowStatus = 'update'  ->  UPDATE the existing booking
    IF Container Number does NOT exist in the (Voyage + Agent) scope:
      rowStatus = 'new'     ->  CREATE a new booking

  After processing the file:
    Any booking belonging to the SAME (Voyage + Agent) scope that is NOT present
    in the imported manifest -> Status = Cancelled.
    Bookings belonging to OTHER agents on the same voyage are NOT affected.

  On save:
    Step 1: Create or update all valid/new/update rows (status: 'Pending')
    Step 2: Mark ALL saved containers on this voyage -> status: 'Final Loading'
    Step 3: Mark ALL bookings in the (Voyage + Agent) scope NOT in manifest -> 'Cancelled'
            (bookings belonging to OTHER agents on the same voyage are untouched)
    Step 4: Invalidate round capacity cache

  Effect on Capacity:
    Final Loading containers -> status 'Final Loading' -> counted by engine
    Cancelled containers -> excluded from engine
    Cache invalidated -> next read is fresh
    TEU from containerType.size -> no quantity -> correct

  Important: Never DELETES any booking. Only sets status to Cancelled.

================================================================================
  BUSINESS IDENTITY RULE
================================================================================

  Every Operational Booking represents exactly ONE physical container.

  Import Scope  =  (Voyage + Agent)
  Matching Key  =  Container Number
  Business Identity  =  (Voyage + Agent + Container Number)

  The import scope is always a single Agent on a single Voyage.
  The system never compares against bookings from other agents, even on the same voyage.

  This is a business matching rule, NOT a database uniqueness constraint.

  Booking Number is NOT part of the matching process.
  Matching is performed using Container Number within the (Voyage + Agent) scope.
  If a Booking Number is supplied in the Excel file, it is informational only.
  If blank, a Booking Number is auto-generated. Existing behaviour unchanged.

  Matching rules applied by BOTH import modes:
    Container Number FOUND in (Voyage + Agent) scope  ->  UPDATE
    Container Number NOT FOUND in (Voyage + Agent) scope  ->  CREATE

  Difference between modes after matching:
    Booking Import:       Create or Update. No reconciliation. No cancellations.
    Final Loading Import: Create or Update. Then cancel all bookings in the
                         (Voyage + Agent) scope NOT present in the manifest.
                         Bookings belonging to other agents on the same Voyage
                         are NEVER affected.

================================================================================
  THE ONLY SCHEMA CHANGE — booking.model.js
================================================================================

  REMOVE:
    dgPercent: { type: Number, min: 0, max: 100, default: null }

  ADD:
    imdgCode: { type: String, trim: true, default: null, maxlength: 50 }

  KEEP UNCHANGED:
    dg: { type: Boolean, default: false }
    All other booking fields — no change.

  Why imdgCode is new data, not an alias:
    dgPercent was a 0-100 number. imdgCode is a free-text IMDG identifier
    (e.g. "3.1", "UN1203 Class 3"). These are different data types representing
    different business concepts. The old dgPercent value in existing documents is
    safely ignored after this change.

  No migration required:
    Old documents with dgPercent: value retained in MongoDB but never read.
    Old documents without imdgCode: imdgCode returns null (Mongoose default).

  PROPOSED EXCEL COLUMN STRUCTURE

  Both import modes use the same template.

  COLUMN              REQUIRED?    NOTES
  Container Number    YES          Primary match key per voyage. Uppercase.
  Container Type      YES          Code, size, or code:size. Resolved vs CT library.
  Container Size      NO           Alternative to Container Type. Also: Size, Length.
  Container Status    YES          Full | Empty (case-insensitive).
  POL                 YES          Port name or UNLOCODE.
  POD                 YES          Port name or UNLOCODE. Must differ from POL.
  Rate                YES          Freight rate per container. Non-negative number.

  Booking Number      NO           Auto-generated if blank.
  Shipper             NO           Free text.
  Consignee           NO           Free text.
  Carrier Name        NO           Free text. Also accepts: Carrier.
  Commodity           NO           Free text.
  VGM                 NO           Non-negative number (kg).

  REMOVED vs previous format:
    Quantity  (removed Sprint 025)
    Currency  (removed Sprint 026)
    DG%       (removed Sprint 026 — replaced by IMDG Code)

================================================================================
  COMPLETE VALIDATION RULES — AFTER SPRINT 026
================================================================================

  All rules apply to both import modes. Runs in bookingImport.service.js validateRow().

  Container Number:    Required. Trimmed, uppercased. Error: "Container Number is required"
  Container Type/Size: At least one required. Resolved vs CT library.
                       Error if missing: "Container Type is required"
                       Error if not found: "Container type 'X' not found in system"
  Container Status:    REQUIRED (Sprint 026 change).
                       Accepted: Full, Empty (case-insensitive, normalized).
                       Error if missing: "Container Status is required"
                       Error if invalid: "Container Status must be Full or Empty"
  POL:                 Required. Matched vs Port library.
                       Error: "POL is required" / "POL 'X' not found in system"
  POD:                 Required. Same as POL. Must differ from POL.
                       Error: "POL and POD cannot be the same port"
  Rate:                Required. Non-negative number.
                       Error: "Rate must be a non-negative number"
  Currency:            REMOVED. Any Currency column silently ignored.
  Hazardous (-> dg):   Optional. Absent/empty = dg=false. Parsed by parseDg().
  IMDG Code:           Conditional. Required if Hazardous=Yes (dg=true).
                       Error: "IMDG Code is required when Hazardous is Yes"
                       If present: trimmed, max 50 chars. Free text.
  VGM:                 Optional. Non-negative number if present.
  Shipper/Consignee/Carrier/Commodity: Optional. Free text.
  Booking Number:      Optional. Auto-generated if blank.

  Booking Import matching (Scope = Voyage + Agent, Key = Container Number):
    FOUND in scope:     rowStatus = 'update' -> UPDATE. Never skipped.
    NOT FOUND in scope: rowStatus = 'valid'  -> CREATE.

  Final Loading matching (Scope = Voyage + Agent, Key = Container Number):
    FOUND in scope:     rowStatus = 'update' -> UPDATE.
    NOT FOUND in scope: rowStatus = 'new'    -> CREATE.

================================================================================
  IMPLEMENTATION NOTES — EXACT CODE CHANGES IN bookingImport.service.js
================================================================================

  NOTE 1: Booking Import matching (previewImport)
  Current code:
    const isDuplicate = importType === 'booking' && !!existingDoc;
    ...if (isDuplicate) rowStatus = 'duplicate';
  Required:
    const isUpdate = !!existingDoc;  // applies to BOTH modes
    ...if (isUpdate) rowStatus = 'update'; (for booking mode, same as finalLoading)
  The 'duplicate' status must become 'update' so the row enters the bulkWrite path.

  NOTE 2: existingBookings query scope (previewImport)
  Current code:
    Booking.find({ containerNumber:{$in:...}, voyageId, isDeleted:false })
  Required:
    Booking.find({ containerNumber:{$in:...}, voyageId, agentId, isDeleted:false })
  Adding agentId limits the match to the current agent's bookings only.

  NOTE 3: Final Loading cancel query scope (saveImport)
  Current code:
    { voyageId, isDeleted:false, status:{$nin:['Cancelled']}, containerNumber:{$nin:...} }
  Required:
    { voyageId, agentId, isDeleted:false, status:{$nin:['Cancelled']}, containerNumber:{$nin:...} }
  Adding agentId ensures only the current agent's bookings are cancelled.
  Other agents' bookings on the same voyage remain untouched.

  NOTE 4: Booking Import 'update' rows in saveImport
  Current code: saveable = rows where _rowStatus in ['valid','new','update']
  Since Booking Import rows now use 'update' (not 'duplicate'), existing containers
  will automatically enter the bulkWrite path. No change needed to saveImport filter.
  The bulkWrite already handles 'update' rows correctly.
