# SPRINT GOAL

Modernize how the system reports on bookings, in two independent pieces:

1. **Migrate the existing Booking Report** off its Layer-2-only,
   partly-dead implementation onto the current dual-layer (Layer 1 +
   Layer 2) architecture, without changing its business purpose.
2. **Add a new, separate report — Booking Revenue Details** — a grouped
   commercial-revenue breakdown by Agent/Commodity/POL/POD, built ONLY
   from Layer 2 Final Loading bookings, with no dependency on
   ManualBooking, Invoice, or Payment.

These two tasks do not share code paths and can be built/shipped
independently of each other.

# ARCHITECTURE DECISIONS

## Decision 1 — Task 1 reuses the Sprint 032 dual-layer pattern, not a new one
`vessel.service.js#getVesselStats` already proved the working shape for
"query Layer 2 and Layer 1 in parallel, merge in JS, one combined
result" (Sprint 032). Task 1's backend rebuild reuses that exact shape
— no new dual-layer convention is invented.

## Decision 2 — Task 1 keeps the report's business purpose unchanged
Per the brief ("keep the current business purpose of the report") and
`docs/booking-report-analysis.md` §4: this stays a filterable operational
booking ledger + count/freight summary. It does not gain Invoice/Payment
awareness — that question was raised in the prior analysis and is
explicitly deferred, not answered, by this sprint.

## Decision 3 — Task 1 fixes the row/summary Cancelled mismatch by
excluding Cancelled from both, consistently
`docs/booking-report-analysis.md` §5 documented that the row list
includes Cancelled bookings (unless the user filters status) while the
summary aggregate silently excludes them. Going forward: **both the row
list and the summary apply the same exclusion** — Cancelled bookings are
shown only when the user explicitly filters `status = Cancelled`;
otherwise both rows and totals agree. This mirrors the "Cancelled is its
own explicit filter, never silently mixed into an unscoped default"
convention already used elsewhere in the codebase (e.g. Booking List's
own status filter).

## Decision 4 — Task 1 replaces `quantity` with nothing (not a
replacement field) for Layer 2, and with `cargoRows[].quantity`/
`totalUnits` for Layer 1
Layer 2 has no unit-count concept since Sprint 025 ("one booking = one
container" — there is nothing to sum beyond a straight document count,
which the report already computes as `count`). Layer 1
(`ManualBooking.totalUnits`) DOES still have a real multi-unit concept.
The "Total Units" KPI is therefore redefined as **Layer 1's
`totalUnits` sum only** — Layer 2 contributes its booking count to
"Bookings", not to "Units". This is the most honest mapping of a real
field to a real KPI, rather than inventing a fabricated combined number
that would conflate two different concepts (containers vs. cargo units).

## Decision 5 — Task 1 drops "Total Slots" entirely
Per the prior analysis, this KPI has had no backing field since Sprint
017. It is removed, not replaced — there is no current concept in either
layer called a "slot."

## Decision 6 — Task 2 is a read-only, Layer-2-only, Final-Loading-only
report, with NO join to Invoice/Payment/ManualBooking
Per the brief's explicit "Data Source" section. This is a hard
constraint, not a starting point for negotiation — Task 2's backend
function must not `require()` `invoice.model.js`, `payment.model.js`, or
`manualBooking.model.js` at all.

## Decision 7 — Task 2 groups on a normalized commodity key, not raw text
`Booking.commodity` is free text (`{ type: String, trim: true, default:
null }` — no enum, no ref). Grouping directly on the raw string would
split what should be one group into several over casing/whitespace
differences ("Rice" vs "rice" vs "RICE"). The grouping key uses a
normalized form (trim + uppercase) of `commodity`, while the row
displayed to the user shows one representative original-case value from
the group (e.g. the first non-null value encountered) — the same
"normalize for matching, display the human original" pattern already
used for container-type matching in `bookingImport.service.js`'s `ctMap`
lookups.

## Decision 8 — the TEUs column reuses `teuResolver.js#resolveTEU()`
unmodified; the 20/40 Qty bucketing is a related, separate report-level
classification (finalized by Decision 10, Revision 3)
`resolveTEU()` extracts the leading numeric length from a container size
string and is used **exactly as-is, unmodified,** for the `TEUs` column
— no change to `teuResolver.js` in this sprint. The 20 Qty / 40 Qty
bucketing reuses that same leading-digit-extraction *idea* (same
normalize-then-match technique) but is its own small classification,
living in the Booking Revenue Details report code, not inside
`teuResolver.js` — because the two questions are not actually the same
question: `resolveTEU()` answers "how many TEU does this container
represent" (a capacity concept, unrelated to and unchanged by this
report), while this report's bucketing answers "does this booking belong
in the 20-column or the 40-column" (a report-presentation concept). Per
Decision 10 (Revision 3, approved), the 40 Qty bucket is explicitly
`40ft`, `40HC`, `44ft`, and `45ft` together — a broader set than
`resolveTEU()`'s own explicit `40 || 45` check, so the two cannot simply
share one function call. This still satisfies "reuse the existing
project architecture wherever possible": the *technique* (leading-digit
extraction, normalize-trim-uppercase-strip-whitespace) is reused
identically; only the bucket-boundary *values* differ, because they
answer genuinely different questions.

## Decision 9 (REVISED, Revision 2/3) — Task 2 groups on exact pricing;
Rate 20/Rate 40 are the Freight Rate shared by all bookings in the
pricing group, never an average
**The Weighted Average recommendation from Revision 1 is rejected and
removed.** Approved business decision: bookings are grouped together
only when Agent, Commodity, POL, POD, Container Type, AND Freight Rate
are all identical. If two bookings agree on Agent/Commodity/POL/POD/
Container Type but carry different Freight Rates — DG surcharges,
different pricing agreements, different container-type pricing, or any
future pricing rule — they are two separate pricing groups and MUST
appear as two separate report rows. Never merged, never averaged.

Consequence: because Container Type and Freight Rate are now part of the
grouping key itself, every booking inside a resulting group shares one
identical container type (hence one identical size bucket) and one
identical freight rate by construction. There is nothing left to
average — Rate 20/Rate 40 are read directly off the group (any booking's
`freightRate` in the group, since by construction they are all equal),
never computed as Revenue ÷ Qty. See the revised Grouping Strategy,
Aggregation Strategy, and Calculation Rules below for the full mechanics.

One structural side effect worth naming explicitly: since a group now has
exactly one container type, a single report row will only ever populate
ONE side of the 20/40 pair — a 20ft pricing group shows `20 Qty`/
`Rate 20`/`Revenue 20` populated and `40 Qty`/`Rate 40`/`Revenue 40` at
zero, and vice versa for a 40ft group. This is the correct, expected
shape of the new design, not a defect — it follows directly from Container
Type being a grouping dimension rather than something summed across
within a row.

## Decision 10 (RESOLVED, Revision 3) — 20 Qty is `20ft` only; 40 Qty
includes `40ft`, `40HC`, `44ft`, AND `45ft`; no separate "45 Qty" column
**Approved business decision — the last open question in this sprint is
now closed.** Container size classification for this report follows the
project's existing TEU-rule philosophy (Decision 8's leading-digit
extraction, the same idea already used by `teuResolver.js`), extended
with an explicit bucket assignment for this report specifically:
```
20 Qty bucket:  20ft
40 Qty bucket:  40ft, 40HC, 44ft, 45ft
```
The Report Structure remains unchanged — no "45 Qty" (or "44 Qty")
column is introduced. A group whose container type is `40HC`, `44ft`, or
`45ft` is simply a 40-bucket pricing group: it populates `40 Qty`/
`Rate 40`/`Revenue 40` exactly like a `40ft` group would, per Decision
9's structural rule (one bucket populated, the other at zero).

**Technical note carried forward from implementation (not a business
decision, a factual observation):** `backend/src/config/constants.js`'s
`CONTAINER_SIZES` enum is currently `['20ft', '40ft', '40HC', '45ft']` —
`'44ft'` is not presently a creatable `ContainerType.size` value at all
(the field is enum-constrained). The 44ft bucket rule is still specified
exactly as approved, so that if `'44ft'` is ever added to that enum in
the future, this report classifies it correctly without any further
change — but no booking can carry that size today, so this branch is
currently unreachable in practice. This does not affect `teuResolver.js`
itself, which is not modified by this sprint (its own `len === 40 ||
len === 45` TEU-value rule is separate from — and untouched by — this
report's own 20/40 bucket-assignment rule; see Decision 8's note that
the TEUs column and the Qty-bucket columns are two different
calculations reusing the same underlying size-parsing idea, not the same
function call for both purposes where they'd need to disagree).

# TASK 1 — BOOKING REPORT MIGRATION

## Business Description
Unchanged from `docs/booking-report-analysis.md` §4: a filterable ledger
of booking activity (by voyage/agent/status/service/date) with a
count + freight summary, for Operations/Finance review. The only change
is that "booking activity" now correctly means both layers, and the
summary numbers are all real (no dead fields).

## Technical Analysis (recap of `docs/booking-report-analysis.md`,
carried forward as the basis for this plan)
- Current implementation: `reports.service.js#getBookingReport` queries
  `Booking` (Layer 2) only; `ManualBooking` is never referenced.
- `quantity` is summed and displayed but does not exist on `Booking`
  since Sprint 025/026 — always 0/blank.
- `totalSlots` is displayed on the frontend but was never returned by
  the backend since Sprint 017.
- `containerNumber` (the system's primary booking match key since
  Sprint 021) is never included in the report's row projection.
- The row list and summary aggregate disagree on Cancelled inclusion.
- No pagination controls exist despite the backend supporting
  `page`/`limit`/`total`.
- No export is wired for this report (true of every report in the
  module).

## Backend Tasks

# TASK 2 — BOOKING REVENUE DETAILS REPORT

## Business Description
A commercial revenue breakdown, not an operational ledger: "for each
Agent/Commodity/POL/POD combination, how many 20ft and 40ft containers
moved, how many TEUs and how much VGM did that represent, and how much
revenue did it generate, broken out by container size and totaled."
This answers a different question than Task 1's report (activity
listing) or the Agent Financial Account (invoicing/payment state) — it
is a pure freight-revenue-by-lane-and-commodity view, scoped exclusively
to bookings that have actually reached Final Loading (i.e. cargo that
actually moved, not still-pending reservations).

**Business clarification (Revision 3, Final Business Update #2) — every
report row represents exactly ONE commercial pricing group.** A pricing
group is uniquely identified by all six of: Agent, Commodity, POL, POD,
Container Type, and Freight Rate. Bookings belonging to different
pricing groups — even if they agree on every other dimension — must
never be merged into the same row. This is the report's core business
intention and governs every calculation below: the report does not show
"average commercial activity per lane," it shows "every distinct real
price actually agreed for that lane," one row per distinct price.

## Required Analysis — Does Layer 2 Contain Enough Information?

Checked directly against `booking.model.js`'s current fields:

| Report need | Field | Present on Booking? | Note |
|---|---|---|---|
| Agent grouping key | `agentId` | Yes (required, ref Agent) | |
| Commodity grouping key | `commodity` | Yes, but free text, nullable | Needs normalization for grouping (Decision 7); a booking with `commodity: null` needs an explicit "Uncategorised"-style bucket, same pattern already used in `export.service.js`'s expense-category grouping |
| POL grouping key | `polId` | Yes (required, ref Port) | |
| POD grouping key | `podId` | Yes (required, ref Port) | |
| Container size (20/40 bucketing) | `containerTypeId` → `ContainerType.size` | Yes, via populate/lookup | `size` is an enum (`20ft`,`40ft`,`40HC`,`45ft`) on `ContainerType`, not stored directly on `Booking` |
| TEU calculation | derived from `ContainerType.size` | Yes | Via `teuResolver.js#resolveTEU()` (Decision 8) — already exists, reused as-is |
| VGM | `vgm` | Yes, nullable Number | MongoDB `$sum` naturally treats null/missing as 0 contribution — no special-casing needed |
| Rate / Revenue | `freightRate` / `totalFreight` | Yes | Identical values per booking today; `freightRate` is also now a grouping-key dimension itself (Decision 9, Revision 2) |
| Status filter | `status` | Yes (`BOOKING_STATUS` enum, includes `'Final Loading'`) | |

**Conclusion: every column the brief lists can be generated from the
current Layer 2 Booking model plus its existing `ContainerType`
reference — no field is missing, and nothing needs to be invented.**

**Gap identified and now resolved (Decision 10, Revision 3):** the
report structure has no column for 45ft bookings. Approved resolution:
45ft (and 44ft, 40HC) bookings are not excluded and do not need their
own column — they are 40-bucket pricing groups, populating `40 Qty`/
`Rate 40`/`Revenue 40` exactly as a `40ft` group would.

## Grouping Strategy (REVISED, Revision 2/3 — exact pricing groups)
**Each report row represents one commercial pricing group, uniquely
identified by Agent + Commodity + POL + POD + Container Type + Freight
Rate (Revision 3, Final Business Update #2). Bookings belonging to
different pricing groups are never merged.** Group key (six dimensions,
per the approved business decision):
`(agentId, normalizedCommodity, polId, podId, containerTypeId,
freightRate)`, where `normalizedCommodity = (commodity || '').trim()
.toUpperCase()` (Decision 7, unchanged). Using the booking's own
`containerTypeId` reference (not just a derived size bucket) as the
grouping dimension naturally captures "different container pricing"
(e.g. a Reefer and a Dry container of the same size legitimately pricing
differently) without any extra logic — two bookings only fall in the
same group if they reference the exact same `ContainerType` document.
`freightRate` is compared for exact equality as stored (a plain Number
comparison — no rounding/tolerance logic is introduced; if this ever
proves too strict in practice, that is a future decision, not one made
here).

Each distinct combination of all six values becomes exactly one report
row — this is a genuine change from Revision 1's four-dimension grouping.
Two bookings identical on Agent/Commodity/POL/POD/Container Type but
carrying different Freight Rates now produce two separate rows, per the
approved business reason (DG cargo, different pricing agreements,
different container pricing, future pricing rules). The displayed
"Commodity" text for a group is still the first non-empty original-case
`commodity` value encountered (Decision 7). Only Layer 2 bookings with
`status === 'Final Loading'` and `isDeleted: false` participate — nothing
else is queried (Decision 6, unchanged).

## Aggregation Strategy (REVISED, Revision 2/3)
Because Container Type and Freight Rate are now grouping-key dimensions,
every booking inside one resulting group already shares one identical
container type and one identical freight rate — there is no
within-group size mixing or rate variance left to reconcile. Per group,
accumulate:
- `qty20` — count of the group's bookings, IF the group's shared
  container size is `20ft` (Decision 10, approved); otherwise 0 for this
  group
- `qty40` — count of the group's bookings, IF the group's shared
  container size is `40ft`, `40HC`, `44ft`, or `45ft` (Decision 10,
  approved — all four are one bucket); otherwise 0 for this group
- `teus` — `resolveTEU(size).teu` × the group's booking count, via
  `teuResolver.js#resolveTEU()` unmodified (every booking in the group
  shares the same size, so this is no longer a mixed-size sum)
- `vgm` — sum of `booking.vgm` across the group's bookings (null treated
  as 0)
- `freightRate` — the group's own shared rate, read directly (any
  booking's `freightRate` in the group — they are all equal by
  construction) — this is the value described everywhere in this report
  as "the Freight Rate shared by all bookings in the pricing group"
  (Revision 3 rate-description wording)
- `revenue20` — `qty20 × freightRate` if the group is a 20ft group, else 0
- `revenue40` — `qty40 × freightRate` if the group is a 40/40HC/44ft/45ft
  group, else 0

This can be implemented either as a single MongoDB aggregation pipeline
(a `$group` on the six-part key, with a `$lookup` to `containertypes`
first to resolve `containerTypeId` into its `size`) or as a plain
`Booking.find(...).populate('containerTypeId')` followed by an in-memory
JS reduce — the same "fetch, then merge/group in JS" shape already used
by `agent.service.js#getAgentFinancialAccount` and
`vessel.service.js#getVesselStats`. Recommended: the in-memory approach,
specifically so `teuResolver.js#resolveTEU()` can be called directly and
unmodified (a Mongo-side `$switch` would otherwise have to duplicate
that same size-parsing logic in aggregation-pipeline syntax, violating
"reuse the existing project architecture").

## Calculation Rules (every column) — REVISED, Revision 2/3
| Column | Rule |
|---|---|
| Sr | Row sequence number, generated at render/response time — not stored data |
| Agent | `agentId.agentName` (or code) for the group |
| Commodity | first non-empty original-case `commodity` seen in the group (grouping itself uses the normalized form, Decision 7) |
| POL | `polId.name` for the group |
| POD | `podId.name` for the group |
| 20 Qty | the group's booking count, IF the group's (single, shared) container size is `20ft` — otherwise 0 (Decision 10, approved) |
| 40 Qty | the group's booking count, IF the group's (single, shared) container size is `40ft`, `40HC`, `44ft`, or `45ft` — otherwise 0 (Decision 10, approved — all four count as one bucket, no separate "45 Qty"/"44 Qty" column) |
| TEUs | `resolveTEU(size).teu × group booking count`, via `teuResolver.js#resolveTEU()` unmodified |
| VGM | sum of `booking.vgm` across the group's bookings, null treated as 0 |
| Rate 20 | **The Freight Rate shared by all bookings in the pricing group** — read directly, NEVER averaged or derived — shown only when the group is a 20ft group (0/blank otherwise) |
| Rate 40 | **The Freight Rate shared by all bookings in the pricing group** — read directly, NEVER averaged or derived — shown only when the group is a 40/40HC/44ft/45ft group (0/blank otherwise) |
| Revenue 20 | `20 Qty × Rate 20` |
| Revenue 40 | `40 Qty × Rate 40` |
| Total Revenue (USD) | `Revenue 20 + Revenue 40` — labeled USD per the existing system-wide assumption that `totalFreight`/`freightRate` are single-currency figures (Booking has no currency field, same inherited assumption already noted in `docs/invoice-behavior-analysis.md`) |

Because grouping now includes Container Type and Freight Rate (Decision
9), a single row's 20-side and 40-side columns are never both populated
— exactly one pair (`Qty`/`Rate`/`Revenue`) is non-zero per row, per the
structural note under Decision 9.

## Backend Tasks
- New file `backend/src/modules/reports/reports.service.js` function
  `getBookingRevenueDetails({ agentId, voyageId, roundId, dateFrom,

  - Query: `Booking.find({ status: 'Final Loading', isDeleted: false,
    ...filters }).populate('agentId', 'agentCode agentName')
    .populate('polId', 'name').populate('podId', 'name')

  - Group in JS on the six-part key `(agentId, normalizedCommodity,
    polId, podId, containerTypeId, freightRate)` per the revised
    Grouping/Aggregation Strategy above — NOT the four-part key from
    Revision 1.
  - Return `{ rows, grandTotal }`, `grandTotal` summing every numeric
    column across all groups (qty20, qty40, teus, vgm, revenue20,
    revenue40, totalRevenue) — no grand-total "rate" of any kind (average
    or otherwise); only sums are totaled, matching the pattern
    `getRevenueReport`'s existing `grandTotal` already uses.
- `backend/src/modules/reports/reports.controller.js` — new

## Acceptance Criteria (Task 2) — REVISED, Revision 2
1. The report queries ONLY Layer 2 `Booking` documents with `status:
   'Final Loading'` — confirmed by code review that
   `manualBooking.model.js`, `invoice.model.js`, and `payment.model.js`
   are never required by this report's backend function.
2. Each report row represents one distinct (Agent, Commodity, POL, POD,
   Container Type, Freight Rate) combination — never one row per
   booking, and never one row merging two different freight rates.
3. Two bookings that agree on Agent/Commodity/POL/POD/Container Type but
   have different Freight Rates always appear as two separate rows —
   confirmed by a test case exercising exactly this scenario.
4. Commodity grouping is case/whitespace-insensitive (Decision 7) —
   confirmed by a test case with mixed-case commodity text across
   otherwise-identical bookings (same rate, same container type)
   producing exactly one group.
5. TEUs uses `teuResolver.js#resolveTEU()` unmodified; 20 Qty / 40 Qty
   use the report's own size-bucket classification (Decision 10,
   approved: 20ft → 20 Qty; 40ft/40HC/44ft/45ft → 40 Qty) — confirmed by
   code review that `teuResolver.js` itself was not modified and that
   the two calculations are kept separate, per Decision 8.
6. Rate 20 and Rate 40 are always the Freight Rate shared by all
   bookings in the pricing group — read directly from the grouped
   bookings, never computed as an average, a weighted average, or any
   other derived
   statistic. Confirmed by code review that no division of Revenue by
   Qty (or any similar averaging formula) exists anywhere in this
   report's rate calculation.
7. Revenue 20 = 20 Qty × Rate 20, and Revenue 40 = 40 Qty × Rate 40, for
   every row — both being simple multiplications against the row's own
   real rate, not the other way around.
8. Total Revenue always equals Revenue 20 + Revenue 40, for every row
   and for the grand total.
9. `40ft`, `40HC`, `44ft`, and `45ft` container types all populate
   `40 Qty`/`Rate 40`/`Revenue 40` identically as one bucket (Decision
   10, approved) — confirmed by a test case covering all four size
   values. No "45 Qty" or "44 Qty" column exists anywhere in the report.
10. No change to `capacity.service.js`, `teuResolver.js`'s own rule set,
    `booking.model.js`, `manualBooking.model.js`, `invoice.model.js`, or
    `payment.model.js`.

  `freightRate` for exact equality as a plain Number. This is expected
  to be safe in practice (rates are entered as fixed decimal values, not

  something this plan invents a tolerance/rounding rule for.
