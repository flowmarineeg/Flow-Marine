# Sprint 039 — Dashboard Architecture & KPI Planning
Status: ✅ APPROVED (Revision 2) — approved with 4 required refinements,
applied below: (1) a Global Dashboard Filter Bar (Round/Voyage/Service/
Agent/Date Range) shared across widgets via one context, applied by
each widget only where it's relevant to that widget's own data; (2) the
widget architecture is now explicit — Dashboard → Sections →
Independent Widgets → Charts/Cards/Tables, every widget independently
reusable; (3) a Quick Actions section for the most common operational
actions; (4) sections load independently — no single blocking
data-fetch gates the whole page, each section owns its own query/
loading state. Implementation proceeds immediately following this
revision.
Every KPI, chart, and API mapping below was checked against the actual
current state of the code (services, models, reports) — not assumed
from memory or from what claude.md's older Sprint 020/022 dashboard
description implies. Where the CURRENT dashboard already deviates from
"reuse only, never duplicate," that deviation is called out explicitly,
because Sprint 039's own stated objective — "the Dashboard must NEVER
duplicate business logic" — cannot be honestly planned without first
admitting the existing Dashboard already breaks that rule in three
places (Section 3.1).

# 1. EXECUTIVE SUMMARY

The reporting layer (Sprints 022, 034, 035, 036, 037, 038) now has a
complete, self-consistent set of business rules: Layer 1/Layer 2
booking architecture, a single Capacity Engine, a Layer-2/Final-Loading
Revenue rule, a config-driven Voyage Cost/Other Voyage Cost
classification, and a Round/Voyage/Port Expense scope. The Dashboard
(`dashboard.service.js`), by contrast, **predates every one of those
sprints** and currently computes its own, separate versions of several
of the same numbers — using older, now-inconsistent rules. Concretely,
confirmed by reading the current `dashboard.service.js`:

- Its 30-day revenue figure (`revenue30d`) aggregates `Booking` on
  `status: 'Confirmed'` — not Final Loading — the exact "Revenue"
  definition Sprint 038 just finished eliminating from every other
  report.
- Its 6-month trend and its "Revenue by Service" chart both aggregate
  Booking on `status: {$ne: 'Cancelled'}` (Pending+Confirmed+Final
  Loading combined) — again, the pre-Sprint-038 revenue population, not
  the current one.
- Its Fleet Utilisation widget (`getFleetUtilisation`, otherwise the
  **one part of today's Dashboard that already does this correctly** —
  it calls `computeRoundCapacity()` directly, the exact reuse pattern
  this sprint wants everywhere) reads `d.totals?.totalBookedTEU`, a
  field that does not exist on the Capacity Engine's payload (the real
  field is `totals.totalLoadedTEU`) — the same stale-field bug class
  Sprint 037/038 already found and fixed in three other reports.
- `totalExpenses` is a raw `Expense.countDocuments({})` — a count, not a
  sum, with no classification, no scope, no currency awareness at all.

**This sprint's plan therefore has two parts, not one:** (1) a forward
KPI/chart/drill-down catalog for the "operational command center" the
prompt asks for, and (2) an explicit realignment of the Dashboard's
*existing* revenue/utilisation figures onto the exact same
already-approved rules and functions the rest of the system now uses —
because building new KPIs on top of a Dashboard that still privately
disagrees with Revenue Report about what "revenue" means would
immediately recreate the Sprint 037 cross-report inconsistency problem,
one layer up.

**Core architectural stance carried through this entire plan:** the
Dashboard adds **zero** new aggregation pipelines against `Booking`,
`ManualBooking`, or `Expense` for any figure a Report or Service
function already computes. Every KPI in Section 5 is mapped to an
existing service function it calls directly; where no such function
exists yet, it is listed once in Section 11 (Missing APIs) rather than
invented ad hoc per KPI.

# 2. DASHBOARD GOALS

1. Be the single, at-a-glance operational overview of Rounds, Voyages,
   Capacity, Revenue, Expenses, Profitability, and Bookings — reusing
   the exact rules Sprints 022–038 already established for each of
   those domains.
2. Never compute a number a Report doesn't already compute the same
   way. If the Dashboard and a Report ever disagree, that is a defect,
   not an acceptable design tradeoff (this is the direct lesson of
   Sprint 037).
3. Every KPI card is a **summary + navigation surface**, not a
   destination in itself — clicking through always lands on the
   already-existing Report or detail page that has the full picture
   (Section 7, Drill-down Map).
4. Read-only. The Dashboard issues no writes, ever (unchanged from the
   current architecture — confirmed: `dashboard.controller.js` exposes
   only two GET actions today, and this plan adds none of any other
   verb).
5. Stay SuperAdmin-only by role identity, exactly as documented in
   claude.md Section 6 ("Dashboard is SuperAdmin-only... enforced by
   isSuperAdmin... NOT enforced through the permission system") —
   unchanged by this sprint.

# 3. DASHBOARD ARCHITECTURE

## 3.1 Current State (confirmed by reading the code, not assumed)

- `dashboard.service.js#computeStats()` — one large `Promise.all` of
  ~20 counts/aggregates directly against `Vessel`, `Round`, `Voyage`,
  `Booking`, `ManualBooking`, `Agent`, `Invoice`, `Expense`, `AuditLog`.
  Cached 90s (`cache.js`, key `dashboard:stats`), matching claude.md's
  documented TTL.
- `dashboard.service.js#getFleetUtilisation()` — the one function
  already following this sprint's intended pattern: it calls
  `capacity.service.js#computeRoundCapacity(roundId)` per Active round
  and reshapes the result. **This is the reference implementation every
  other KPI in this plan should imitate.**
- Frontend: `app/(dashboard)/dashboard/page.jsx` — a single monolithic
  page (not a `modules/dashboard/` component tree like every other
  feature in this codebase), Chart.js with targeted registration (per
  claude.md), `enabled: isSuperAdmin` gate on the stats query.
- **Confirmed duplication/drift** (the "must not repeat" list for this
  sprint):
  1. `revenue30d` — `Booking.aggregate({status:'Confirmed', ...})`.
     Should be Layer 2 + Final Loading, matching Revenue Report/Voyage
     Profitability (Sprint 038's now-final rule).
  2. `monthlyTrend`/`revByService` — both aggregate on
     `status:{$ne:'Cancelled'}` (Pending+Confirmed+Final Loading
     combined). Same drift as #1.
  3. `getFleetUtilisation`'s `totalBookedTEU: d.totals?.totalBookedTEU`
     — this field does not exist on `computeRoundCapacity()`'s payload
     (confirmed: the real field is `totals.totalLoadedTEU`); this has
     been silently rendering `0` on the Fleet Utilisation widget the
     same way Sprint 037/038 found on three separate report pages.
  4. `totalExpenses` — `Expense.countDocuments({})`, a bare count with
     no sum, no classification, no scope — not wrong, but not useful
     for a "Total Expenses" KPI a user would expect to be a currency
     figure.

## 3.2 Target Architecture

```
Frontend (dashboard/page.jsx, restructured into sections)
        │
        │  read-only GET calls only
        ▼
dashboardService (frontend/src/services/dashboard.service.js)
        │
        ▼
GET /dashboard/stats            ← existing, corrected in place
GET /dashboard/fleet-utilisation ← existing, corrected in place
GET /reports/*                  ← EVERY existing report endpoint,
                                    called directly by new dashboard
                                    widgets wherever a KPI's numbers
                                    already come from a report
        │
        ▼
reports.service.js / capacity.service.js / agent.service.js /
vessel.service.js / expenseType.service.js
        │
        ▼
Mongoose models (unchanged — this sprint touches zero schemas)
```

The Dashboard becomes a **thin composition layer**: `dashboard.service.js`
keeps doing what `getFleetUtilisation` already does today (call another
service's exported function, reshape for widget consumption, cache) —
it does not gain new `Booking.aggregate()`/`Expense.aggregate()` calls
of its own for anything a Report already computes. Where a KPI's number
already has a dedicated report endpoint (e.g. Revenue, Expense
classification, Voyage Profitability), the **frontend widget calls that
report endpoint directly** (same as how `RoundPnlReport.jsx` already
calls `reportsService.getRoundPnL()`) rather than the backend
`dashboard.service.js` re-fetching and re-shaping it — this avoids a
second server-side hop and a second cache layer for data a report
endpoint already caches/computes (e.g. `getRoundPnL`'s classification
map, `capacity.service.js`'s own 60s cache).

## 3.3 Global Dashboard Filter Bar (Refinement 1)

One shared client-side context — `DashboardFilterContext` — holds
`{ roundId, voyageId, serviceId, agentId, dateFrom, dateTo }` and is
provided once at the Dashboard page's root, above every Section. A
single `DashboardFilterBar` widget (itself just another widget in the
Section 3.4 tree, rendered once at the top of the page, not duplicated
per-section) reads and writes this context; every other widget reads
from it via a hook (`useDashboardFilters()`) and decides for itself
which of the five fields are relevant to its own data — exactly the
same "the report defines what it needs" principle already used
elsewhere (e.g. `RoundPnlReport.jsx` requires `roundId`, Revenue Report
does not). Concretely:
- Round/Voyage cascade the same way every existing report page's own
  Round→Voyage dropdown already cascades (reused convention, not a new
  one).
- Widgets whose backing report is inherently Round-scoped (Financial
  section's Voyage Cost/Profit/Margin, Performance's Best/Lowest
  Voyages) render an explicit "Select a Round to see this" empty state
  when `roundId` is unset — never a silent zero or a fabricated
  fleet-wide fallback (ADR-3 already forbids inventing a cross-round
  aggregate).
- Widgets whose backing report is NOT Round-scoped (Bookings section's
  status counts, Revenue Report-backed widgets, Expense Report-backed
  widgets) apply whichever subset of Service/Agent/Date Range their own
  existing report endpoint already accepts as query params, and simply
  ignore Round/Voyage if set — no widget invents a new filter dimension
  its underlying report endpoint doesn't already support.
- The filter bar itself does not fetch anything — it is pure shared
  state. No new "resolve these five filters into one payload" backend
  endpoint is introduced; each widget still calls its own existing
  endpoint with whichever subset of filters it accepts, per ADR-1's
  two-tier rule.

## 3.4 Widget Architecture (Refinement 2)

```
Dashboard (app/(dashboard)/dashboard/page.jsx)
   │
   ├── DashboardFilterProvider (context, Section 3.3)
   │
   ▼
Dashboard Sections (frontend/src/modules/dashboard/sections/*.jsx)
  Operations · Commercial · Financial · Bookings · Performance · Alerts
   │  (one Section = one layout region; a Section owns no data itself —
   │   it only arranges its own Widgets and gives them a heading)
   ▼
Independent Widgets (frontend/src/modules/dashboard/widgets/*.jsx)
  e.g. ActiveRoundsWidget, RevenueTrendWidget, VoyageCostWidget,
  TopAgentsWidget, OverbookedVoyagesWidget, QuickActionsWidget
   │  (one Widget = one KPI/chart/table + its OWN useQuery, its OWN
   │   loading/empty/error state, reading only the filter fields it
   │   needs from useDashboardFilters()). A Widget takes no required
   │   props beyond an optional className — it is fully self-contained
   │   and could be dropped onto any other page unchanged (e.g. reused
   │   directly on a future Vessel/Agent detail page), satisfying
   │   "every widget should be independently reusable."
   ▼
Charts / Cards / Tables (presentational only — reused from existing
  primitives: reportHelpers.jsx's ReportStatCard, Chart.js wrappers
  already proven on report pages, plain tables) — these render
  whatever data their owning Widget already fetched; they hold no
  query, no filter-reading logic, no navigation logic of their own.
```

This is a strictly one-way dependency chain — a Section never reaches
into a Widget's internals, and a Widget never reaches into another
Widget's state (only the shared `DashboardFilterContext`, which is
read-only from every Widget's perspective except the one
`DashboardFilterBar` widget that owns it).

## 3.5 Quick Actions (Refinement 3)

A dedicated `QuickActionsWidget`, placed directly under the Filter Bar
(above Operations), one button per common operational action — reusing
each action's own already-existing create route, never a new modal or
a new creation flow:
- New Booking → `/bookings/new` (and `/bookings/new-manual` for Layer 1)
- New Expense → `/expenses/new`
- New Invoice → `/invoices/new`
- New Round → `/rounds` (opens the existing create form there)
- Import Bookings → `/bookings/import`
Each button is gated by the same `can(module, 'create')` permission
check every existing "+ New X" button on its own list page already
uses (`usePermission()`'s `can()`), reusing that convention rather than
inventing a new one — even though the Dashboard itself is
SuperAdmin-only, the underlying permission check is kept for
consistency and in case that constraint is ever relaxed.

## 3.6 Independent Section Loading (Refinement 4)

No Section or Widget waits on any other Section's data. Concretely:
- There is no single "dashboard bootstrap" query that every Section
  depends on. `GET /dashboard/stats` and `GET /dashboard/fleet-
  utilisation` remain two separate queries (as today), and every
  Tier 2 widget (Section 3.3's `reportsService.getX()` calls) is its
  own independent `useQuery`, each with its own `isLoading`/`isError`
  state rendered ONLY inside that widget's own card boundary.
- A slow or filter-incomplete widget (e.g. Financial section's
  Round-scoped widgets before a Round is selected) shows its own
  loading skeleton or empty state without blocking Operations/
  Bookings/Commercial widgets that have everything they need.
- This requires no new data-fetching library or pattern — React
  Query's existing per-`useQuery` independence already provides this;
  the change is purely architectural discipline (Section 9 Frontend
  Impact): no component higher than an individual Widget is allowed to
  gate rendering on more than its own single query.

## 3.7 Two-Tier Data Access Pattern (ADR-1, expanded)

1. **Tier 1 — genuinely dashboard-native counts/statuses** (Active
   Vessels, Active/Planned/Completed Rounds, booking status counts,
   invoice status counts, recent activity) stay in
   `dashboard.service.js#computeStats()`, exactly as today — these are
   simple `countDocuments()`/status-group-by calls with no business
   rule to duplicate (a Round's `status` field, a Booking's `status`
   field — reading a status value is not "business logic," it's a
   field read).
2. **Tier 2 — anything with a business RULE behind it** (Revenue, Voyage
   Cost/Other Voyage Cost, Capacity/Utilisation, Profit, Agent Financial
   Summary) is fetched from the exact existing report/service function
   that already encodes that rule, either backend-side (mirroring
   `getFleetUtilisation`'s existing pattern) or frontend-side (the
   widget calls the report endpoint directly). No Tier 2 number is ever
   computed by a second, parallel aggregation pipeline anywhere in the
   Dashboard's own code.

# 4. DASHBOARD SECTIONS

Six sections, each mapped to KPI Catalog entries in Section 5:

1. **Operations** — Active Rounds, Active Voyages, Vessel Utilisation,
   Capacity Utilisation, Overbooked Voyages, Available Capacity, Port
   Activity.
2. **Commercial** — Total Revenue, Revenue This Month, Revenue by
   Service, Revenue by Agent, Revenue Trend.
3. **Financial** — Total Expenses, Voyage Cost, Other Voyage Cost,
   Profit, Profit Margin, Revenue vs Expenses.
4. **Bookings** — Layer 1 Bookings, Layer 2 Bookings, Final Loading
   Bookings, Pending Bookings, Confirmed Bookings.
5. **Performance** — Top Routes, Top Services, Top Agents, Best/Lowest
   Performing Voyages.
6. **Alerts** — Capacity Warnings, Overbooked Voyages, Missing Final
   Loading, Voyages Near Capacity, Operational Warnings.

Section ordering on the page (top to bottom): Operations → Commercial →
Financial → Bookings → Performance → Alerts — operational state first
(what's happening right now), money second (what it's worth), booking
mix third (what's behind the money), performance leaderboards fourth,
alerts last as a dedicated "things needing attention" footer section —
mirroring the existing page's own layout convention (KPI cards, then
charts, then a fleet-utilisation/warnings area at the bottom, confirmed
by the current `page.jsx`'s icon imports and section ordering).

# 11. MISSING APIs

Only two genuinely new pieces of backend surface are identified across
the entire KPI/Chart catalog — both are additive, both reuse an
existing service's own logic, neither introduces a new aggregation
rule:

1. **Fleet-wide Port Activity** (Operations 5.1) — no existing endpoint
   answers "which ports, across ALL active rounds, have the most
   Voyage-Cost activity right now." `getRoundPnL`'s `byPort` breakdown
   is inherently per-round. Recommended shape for a future
   implementation sprint: a new, small
   `dashboard.service.js#getPortActivity()` that loops the same Active
   rounds `getFleetUtilisation` already fetches, calls
   `getRoundPnL({roundId})` for each (an existing function, already
   cached per-round-pnl request pattern — no new aggregation), and
   merges the `byPort` arrays — same "loop existing rounds, call an
   existing per-round function, merge in JS" shape `getFleetUtilisation`
   already uses for capacity. New route:
   `GET /dashboard/port-activity`.
2. **Missing Final Loading** (Alerts 5.6) — no existing function
   cross-references a voyage's `eta` against its bookings' status. This
   is a genuinely new question ("which voyages are overdue for Final
   Loading"), not a reframe of an existing one. Recommended shape: a
   new `capacity`-adjacent or `bookings`-adjacent function (exact home
   module TBD at implementation time — either
   `booking.service.js#getVoyagesMissingFinalLoading()` or a Dashboard-
   local Tier 1 query) — `Voyage.find({eta: {$lt: now}, status: {$nin:
   ['Completed','Cancelled']}})` joined against a count of that
   voyage's non-Final-Loading, non-Cancelled bookings (both layers).
   New route: `GET /dashboard/missing-final-loading`.

**Revenue Trend / Profit Trend / Monthly Profit charts (Section 6)**
are NOT listed here as missing APIs — they are achievable today by
calling existing endpoints multiple times (once per month/round) from
the frontend, or by a small, rule-preserving date-bucketing addition
to `getRevenueReport` if per-bucket round trips prove too slow (see
Risks) — this is optimization, not a missing capability, so it is not
counted as a new API requirement.

# 12. ARCHITECTURE DECISIONS (ADR)

**ADR-1 — Two-tier data access (Section 3.3) is the organizing
principle for every KPI in this plan.** Tier 1 (simple counts/status
reads) stays in `dashboard.service.js`; Tier 2 (anything with a
business rule) is fetched from the exact existing report/service
function, either backend-composed (mirroring `getFleetUtilisation`) or
frontend-fetched directly from the report endpoint. This single rule
is what makes "never duplicate business logic" enforceable rather than
aspirational — every KPI in Section 5 was checked against it.

**ADR-2 — The Dashboard's existing revenue/utilisation drift (Section
3.1) is fixed as part of this sprint's baseline, not deferred.**
Building new Commercial/Financial KPIs on top of a `revenue30d` figure
that still uses the pre-Sprint-038 "any non-Cancelled" rule would
reintroduce, one layer higher, the exact cross-report inconsistency
Sprint 037 spent an entire sprint finding and Sprint 038 spent an
entire sprint fixing. This is treated as a required baseline
correction, cited under Backend Impact, not as new scope creep.

**ADR-3 — Round-scoped Financial/Performance KPIs are not force-fit into
a fleet-wide figure.** `getRoundPnL` is deliberately round-scoped
(Sprint 035 ADR-1); this plan does not invent a "Total Profit (all
rounds, all time)" card by re-summing `getRoundPnL` across every round
in the system, because that re-introduces exactly the kind of
independent, parallel aggregation this sprint's own objective forbids.
Where the business wants a true fleet-wide profit figure, that is a new
report-level decision for a future sprint, not something the Dashboard
should quietly compute on its own.

**ADR-4 — `getFleetUtilisation` is the reference pattern for every new
Tier 2 backend composition.** It already does exactly what ADR-1
prescribes (call an existing service function per round, reshape,
return) — new backend work in this sprint's eventual implementation
(the `totalBookedTEU` fix, the two Section 11 additions) follows its
exact shape rather than inventing a new composition style.

**ADR-5 — Widgets that already have a natural home in an existing
report call that report's own service/endpoint directly from the
frontend, rather than proxying through `dashboard.service.js`.** This
avoids a second cache layer and a second data-shaping step for data a
report endpoint already owns (e.g., Revenue/Expense/Voyage
Profitability widgets hit `/reports/*` directly, the same way the
report pages themselves do) — only genuinely dashboard-native
aggregates (Tier 1 counts, and Tier 2 items with no natural single-
report home, like Fleet Utilisation spanning multiple rounds) are
composed server-side inside `dashboard.service.js`.

# 13. RISKS

1. **Per-bucket round-trip cost for trend charts.** Building Revenue
   Trend/Profit Trend by calling an existing endpoint once per month/
   round (rather than one new bucketed backend aggregate) could be slow
   for a long history. Mitigation: if implementation-time testing shows
   this is too slow, the fallback is a small, rule-preserving date-
   bucket addition to `getRevenueReport` (same match condition, just
   grouped by month too) — not a new, independently-defined revenue
   rule.
2. **Fixing `revenue30d`/`monthlyTrend`/`revByService`'s match condition
   changes a number that has been showing on the Dashboard until now**
   — the same "visible discontinuity, not a bug" risk Sprint 038 already
   flagged for Revenue Report itself; it applies identically here and
   should be communicated the same way.
3. **`getFleetUtilisation`'s reshape carrying more per-round data
   (warnings, per-voyage utilisationPct)** slightly increases the
   payload size of an already-cached endpoint — low risk, bounded by
   the same 60s capacity cache already in place.
4. **Section 11's two new endpoints, if approved for implementation,
   are genuinely new code paths** (not pure reuse) — they must be
   reviewed with the same rigor as any new report logic, since they are
   the one place in this whole plan where "no duplicated business
   logic" needs a freshly-written, correctly-scoped implementation
   rather than a call-through.
5. **A monolithic dashboard page being split into a `modules/dashboard/`
   component tree (Section 9)** is a nontrivial frontend refactor
   touching a page every SuperAdmin sees on login — needs the same
   manual QA rigor Sprint 038 applied to its Round Capacity Report
   rebuild (empty states, loading states, permission-gated rendering).
