================================================================================

  REVISION 1 — BUG-010
  ─────────────────────
  Cancelled voyages must be excluded from the capacity chain COMPLETELY:
    - Excluded from the voyage sequence.
    - Excluded from capacity calculations.
    - Excluded from onboard calculations.
    - Excluded from remaining capacity calculations.
  A cancelled voyage is not a physical sailing and must never participate in
  the cargo-flow calculation. (Confirms/reinforces the original BUG-010 fix —
  no change to the fix itself, but the filter must be applied consistently at
  every point voyages feed into capacity, onboard, and remaining-capacity math,
  not only the initial Voyage.find query.)

  REVISION 2 — BUG-003
  ─────────────────────
  The original plan's "load-only, carry TEU to end of round" fallback is
  REJECTED. Replaced with:
    - Do NOT create artificial load-only events.
    - Do NOT keep unresolved cargo onboard until the end of the round.
    - If a Manual Booking's POL/POD cannot be resolved: emit a warning AND
      EXCLUDE the booking from capacity calculation entirely.
    - Never create synthetic cargo-flow events (no load event, no discharge
      event, no phantom pair).
  This supersedes BR-3 and the BUG-003 fix/testing sections below.

  REVISION 3 — BUG-004
  ─────────────────────
  Voyage resolution must NOT use a global port map keyed by POL/POD — repeated
  ports within the same round make a global map ambiguous. Instead the
  algorithm must be voyage-based:
    1. Anchor the booking using its actual `booking.voyageId`.
    2. Start from that voyage.
    3. Walk forward through the voyage sequence.
    4. Find the first voyage whose destination matches the booking's POD.
    5. Use that voyage as the discharge point.
  This applies to both computeRoundCapacity's L1/L2 discharge resolution and
  computeVoyagePreview's dischargeIdx resolution — neither may use a global
  portAsTo/portAsFrom map for this purpose. This supersedes the BUG-004
  "portAsTo" map-based approach described below.

================================================================================
  ROOT CAUSE ANALYSIS
================================================================================

  BUG-001 — Silent cache invalidation failure in import
  ─────────────────────────────────────────────────────
  In bookingImport.service.js saveImport(), the roundId for cache invalidation is
  looked up AFTER all inserts/updates complete, inside a try/catch that swallows
  every error. If the Voyage lookup fails, cache is not invalidated and the system
  serves stale capacity for up to 60 seconds.

  Root cause: Cache invalidation is treated as fire-and-forget cleanup instead
  of a required post-mutation step. The voyageId is already in scope at the top
  of saveImport() — the roundId lookup can be done upfront.

  BUG-003 — L1 phantom event instead of warning
  ──────────────────────────────────────────────
  In capacity.service.js Step D, when an L1 booking's port cannot be resolved,
  the code pushes a load+discharge event on the SAME voyage (loadIdx === dischargeIdx).
  Net effect on onboardTEU is zero, but it creates misleading breakdown numbers
  ("+X TEU loaded / −X TEU discharged" at a single voyage) and emits no warning.
  L2 (Step C) correctly warns and excludes. L1 was written to "never disappear"
  which was a valid intent, but the implementation is wrong.

  Root cause: The L1 fallback was written to prevent cargo from silently disappearing,
  but it created a phantom pair instead of using the correct fix (load-only event + warning).

  BUG-004 — computeVoyagePreview single-voyage check
  ───────────────────────────────────────────────────
  computeVoyagePreview receives voyageId (the load voyage) and containerTypeId.
  It checks only the load voyage's onboardTEU + addedTEU. For bookings that span
  multiple legs (POL ≠ voyage.fromPort's route position, or POD is further than
  the load voyage's toPort), intermediate voyages are not checked.

  Root cause: The function was designed to check only one voyage. The `podId` parameter
  was never passed, making it structurally impossible to identify intermediate legs.

  BUG-005 — Dead /capacity/preview endpoint
  ──────────────────────────────────────────
  capacity.controller.js calls `capacityService.computeSegmentPreview` — a function that
  was renamed to `computeVoyagePreview` during Sprint 023. The controller was not updated.
  Additionally the controller passes legacy parameters (polId, podId, quantity) that the
  current function signature does not accept.

  Root cause: Sprint 023 renamed the service function but did not update the controller.

  BUG-010 — Cancelled voyages in the capacity chain
  ─────────────────────────────────────────────────
  The voyage query in Step A has no status filter:
  `Voyage.find({ _id: { $in: voyageIds } })`.
  Voyages with status 'Cancelled' are fetched and included in the sequence chain,
  and their bookings (if not cancelled themselves) contribute to onboardTEU.

  Root cause: No filter was added when the Voyage status model was implemented.

  BUG-012 — No whitelist validation on ?statuses= parameter
  ─────────────────────────────────────────────────────────
  The controller accepts any comma-separated string for the statuses override:
  `opts.statuses = req.query.statuses.split(',').map(...)`
  'Cancelled' is a valid booking status but must NEVER count toward capacity.
  No validation exists.

  Root cause: The ?statuses= parameter was added for diagnostic/planning use
  (e.g. "show capacity counting only Confirmed bookings") but the whitelist was
  never enforced.

  BUG-016 — Wrong warning code key in CapacityWarnings.jsx
  ─────────────────────────────────────────────────────────
  capacity.service.js emits warnings with code 'BOOKING_PORT_NOT_IN_ROUND'.
  CapacityWarnings.jsx ICONS map has 'BOOKING_PORT_NOT_IN_ROUTE' (different name).
  The fallback '⚠️' happens to be the same icon, so no visual regression occurs.
  But the code is wrong and will fail silently if the fallback icon ever changes.

  Root cause: The warning code was renamed at some point but the component was not updated.

  ARCHITECTURE CHANGES
================================================================================

  BUG-004 requires an architecture change to computeVoyagePreview:
  ─────────────────────────────────────────────────────────────────

  Current signature: computeVoyagePreview(roundId, voyageId, containerTypeId)
  New signature:     computeVoyagePreview(roundId, voyageId, containerTypeId, podId)

  `podId` is OPTIONAL for backward compatibility. If not provided, the function
  behaves as today (checks only the load voyage). If provided, the function:
    1. Finds the loadIdx for voyageId in the computed capacity data
    2. Resolves the dischargeIdx using the same port map logic from computeRoundCapacity
    3. Checks all voyages from loadIdx to dischargeIdx - 1 (inclusive)
    4. Returns the bottleneck voyage (minimum remainingAfter across all transited legs)
    5. Reports canFit = true only if ALL transited voyages have remaining capacity

  The internal call in booking.service.js create() must also pass the podId:
    computeVoyagePreview(voyage.roundId, String(data.voyageId), String(data.containerTypeId), String(data.podId))

  BUG-005 also requires updating the controller and route documentation:
  ────────────────────────────────────────────────────────────────────
  POST /capacity/preview body changes from:
    { roundId, polId, podId, quantity, containerTypeId }
  to:
    { roundId, voyageId, containerTypeId, podId? }
  where podId is optional (for the multi-voyage check if BUG-004 is also fixed).

      if (podId) {
        // Voyage-based resolution (REVISED — no global port map):
        // 1. Anchor on the booking's actual voyageId (the load voyage).
        // 2. Start from that voyage's index in the round's voyage sequence.
        // 3. Walk forward through the voyage sequence from there.
        // 4. Find the first voyage whose destination (toPort) matches podId.
        // 5. Use that voyage as the discharge point.
        const loadIdx = current.voyages.findIndex(v => String(v.voyageId) === String(voyageId));

        let dischargeIdx = null;
        if (loadIdx !== -1) {
          for (let i = loadIdx; i < current.voyages.length; i++) {
            if (String(current.voyages[i].toPort.portId) === String(podId)) {
              dischargeIdx = i;
              break;
            }
          }
        }

        if (loadIdx !== -1 && dischargeIdx != null && loadIdx <= dischargeIdx) {
          // Check all voyages from loadIdx to dischargeIdx (the container transits ALL of these)
          const transitVoyages = current.voyages.slice(loadIdx, dischargeIdx + 1);

          for (const tv of transitVoyages) {
            const onboardAfterOnThisVoyage = tv.onboardTEU + addedTEU;
            const remainingOnThisVoyage = cap != null ? cap - onboardAfterOnThisVoyage : null;
            if (remainingOnThisVoyage != null && remainingOnThisVoyage < minRemaining) {
              minRemaining = remainingOnThisVoyage;
              bottleneckVoyage = tv;
            }
          }

          if (bottleneckVoyage) {
            const onboardAfter   = bottleneckVoyage.onboardTEU + addedTEU;
            const remainingAfter = cap != null ? cap - onboardAfter : null;
            const canFit         = remainingAfter == null || remainingAfter >= 0;
            return {
              canFit,
              addedTEU,
              voyage: {
                voyageId:        bottleneckVoyage.voyageId,
                voyageNumber:    bottleneckVoyage.voyageNumber,
                onboardBefore:   bottleneckVoyage.onboardTEU,
                onboardAfter,
                remainingAfter,
                utilisationAfter: cap ? Math.round((onboardAfter / cap) * 100) : null,
                isBottleneck:    true,
              },
            };
          }
        }
      }
      // Fallback: check load voyage only (existing behaviour, also covers case where podId is null)
      // [existing return statement remains here]

================================================================================
  RISK ANALYSIS
================================================================================

  R1 — BUG-004: computeVoyagePreview signature change
       The function is called in two places:
         a) booking.service.js create() — will be updated in this sprint ✓
         b) No other callers found in the codebase
       Risk: Low. podId is optional (default null) so the existing behaviour is preserved
       if called without it. No regression risk.

  R2 — BUG-005: previewCapacity controller parameter change
       The HTTP endpoint POST /capacity/preview now accepts different body params.
       Any external client calling this endpoint with the old params (polId, podId,
       quantity) will get a 400 "voyageId is required" instead of a 500.
       This is an improvement. Risk: Low. The endpoint was previously always throwing 500.

  R3 — BUG-003: L1 fallback behaviour change
       Previously: phantom load+discharge event (net zero onboard effect).
       After fix: load-only event (TEU stays onboard through all subsequent voyages).
       This changes the capacity numbers for rounds that have L1 bookings with
       unresolvable ports. The NEW numbers are MORE CONSERVATIVE (higher onboard TEU)
       than the old phantom numbers (zero net effect). This is the safer direction —
       it over-estimates rather than under-estimates capacity usage.
       Risk: Medium. Operations teams may see slightly higher onboard numbers for
       affected voyages. A warning now appears in the capacity panel explaining why.

  R4 — BUG-010: Cancelled voyage exclusion
       If a round has a cancelled voyage, removing it from the chain shortens the
       voyage sequence. The `portAsFrom`/`portAsTo` maps will be built without the
       cancelled voyage's ports. Any booking attached to the cancelled voyage will
       then trigger the `BOOKING_PORT_NOT_IN_ROUND` warning (because the load port
       is no longer in the map).
       This is correct behaviour — bookings on cancelled voyages should not silently
       contribute to remaining voyages' capacity.
       Risk: Medium. This will surface previously hidden data issues (bookings on
       cancelled voyages) as capacity warnings. This is intentional and correct.

  R5 — BUG-012: Cached results bypass the new validation
       The cache stores results from the DEFAULT statuses (L2_STATUSES). When a caller
       uses ?statuses=, the cache is bypassed (useCache = !opts.statuses). So the
       validation only applies to non-cached requests. This is acceptable — the cache
       is only used for the default full-status computation.

  R6 — BUG-001: Moving roundId lookup to top of saveImport()
       Adding a Voyage.findById() call at the top of saveImport() adds one extra DB
       roundtrip. However, this is a single lean query on an indexed field. The voyage
       document is small. Performance impact is negligible (~1ms).
       The benefit (reliable cache invalidation) outweighs the cost.
