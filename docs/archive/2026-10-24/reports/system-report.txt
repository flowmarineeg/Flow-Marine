See system-flow.txt for detailed per-flow documentation (F-01 onward).

── SETUP ──
  Locations → Vessels → Agents → Container Types → Expense Types (+ cost
  classification) → Services + Routes

── OPERATIONS (dual booking layer) ──
  Round (auto-generates voyages) → Voyages (edit dates/status, manual add)
  → Bookings:
      Layer 1 (ManualBooking) — commercial reservation, multi-row cargoRows[]
      Layer 2 (Booking) — operational, one booking = one container,
        containerNumber primary key, Excel import (Round-scoped, multi-voyage
        resolution)
  → Expenses (Round, Voyage, or Port scope — Sprint 036)
  → Invoices (multi-booking, Final Loading eligible only, explicit Payment
    allocation)
  → Tracking (append-only position history)

── FINAL LOADING IMPORT ──
  Excel → SheetJS client parse → preview (Round-scoped voyage resolution)
  → save (bulkWrite) → saved rows = 'Final Loading'; all other bookings for
  that agent across the ENTIRE Round (not just one voyage) not in the
  manifest → 'Cancelled'. Any already-invoiced line item gets flagged
  `orphaned: true` on the Invoice, never silently.

── INVOICE / PAYMENT ──
  Create invoice (Booking/Voyage/Round type) from eligible Final Loading
  bookings → record Payment with explicit per-booking allocations[] →
  invoice status auto-derived (Issued/Partially Paid/Paid/Overdue) →
  void (not edit) to correct a payment

── REPORTING ──
  9 reports, run-on-demand: Round Capacity (per-voyage cards), Voyage
  Performance (L1/L2/combined + status filter), Revenue (L2+Final Loading),
  Expenses (Round/Voyage/Port + classification), Bookings (dual-layer),
  Voyage Profitability/Round P&L (Round+Voyage scope), Booking Revenue
  Details (pricing-group)

── DASHBOARD (SuperAdmin only) ──
  6 sections, independent widgets, shared filter bar, Quick Actions — every
  Tier-2 KPI reuses an existing report/service function, never a duplicate
  aggregation

── EXPORT ──
  13 modules (Excel), multi-module ZIP, Export Info metadata sheet on every
  file, Date Range filter on 4 modules

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Rules 1-20 are unchanged since Sprint 020 — see claude.md Section 6 for the
full, current list. Added since:

21. Booking (Layer 2): containerNumber is the PRIMARY match key everywhere
    (import, Final Loading reconciliation) — never voyageId+POL/POD text.
22. POL/POD on both booking layers are ALWAYS server-derived from the
    resolved Voyage — never client-editable, never stored independently
    of the voyage they came from.
23. Expense scope (Round/Voyage/Port) is ALWAYS inferred via
    expense.service.js#deriveScope() — never stored as its own field.
24. "Revenue" (a business term) means Layer 2, status = 'Final Loading'
    ONLY, everywhere except: (a) listing reports (Booking Report) that
    intentionally show every status, and (b) getRoundPnL's own legacy
    fields (kept for backward compatibility, not a template to copy).
25. Any KPI/number a Report or Service function already computes must be
    reused by the Dashboard, never recomputed by a second, parallel
    aggregation (Sprint 039's central rule).
26. VGM is always displayed in MT (metric tons) in every report — convert
    at the report layer (÷1000), never change Booking.vgm's own storage unit.
27. Required fields get exactly one red asterisk (text-red-400); optional
    fields get no marker at all — no "(optional)"/"(opt)" text anywhere
    (Sprint 042, system-wide).
28. Every mutation's onError handler uses the shared showErrorToast(error,
    actionType) — never a bespoke flat-string toast.error() call (Sprint 042).
29. Booking.dischargeStatus is independent of Booking.status — set ONLY by
    the 'discharge' import type, never changes `status` itself, and is
    read by the Capacity Engine as a presentation/onboard-carry-forward
    input only, never by rewriting the onboard/discharge recurrence
    (Sprint 045).
30. invoices:override is an ADDITIVE capability on top of the base
    rbac('invoices') route gate, never a replacement for it — a caller
    with zero invoices:update rights still cannot reach PUT /invoices/:id
    at all, override or not (Sprint 046).
