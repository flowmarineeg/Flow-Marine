Before writing Sprint 045, I need you to first verify that you fully understand the intended business flow. Do NOT assume anything.

This sprint is about the Booking module (Layer 1 + Layer 2), the Capacity Engine, and a new Discharge workflow.

The current system already has:

- Layer 1 = Estimated Booking.
- Layer 2 = Operational Booking.
- Final Loading Import.
- Capacity Engine based on Estimated + Final Loading.

The new business flow is as follows:

1. The current Final Loading import remains exactly as it is.
It still creates/updates the actual operational booking and confirms the final container details.

2. A new Import Type called "Discharge" will be added.

This import uses almost the SAME Excel template as the Final Loading import.

The user must select:

- Agent
- Round
- Voyage (required)
- Import Type = Discharge
- Excel file

3. During Preview validation, verify that every row in the uploaded discharge sheet belongs to the selected voyage.

The matching must be based on the voyage's actual POL/POD together with the booking matching logic already used in the system.

If rows belong to another voyage, they must be reported before import.

4. The Discharge import does NOT create bookings.

It only matches existing Final Loading bookings using the existing matching logic (Container Number, BOL, POD, etc.).

5. The import determines the ACTUAL operational result of those bookings.

After processing:

- Containers found in the discharge list become Discharged.
- Containers that were expected to discharge on that voyage but are NOT found in the discharge list become Remaining.

6. The Booking UI will gain two additional operational tabs:

- Discharged
- Remaining

These are additional operational views with filtering exactly like the existing Operational Booking tab (Round, Voyage, Status, etc.).

7. Capacity Engine must now use the discharge result.

Today it depends on Estimated + Final Loading.

After this sprint it must also consider the Discharge result.

Business rule:

- Discharged containers are removed from onboard capacity because they actually left the vessel.
- Remaining containers stay onboard and continue consuming capacity.
- Remaining containers should be visually highlighted (for example in red) inside Capacity Engine tables as an operational warning.

The capacity calculation itself should NOT be rewritten.
Only the source of the actual discharge event changes.

8. Existing Final Loading workflow must remain unchanged.
This sprint extends the operational lifecycle after Final Loading.
